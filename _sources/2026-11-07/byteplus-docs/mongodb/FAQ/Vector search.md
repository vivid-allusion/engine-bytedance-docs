## When creating a vector index, how do you choose the embedding method (manual vs. auto)?

The core deciding factor is whether you already have a vector generation pipeline (i.e., the complete process of generating and maintaining vectors) and whether you need to manage vector generation and synchronization yourself. The manual method is suitable for scenarios with existing self\-built models or third\-party vector pipelines. The auto method is suitable for those who want to set up quickly and avoid maintaining the vector generation pipeline. The detailed comparison is provided below.


|**Comparison items** |**Manual** |**Auto** |
|---|---|---|
|Vector generation |Generate vectors using your own embedding models and store them in collection fields |The system automatically invokes the Ark Embedding Model to generate vectors |
|Model source |Select any embedding model<br><br> |Use models provided by Ark. Currently, only Doubao\-embedding\-vision is supported. Refer to the console for details. |
|Data synchronization |Maintain vectors consistent with source data |The system automatically performs incremental vectorization through a change listening mechanism, eliminating the need for business\-side polling or manual triggering |
|Development threshold |**Higher**, requires writing code to call model APIs and maintaining synchronization logic |**Lower**. Configures the source text fields in the console, which is fully managed. |


<div data-tips="true" data-tips-type="warning" data-tips-is-title="true">warning</div>



* <div data-tips="true" data-tips-type="warning">The embedding model used for querying must be consistent with the one used for indexing. Otherwise, retrieval results will be inaccurate.</div>


* <div data-tips="true" data-tips-type="warning">When selecting manual mode, ensure that vector fields are updated synchronously after document updates. When selecting auto mode, this issue does not require consideration.</div>


* <div data-tips="true" data-tips-type="warning">Before using auto mode, ensure the Ark vector model service is activated and an API Key is obtained. For specific procedure, refer to <a href="https://docs.byteplus.com/en/docs/mongodb/Getting_Ark_API_Key?lang=en">Getting Ark API Key</a>.</div>

## How to select a similarity calculation method?

When creating a Search index, you need to specify the similarity calculation method using the `similarity` parameter. MongoDB Vector search supports three algorithms.

**Core selection principles**

Decide based on the normalization status of vector data and business scenarios, as detailed below:


* `cosine` (cosine similarity)

   Most commonly used, suitable for text embedding and semantic retrieval scenarios. It measures the directional similarity between two vectors, is insensitive to their magnitudes, and is a general choice for processing vectors generated by various embedding models (e.g., `text-embedding-v4`). If you cannot determine the normalization status of vectors, choosing `cosine` is a safe default option.

* `dotProduct` (dot product)

   If and only if vectors are normalized (i.e., their magnitude is 1), the dot product is equivalent to cosine similarity and offers higher computational efficiency. If your vectors come from a normalization model or you have manually normalized them, you can prioritize this method to improve performance.

* `euclidean` (Euclidean distance)

   Measures the absolute distance between vectors in space; smaller distances indicate greater similarity. Applicable to scenarios requiring absolute distance measurement in feature vector space, e.g., image feature comparison or physical feature similarity judgment.


**Configuration examples**

```JSON
fields: [{
  "type": "vector",
  "path": "embedding",
  "numDimensions": 1536,
  "similarity": "cosine"  // Replace with dotProduct or euclidean
}]
```

## How to select quantization/compression method?

Quantization technology significantly reduces storage and memory overhead by compressing the precision of vector data, making it a key method for lowering the cost of large\-scale vector search. You can specify the quantization strategy in the index definition via the `quantization` parameter.


* `none` (no quantization)

   Maintains the highest precision, with the highest cost. Storage and retrieval utilize original 32\-bit floating\-point vectors. Suitable for scenarios with a small number of vectors or extreme requirements for retrieval precision.

* `scalar` (scalar quantization)

   A balanced choice. Mapping 32\-bit floating\-point numbers to smaller integers (e.g.,` int8`) can reduce memory and storage overhead by about 75% (to 1/4 of the original), while maintaining good retrieval accuracy and typically retaining over 90% recall. This is the default option recommended for most production environments.

* `binary` (Binary Quantization)

   Extreme compression. Compressing each dimension to 1 bit (0 or 1) can reduce memory overhead by about 96% (to 1/24 of the original). To compensate for accuracy loss, MongoDB automatically performs a rescoring step, which involves re\-ranking the top\-K results of binary retrieval using the original full\-precision vectors to ensure the accuracy of the final results as much as possible. Suitable for vector scenarios at the million\- and billion\-scale, and for businesses that are extremely cost\-sensitive and can accept minor accuracy loss.


**Configuration examples**

```JSON
fields: [{
  "type": "vector",
  "path": "embedding",
  "numDimensions": 1536,
  "similarity": "cosine",
  "quantization": "scalar" // or binary
}]
```

## How to use multiple vector fields?

You can store multiple vector fields in the same collection. e.g., generate one vector for the product title, another vector for the product description, and yet another vector for the product image. All these fields can be defined in the same Search index.

<div data-tips="true" data-tips-type="warning" data-tips-is-title="true">warning</div>


<div data-tips="true" data-tips-type="warning">Currently, the <code>$vectorSearch</code> stage can only search one vector field at a time. This means you cannot directly search "title vectors" and "description vectors" simultaneously in a single query and automatically merge the results.</div>


**Recommended Approach: Query Separately, Then Merge Results**

You can execute `$vectorSearch` for each vector field separately, and then merge the results using an aggregation pipeline.

**Method 1: Merging with **  **`$unionWith`**

```JSON
// First, perform vector retrieval on title_embedding
const pipelineA = [
  { $vectorSearch: { path: "title_embedding", queryVector: [...], numCandidates: 100, limit: 20 } },
  { $project: { _id: 1, title: 1, score: { $meta: "vectorSearchScore" }, source: { $literal: "title" 
} } }
];

// Then, perform vector retrieval on desc_embedding
const pipelineB = [
  { $vectorSearch: { path: "desc_embedding", queryVector: [...], numCandidates: 100, limit: 20 } },
  { $project: { _id: 1, title: 1, score: { $meta: "vectorSearchScore" }, source: { $literal: "desc" 
} } }
];

// Use $unionWith to merge two results, then re-score and sort by weight in the application layer or subsequent aggregation stages.
db.products.aggregate([
  { $unionWith: { coll: "products", pipeline: pipelineA } },
  { $unionWith: { coll: "products", pipeline: pipelineB } },
  // Group by _id, merge scores, and sort.
  { $group: { _id: "$_id", title: { $first: "$title" }, scores: { $push: "$score" } } },
  { $addFields: { finalScore: { $sum: "$scores" } } },
  { $sort: { finalScore: -1 } },
  { $limit: 10 }
]);
```


<div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div>


<div data-tips="true" data-tips-type="default"><code>$unionWith</code> is a general MongoDB aggregation pipeline operator applicable to all versions. In the above example, we perform a search on two vector fields separately, then merge the results using <code>$unionWith</code>, and finally group by <code>_id</code> to sum the scores and sort. You can also assign different weights to different fields based on your business needs.</div>


**Method 2: Use **  **`$rankFusion`**

If your MongoDB version is 8.3 or higher, you can use the `$rankFusion` stage to merge results more concisely. `$rankFusion` automatically deduplicates and fusion sorts the results of multiple `$vectorSearch` operations.

```JSON
db.products.aggregate([
  {
    $rankFusion: {
      input: {
        pipelines: {
          // Search in title vector
          titleSearch: [
            { $vectorSearch: { 
                index: "vector_index",
                path: "title_embedding",
                queryVector: [0.1, 0.2, ...], 
                numCandidates: 100, 
                limit: 20 
            }}
          ],
          // Search in description vector
          descSearch: [
            { $vectorSearch: { 
                index: "vector_index",
                path: "desc_embedding",
                queryVector: [0.1, 0.2, ...], 
                numCandidates: 100, 
                limit: 20 
            }}
          ]
        }
      },
      // Optional: Assign weights to different pipelines
      combination: { 
        weights: { titleSearch: 0.6, descSearch: 0.4 } 
      }
    }
  },
  { $limit: 10 }
]);
```

## When do you need to add filter fields?

You need to add filter fields when you want to layer precise conditional filtering on top of vector search (e.g., 'query for products similar to a certain product description, with a price below 500 USD and sufficient stock').

**Operation Method**


1. Index Definition: In the `fields` of the Search index, specify ` type: \"filter\"` for the fields that need to be filtered (e.g., `price`, `category`, `inStock`).

2. Query Stage: In the `$vectorSearch` stage, use the `filter` parameter to pass MQL filter conditions.


**Index Definition Example**

```JSON
{
  fields: [
    { type: "vector", path: "embedding", ... },
    { path: "category", type: "filter" },
    { path: "price", type: "filter" }
  ]
}
```


**Query Example**

```JSON
db.collection.aggregate([
  {
    $vectorSearch: {
      index: "vector_index",
      path: "embedding",
      queryVector: [...],
      filter: { $and: [ { category: "Electronics" }, { price: { $lt: 500 } } ] },
      numCandidates: 100,
      limit: 10
    }
  }
]);
```


<div data-tips="true" data-tips-type="warning" data-tips-is-title="true">warning</div>



* <div data-tips="true" data-tips-type="warning">You must define the filter field in the index as a <code>filter</code> type, otherwise the filtering operation will not take effect.</div>


* <div data-tips="true" data-tips-type="warning">Filtered queries are usually slower than unfiltered queries because pre\-filtering needs to be performed before calculating vector similarity. Filtering performance depends on the selectivity of the filter conditions—the higher the selectivity (fewer matching documents), the better the performance usually is.</div>


* <div data-tips="true" data-tips-type="warning">Pre\-filtering data does not affect the similarity score (range 0\-1) returned by <code>$vectorSearch</code>.</div>


* <div data-tips="true" data-tips-type="warning">Enabling quantization (<code>scalar</code> or <code>binary</code>) can solve memory issues for pre\-filtered queries without requiring more memory.</div>



It is recommended to use highly selective fields (i.e., fields with many distinct values, such as `userId`) as filter fields to effectively narrow down the search scope and improve performance.

## How to estimate mongot's memory and storage?

Vector search relies on mongot, a search process independent of mongod. You need to reasonably plan storage and memory resources for mongot. The core idea for estimation is to first count the total vector data in mongod, and then deduce the storage and memory required for the mongot index. The final specifications recommend reserving 40% of the remaining space.

Estimation methods vary for different instance types, as follows.


|**Instance type** |**Estimation method** |
|---|---|
|Replica set instance |Fixed 2 mongot nodes, each holding a full index. |
|Sharding cluster instance |Each shard deploys 2 mongot nodes, each indexing data for its own shard. Resources required for a single shard can be estimated by dividing total resources by the number of shards (actual usage may vary slightly due to data distribution; it is recommended to reserve an appropriate buffer). |


You can estimate mongot memory and storage by following these steps.


1. **Query vector data size in mongod**

* Method A: Calculate using a formula (Recommended)

   If the vector dimensions and number of documents are known, you can use the following formula.

   ```Plain Text
   向量数据总大小（GiB）= 文档数量 × 向量维度 × 4 ÷ 1024³
   ```
   

   <div data-tips="true" data-tips-type="default" data-tips-is-title="true" data-wrapper-indent="1">tip   </div>
   

   * <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">4 represents that each dimension of the float32 (32\-bit single\-precision floating\-point number) type occupies 4 bytes.   </div>
   

   * <div data-tips="true" data-tips-type="default" data-wrapper-indent="1"><code>1024³</code> is used to convert bytes to GiB (1 GiB = 1024³ bytes).   </div>
   

   * <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">Vector dimensions are determined by the embedding model you use. An embedding model is an AI model that converts text into vectors, provided by vendors such as OpenAI, Google, and Cohere, and can also be obtained from open\-source communities like Hugging Face. Dimension reference for common models: OpenAI ada\-002 (1536), OpenAI 3\-large (3072), Cohere v3 (1024), Google gecko (768). MongoDB supports a maximum dimension of 8192. For details, see <a href="https://www.mongodb.com/zh-cn/docs/manual/reference/operator/aggregation/vectorsearch/">$vectorSearch (aggregation stage)</a>.   </div>
   

   Calculation example

   
   |**Scenario** |**Number of documents** |**Common Models** |**Dimension** |**Calculation process** |**Result** |
   |---|---|---|---|---|---|
   |Small knowledge base |100,000 |Google gecko |768 |100000 × 768 × 4 ÷ 1024³ |0.28 GiB |
   |Medium\-sized product catalog |1 million |OpenAI ada\-002 |1536 |1000000 × 1536 × 4 ÷ 1024³ |5.72 GiB |
   |Large corpus |10 million |OpenAI ada\-002 |1536 |10000000 × 1536 × 4 ÷ 1024³ |57.2 GiB |
   

   **Single vector size example**: 1536 dimensions × 4 = 6144 bytes ≈ 6 KiB.

* Method B: Querying via MongoDB Shell

   If you are unsure about vector dimensions or if there are multiple vector fields in the collection, execute the following script in MongoDB Shell for automatic calculation.

   ```JavaScript
   // Usage: Replace <collection name> and <vector field name> with actual values, then execute
   var collName = "<集合名称>";       // e.g. "products"
   var fieldName = "<向量字段名>";    // e.g. "embedding"
   var sampleSize = 1000;             // Sample size, adjustable based on data scale
   
   var result = db.getCollection(collName).aggregate([
     { $sample: { size: sampleSize } },
     { $match: { [fieldName]: { $exists: true } } },
     {
       $group: {
         _id: null,
         avgDim: { $avg: { $size: "$" + fieldName } },
         count: { $sum: 1 }
       }
     }
   ]).toArray();
   
   if (result.length === 0) {
     print("未找到包含字段 " + fieldName + " 的文档，请检查字段名是否正确。");
   } else {
     var avgDim = result[0].avgDim;
     var sampledCount = result[0].count;
     var totalDocs = db.getCollection(collName).estimatedDocumentCount();
     var vectorSizeBytes = totalDocs * avgDim * 4;
     var vectorSizeGiB = vectorSizeBytes / (1024 * 1024 * 1024);
   
     print("===== 向量数据估算结果 =====");
     print("集合名称:       " + collName);
     print("预计文档总数:    " + totalDocs);
     print("采样文档数:      " + sampledCount);
     print("平均向量维度:    " + avgDim.toFixed(0));
     print("单条向量大小:    " + (avgDim * 4 / 1024).toFixed(2) + " KiB");
     print("向量数据总大小:  " + vectorSizeGiB.toFixed(2) + " GiB");
   }
   ```
   

   Expected output example

   ```Plain Text
   ===== 向量数据估算结果 =====
   集合名称:       products
   预计文档总数:    1000000
   采样文档数:      987
   平均向量维度:    1536
   单条向量大小:    6.00 KiB
   向量数据总大小:  5.72 GiB
   ```
   

   <div data-tips="true" data-tips-type="default" data-tips-is-title="true" data-wrapper-indent="1">tip   </div>
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">If the collection contains multiple vector fields (e.g., title_embedding and image_embedding), modify `fieldName` and execute the script separately, then sum the results for each field.   </div>
   

2. **Calculate disk space required for mongot index**

   After obtaining the total vector data size, you can calculate the disk space required by mongot.

   First, confirm if you have also enabled full\-text search indexes. The difference in the disk space required by mongot, depending on whether it's enabled or not, is as follows:

   * Vector search only: Total disk requirement = Vector index disk size (Read the **Vector Index Disk Size** section)

   * Vector search + Full\-text search: Total disk requirement = Vector index disk size + Full\-text index disk size (read all content)

   **Vector index disk size**

   ```Plain Text
   向量索引磁盘大小 = 向量数据总大小 × 1.0（基线）
   ```
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">Description   </div>
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">The formula above calculates the base size of the vector index. The HNSW (Hierarchical Navigable Small World) structure generates additional metadata overhead, but it is usually small. This overhead is uniformly covered in Step 4 of this document by allocating 40% redundant space.   </div>
   

   **Full\-text index disk size (if applicable)** 

   Additional disk usage must be calculated if full\-text search indexing is enabled concurrently.

   ```Plain Text
   全文索引磁盘大小 = 索引文本总大小 × 扩展系数
   ```
   

   The expansion factor depends on the tokenization strategy; for standard tokenization, it is generally 1.5 to 3 times, and it is recommended to estimate at **2 times**. For details, refer to [Resource Allocation Precautions for mongot Deployment](https://www.mongodb.com/zh-cn/docs/manual/tutorial/mongot-sizing/advanced-guidance/resource-allocation/).

3. **Calculate Memory Required for mongot Indexes**

   After disk specifications are determined, calculate memory requirements next. Total memory requirements consist of the following three parts:

   ```Plain Text
   总内存需求 = 向量索引内存 + JVM 堆内存 + 文件系统缓存
   ```
   

   <div data-tips="true" data-tips-type="default" data-tips-is-title="true" data-wrapper-indent="1">tip   </div>
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">File system cache is automatically managed by the operating system; you need to actively plan for <strong>vector index memory</strong> and <strong>JVM heap memory</strong>.   </div>
   

   **Vector Index Memory**

   ```Plain Text
   向量索引所需内存 = 向量索引磁盘大小 × 1.25
   ```
   

   <div data-tips="true" data-tips-type="default" data-tips-is-title="true" data-wrapper-indent="1">tip   </div>
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">MongoDB officially recommends adding an additional 20% to 25% buffer space to the index size for the runtime overhead of the HNSW graph structure in memory. Therefore, the factor is 1.25 (i.e., 100% + 25%). For details, see <a href="https://www.mongodb.com/zh-cn/docs/manual/tutorial/mongot-sizing/advanced-guidance/resource-allocation/">Resource Allocation Precautions for mongot Deployments</a>.   </div>
   

   Calculation example: If the vector index disk size is 5.72 GiB, the required vector index memory = 5.72 × 1.25 = 7.15 GiB.

   * **Reduce memory requirements through vector quantization**

      When the index size is large, vector quantization can compress floating\-point vectors (e.g., float32) into low\-precision representations to reduce memory usage. Quantization methods supported by MongoDB are as follows:

      
      |**Quantization method** |**Memory reduction effect** |**Applicable scenarios** |
      |---|---|---|
      |No quantization |1x (baseline) |Strict requirements for recall accuracy |
      |Scalar quantization |Approximately 3.75x (i.e., reduced to 1/3.75 of the original, about 26.7%) |Balance solution for accuracy and resources |
      |Binary quantization |Approximately 24x (i.e., reduced to 1/24 of the original, about 4.2%) |Large\-scale, highly cost\-optimized |
      

      <div data-tips="true" data-tips-type="warning" data-tips-is-title="true" data-wrapper-indent="2">warning      </div>
      

      <div data-tips="true" data-tips-type="warning" data-wrapper-indent="2">When the vector index disk size <strong>exceeds 3 GiB</strong>, it is recommended to evaluate enabling quantization. For details, see <a href="https://www.mongodb.com/zh-cn/docs/vector-search/about/vector-quantization/?embedding=auto&interface=mongosh&data-source=new">vector quantization</a>.      </div>
      

4. **Add a safety margin to determine the final specifications.** 

   Steps 2 and 3 calculate the minimum specifications required for the current workload. In a real production environment, an additional safety margin must be added to accommodate future growth and operational needs.

   ```Plain Text
   推荐磁盘空间 = mongot 总磁盘需求 ÷ 0.6
   推荐内存大小 = mongot 总内存需求 ÷ 0.6
   ```
   

   Reserving 40% means that the current load only accounts for 60% of the final specification. Therefore: final specification = current load ÷ 0.6.

   **The 40% margin is composed as follows:** 

   
   |**Remaining items** |**Description** |
   |---|---|
   |Index rebuild space |Modifying index definitions requires retaining both new and old indexes, which necessitates additional space. |
   |Data growth buffer |Reserve space for the natural growth of business data. |
   |Runtime overhead |Overhead from JVM garbage collection, file system cache, operating system, etc. |
   |Read\-only protection threshold |Mongot will enter read\-only state when disk utilization reaches 90% |
   

   <div data-tips="true" data-tips-type="default" data-tips-is-title="true" data-wrapper-indent="1">tip   </div>
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">If a precise estimation is not currently possible, it is recommended to keep the mongot storage space consistent with mongod's initial storage configuration value, and then adjust it based on Monitoring.   </div>

**Complete Estimation Example**

Below is a complete calculation process for a medium\-sized e\-commerce recommendation scenario. **This example corresponds to the "Medium (vector data size 1~10 GiB)" configuration in the "Quick Reference Table for Specifications" above**, and can serve as a validation reference for precise calculations.

**Business Assumptions**:


* 1 million item documents, each containing 1536\-dimensional vectors (OpenAI ada\-002)

* Full\-text search is also enabled (standard tokenization, indexed text approximately 500 MiB)

* Quantization is not enabled

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1"><strong>Logic for determining example JVM heap</strong>   </div>
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">The size of the JVM heap depends on the final chosen memory specifications; mongot by default allocates 25% of the system's available memory to the JVM heap. Therefore, it is necessary to first assume a specification and then verify if it is sufficient.   </div>
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">This example, based on the 'medium' memory range (32~64 GiB) from the specification quick reference table, takes the minimum value of 32 GiB as the assumed specification:   </div>
   

   * <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">JVM Heap = 32 × 25% = 8 GiB   </div>
   

   * <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">Total Memory Requirement = Vector Index Memory 7.15 GiB + JVM Heap 8 GiB = 15.15 GiB   </div>
   

   * <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">Add 40% buffer: 15.15 ÷ 0.6 = 25.25 GiB → Rounded up to 32 GiB   </div>
   

   * <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">✅ Validation passed: 25.25 GiB ≤ 32 GiB   </div>
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">If validation fails, recalculate with a larger specification (e.g., 64 GiB) until validation passes.   </div>
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">For details, see <a href="https://www.mongodb.com/zh-cn/docs/manual/tutorial/mongot-sizing/advanced-guidance/hardware/">hardware Precautions for mongot deployment</a>.   </div>
   


|**Calculation item** |**Result** |**Calculation process** |
|---|---|---|
|Step 1: Total vector data size |5.72 GiB |1,000,000 × 1536 × 4 ÷ 1024³ |
|Step 2: Mongot total disk requirement |6.72 GiB |Vector index disk size 5.72 GiB + full\-text index disk size (500 MiB × 2) |
|Step 3: mongot total memory requirement |15.15 GiB |Vector index memory 7.15 GiB (5.72 × 1.25) + JVM heap 8 GiB (assuming 32 GiB × 25%) |
|Step 4: Recommended disk (with 40% headroom) |≈ 11.2 GiB |6.72 ÷ 0.6 |
|Step 4: Recommended Memory (with 40% headroom) |≈ 25.25 GiB → rounds up to 32 GiB |15.15 ÷ 0.6 |

**Replica set instance vs. sharding cluster instance (3 shards) comparison:** 


|**Calculation item** |**Replica set instance (single node)**  |**Sharding cluster instance (single shard)**  |
|---|---|---|
|Vector index disk size |5.72 GiB |≈ 1.91 GiB（5.72 ÷ 3） |
|Mongot total memory requirement |15.15 GiB |≈ 5.05 GiB（15.15 ÷ 3） |
|Recommended disk (including 40% margin) |≈ 11.2 GiB |≈ 3.7 GiB（11.2 ÷ 3） |
|Recommended memory (with 40% reserve) |≈ 25.25 GiB → rounds up to 32 GiB |≈ 8.4 GiB (25.25 ÷ 3) → Round up |


**Example recommended configuration:**  32 GiB memory / 200 GiB disk / 4 vCPU (Source: MongoDB official medium specification table for low CPU workloads, see configuration description in the 'Specification Quick Reference' above. 4 vCPU is the lower limit for medium specifications; for QPS \> 100, it is recommended to start with 8 vCPU.)
