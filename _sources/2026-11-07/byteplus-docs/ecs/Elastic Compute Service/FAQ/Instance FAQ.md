### Why does the Docker container in the ECS instance automatically run Ubuntu 18.04 image all the time?

The possible causes of this issue are as follows:


* **Default image setting**

   You may not specify the image to be used when creating the Docker container. Therefore, the container defaults to the Ubuntu 18.04 image from Docker Hub.

* **Auto\-start setting**

   You may enable the auto\-start setting when configuring your Docker container. Therefore, the container automatically starts and runs Ubuntu 18.04 image every time the instance starts.

* **Orchestration tool setting**

   If you are using orchestration tools such as Docker Compose or Kubernetes, these tools might default to the Ubuntu 18.04 image for container startup.

* **Custom image error**

   If you use a custom image but fail to build and deploy it correctly, Docker will then use the default Ubuntu 18.04 image.


You can try the following solutions to solve the problem:


* **Check the startup command and configuration of the Docker container**

   Make sure when creating or starting the container, you specify the required image rather than use the default Ubuntu 18.04 image.

* **Set the automatic restart policy for the container**

   If you enable the automatic start when configuring the Docker container, choose an appropriate automatic restart policy to handle unexpected situations.

* **Check the configuration file of orchestration tools**

   If you use orchestration tools such as Docker Compose or Kubernetes, make sure the correct image that you require is specified in the configuration file.

* **Create and deploy the custom image correctly**

   If you need to use a custom image, make sure the image is correctly built and pushed to the Container Registry.

### How to improve the read/write performance of ECS instances?

When read/write latency of ECS instances occurs, multiple factors are required to be considered, such as geographic location, instance configuration, cache technology, and load balancing. Detailed solutions are as follows:


* **Select the optimal geographic location**

   Select a region near your business to create an ECS instance to reduce data transmission time and latency. This can improve instance performance and accelerate access.

* **Optimize read/write performance**

   The read/write speed is associated with your ECS instance configuration. You can consider adjustments of instance compute resources, memory, and cloud volume configuration based on your needs. The platform provides a rich variety of instance types, which you can adjust based on your needs.

* **Use cache technology**

   Cache technology can be used to improve read/write latency. By caching frequently used data in memory, you can reduce the number of disk accesses and thus improve read/write speeds. The platform offers multiple cache services, such as Redis and MongoDB. You can select the appropriate cache technology based on your needs.

* **Use Classic Load Balancer (CLB)** 

   If you have multiple ECS instances, you can consider CLB to distribute the load of read/write requests. CLB can distribute requests evenly across multiple ECS instances, thereby improving overall read/write speeds.

### What is the difference between the base frequency, Max Turbo Frequency, and all\-core turbo frequency of an Intel processor?


* Processor Base Frequency: Also known as the default frequency, it is the reference frequency that the CPU can still achieve even under extreme conditions.

* Max Turbo Frequency: Also known as the single\-core maximum frequency, it specifically refers to the maximum frequency that the highest\-quality core within the CPU can achieve.

* All\-core turbo frequency: Also known as the all\-core maximum frequency, it refers to the maximum frequency that all physical or logical cores within the CPU can achieve at the same time.


Theoretically, the higher the Max Turbo Frequency, the stronger the single\-core performance of the CPU is, and thus leading to higher efficiency in workload scenarios such as decompression. However, in a wider range of high\-load application environments, all\-core turbo frequency is actually the key metric that most significantly and directly affects CPU performance output.

<span id=".5L2_55SoZnJlZeaIli9wcm9jL21lbWluZm_lkb3ku6Tmn6XnnIvlrp7kvovnmoTmgLvlhoXlrZjvvIzkuLrku4DkuYjmr5Tlrp7kvovop4TmoLzlrprkuYnnmoTlhoXlrZjlsJHkuIDkupvvvJ8="></span>
### Why is the total memory displayed by the `free` command or `/proc/meminfo` slightly less than the memory specified in the instance specification?

The total memory displayed by the `free` command or the `/proc/meminfo` is the available memory of the system.

Available memory refers to the total memory available for allocation to the kernel and applications after the operating system starts. Available memory excludes memory reserved by the BIOS for special purposes, as well as memory used for kernel code segments and metadata (struct page) for memory page management. Therefore, available memory is slightly less than the memory specified in the instance specification.

In addition, the memory used by kernel code segments and similar components varies slightly based on operating systems. Therefore, even when the memory specified in the instance configuration is the same, the available memory may differ slightly for instances with different operating systems.

### How to migrate data from a Linux system volume?

When your business scales up, the existing system volume may no longer meet your needs. You can migrate system volume data to a data volume or another instance based on your needs.


* Migrate data from the system volume to a data volume.

   1. Execute the `df -h` command to view the usage rate of the system volume (for example: /mnt/eee).

   2. Mount the data volume for data storage to a directory (for example: /mnt/disk1) on an ECS instance.

   3. Copy the data from instance system volume (/mnt/eee) to the data volume (/mnt/disk1).

   4. Unmount the data volume from /mnt/disk1 and remount it to /mnt/eee.

   5. Execute the `vi /etc/fstab` command to modify the fstab file by adding the following content. This can specify the mount point of the data volume to enable auto\-mount on boot.

      `/dev/disk1 /mnt/eee ext4 defaults 0 0`

   6. Restart the ECS instance to check if the instance runs normally. For example, verify if the database can be connected and accessed. If no exception occurs, the data migration is completed.

* Migrate the system volume data to other instances.

   1. Create a custom image for source instance to back up the instance data from system volume. For specific steps, refer to [Creating custom images](https://docs.byteplus.com/en/docs/ecs/Creating-custom-images-1).

   2. Use the custom image of the source instance to create the target instance. After this, the system volume data can be migrated. For specific actions, refer to [Purchasing an instance based on a custom image](https://docs.byteplus.com/en/docs/ecs/Buying-ECS-instances-with-custom-images).

   3. Check the data storage and related data status within the newly created ECS instance. Make sure your business can operate normally after instance data migration. If no exception occurs, the data migration is completed.

* Automated O&M scenarios, where the number of instances requires automatic adjustments and the instance lifecycle needs flexible management based on business.

* The total resource amount remains relatively stable, but resources must be used flexibly based on business needs.

### How to calculate the effective time of an RI?

After you purchase an RI, it takes effect immediately. The effective time is calculated on the hour. The billing starts from the effective time and ends at 23:59:59 of the expiration date.

For example, you have purchased an RI at 2022\-11\-01 22:45:00, with a validity period of one year. Therefore, the effective time and billing start time of this RI are 2022\-11\-01 22:00:00, and the end time is 2023\-11\-01 23:59:59. If you have a matching instance when you purchase an RI, the RI will be used to deduct the hourly bill from 2022\-11\-01 22:00 to 23:00 until the RI expires.

<span id=".6aKE55WZ5a6e5L6L5Yi45pu05pS55ZCO55qE55Sf5pWI5pe26Ze05aaC5L2V6K6h566X77yf"></span>
### How to calculate the effective time of a modified RI?

After you modify an RI, a target RI is generated along with the immediate invalidity of the modified RI (original RI). The effective time of the target RI is calculated on the hour.

Suppose at 13:35:00 on December 20, 2022, you successfully changed an RI with the specification ecs.g2i.2xlarge (RI1) into two RIs with the specification ecs.g2i.xlarge (RI2 and RI3).

Then:

RI1 would expire at 13:35:00 on December 20, 2022. It could only be used to offset hourly bills for ecs.g2i.2xlarge instances generated before 13:00:00 on December 20, 2022.

RI2 and RI3 were also created at 13:35:00 on December 20, 2022. They could be used to offset hourly bills for ecs.g2i.xlarge instances from 13:00:00 on December 20, 2022 until they expired. Additionally, the resources they could offset and reserve would change from ecs.g2i.2xlarge to ecs.g2i.xlarge. If RI2 and RI3 successfully matched with an instance immediately after they took effect, they would start to deduct the hourly bill of the ecs.g2i.xlarge instance from December 20, 2022 13:00:00.

## Shared instance FAQ

<span id="bs5wL0HW"></span>
### What does "Shared" in Shared instances mean?

The "Shared" in Shared instances refers to the CPU resource sharing mode rather than the sharing of IP address.

<span id="1J0if7MX"></span>
### What is the difference between Shared instance types and Dedicated instance types (such as General\-purpose, EBM, and GPU\-accelerated)?

**Based on whether CPU resources are shared, instances provided by the platform can be classified into shared and dedicated types. The two types have identical configuration options for storage (such as memory and system/data volumes) and network (such as Internet bandwidth), and differ only in CPU computing performance**. Details are as follows:


|Type |Covered instance types |Difference description |
|---|---|---|
|[Shared](https://docs.byteplus.com/en/docs/ecs/Shared) |* Shared Standard Type S series |In the non\-binding CPU scheduling mode of shared instances, each vCPU is randomly assigned to any idle CPU hyper\-thread. vCPUs from different instances may compete for physical CPU resources, leading to **unstable fluctuations in computing performance under high load**. This mode guarantees an availability SLA but not a performance SLA. |
|[Dedicated](https://docs.byteplus.com/en/docs/ecs/Introduction-to-instance-types#I6PbNGwC) |Instances other than the Shared type, such as General\-purpose, EBM, and GPU Accelerated |Adopts a fixed CPU scheduling mode, where each vCPU is associated with a physical CPU hyper\-thread. There is no competition for CPU resources between instances, providing **stable compute performance** and a strict SLA guarantee. |


<span id="ANU9dKM8"></span>
### Can I have ensured performance of Shared instances?

Shared instances have no computing performance stability ensured. Shared instances use an unassociated CPU scheduling mode where each vCPU is randomly allocated to a free CPU hyper\-thread. The vCPUs of different instances compete for physical CPU resources, thereby causing unstable computing performance under high load. Shared instances mainly share the performance of computing resources at lower costs. However, computing stability is not ensured.

&nbsp;
