The system table `system.view_tables` contains detailed information about all materialized views in the current database, including the definitions of materialized views, associated base tables, refresh configurations, status information, and other information, helping you monitor and manage the configuration and operational status of materialized views.

<span id="bb1ad1eb"></span>
## Cautions

Currently, only engine versions v2.7 and above support querying the materialized view system table. Before querying, you can log in to the ByteHouse Enterprise Edition console. Click **Cluster management**, click the target cluster you need to query, and view the engine version in **Basic information**.

## Column names


|**Field name** |**Data types** |**Field descriptions** |
|---|---|---|
|database |String |Name of the database to which the materialized view belongs. |
|table |String |The name of the materialized view. |
|uuid |UUID |The globally unique identifier of the materialized view, which is automatically generated by the system. |
|definition |String |The creation statement for materialized views. |
|base_tables |Array(String) |The base table that a view depends on. |
|dependent_table |Array(String) |The partitioning of a materialized view depends on the partition definition of the base table: if the partitions of the base table can be converted into the partitions of the materialized view's target table by a function, the materialized view is considered to depend on the base table. |
|non_dependent_tables |Array(String) |Partitioning of base tables can only be aligned with one of the base tables; the other tables are not dependent base tables. |
|target_table |String |The target table name for materialized view data storage. |
|partition_diffs |Array(String) |The current view displays a list of differences in partition distribution between this refresh and the previous refresh: `add_partitions` represents the partitions added in this refresh, and `drop_partitions` represents the partitions deleted in this refresh. The system will automatically create corresponding refresh tasks based on the difference list. |
|latest_visible_partitions |Array(String) |Partition version list information for the current base table. |
|previous_partitions |Array(String) |The refreshed partition version list |
|refresh_type |String |Data refresh types for materialized views. `SYNC` is the sync view. |
|refresh_start_time |String |The time when the materialized view starts refreshing. |
|refresh_interval |String |The refresh interval of the materialized view. |
|active |UInt8 |It indicates whether the materialized view is currently in a valid state. When the base table is modified in a way that affects the materialized view, the view is marked as being in an invalid state. Views in an invalid state cannot be rewritten or refreshed, and their status cannot be changed directly. To restore normal functionality, you must delete and recreate them. |
|enable_refresh |UInt8 |Indicator of whether the auto\-refresh feature is enabled. `1` indicates that auto\-refresh is enabled; `0` indicates that auto\-refresh is disabled and manual refresh is required. |
|enable_query_rewrite |UInt8 |Flag indicating whether query rewrite is enabled. `1` means enabled, `0` means this feature is disabled. |
|base_table_validity |UInt8 |Whether the base table structure is valid. If operations such as RENAME COLUMN, MODIFY COLUMN, or DROP COLUMN are performed on relevant columns of the base table, or if ALTER TABLE or DROP TABLE operations are performed on the base table, the value of `base_table_validity` will be automatically set to false. In this case, the view will stop refreshing and updating.<br><br>To restore the base table to a valid state, you can execute the `ALTER...MODIFY PROPERTY` command and set `base_table_validity` to true. Here is an example:<br><br>```SQL```<br>```ALTER TABLE db_name.mv_name MODIFY PROPERTY base_table_validity = true;```<br><br><br>If the base table does not require repair or you decide not to repair it, you can directly delete the corresponding materialized view to clean up invalid objects. |
|refresh_work_period |String |The time window that material views allow executing refresh operations. |
|coordinator_address |String |Address information of the coordinator responsible for scheduling materialized view refresh tasks. |
|refresh_status |String |It indicates the current running status of refresh tasks and the number of tasks in progress, including the status indicator (running) and the number of running tasks (running_tasks). |
