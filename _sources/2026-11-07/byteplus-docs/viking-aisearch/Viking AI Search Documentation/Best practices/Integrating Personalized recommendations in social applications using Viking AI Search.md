# 1. Data preparation

Before you start configuration, **you must first complete all tasks in the data preparation phase.** 

<div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div>


<div data-tips="true" data-tips-type="default"><strong>We recommend filtering fields instead of uploading all fields.</strong> Invalid fields increase your token cost and interfere with the large model's analysis.</div>


<div data-tips="true" data-tips-type="default">You can remove oversized and low\-value fields (such as large blocks of HTML source code or Base64\-encoded images), and retain data fields that help the recommendation model understand content semantics and user interests.</div>


<span id="4591cd5f"></span>
## 1. Item dataset

The item dataset includes core metadata for posts, such as the Title, body text, visuals, and Tags. This dataset is the foundation for the recommendation engine to build a multimodal semantic index and achieve precise item retrieval.

The following is a general **list of recommended core fields for item data in the Social industry**. Including the following key information will help improve overall performance.

If some fields are missing, filter by your existing business fields and upload the data.


|**Example field name (your actual field name does not need to match this exactly)**  |**Purpose and recommendation scenarios** |
|---|---|
|**`item_id`** |**The unique identifier for the post**. A system\-level identifier used for data deduplication, updates, and recording user events such as clicks. |
|**`images`**<br><br> |**Image information associated with the post**. Used for multimodal semantic understanding, the system analyzes the visual features of the image to enable search by image or recommendations based on visual style. Note that **all Image URLs must be publicly accessible**; otherwise, the product data loses its visual information. Recommendation: **Images should be clear with a prominent subject**; **dimensions should be at least 300x300 pixels, and the size should be kept within 5 MB**. Otherwise, processing efficiency and quality will be affected. |
|**`post_time`**<br><br> |**The post's release time**. Used for timeliness control, it allows you to configure a strategy to boost new posts or filter out expired content. |
|**`user_id`**<br><br> |**The publisher's unique identifier**. Used for author\-based recommendation strategies, such as a following feed, or for content diversification to avoid recommending too much content from the same author. |
|**`username`**<br><br> |**The poster's username**. Used to support searches for specific creators or to provide an autocomplete feature in the search box. |
|**`title`** |**The Title of the post.**  Used for precise item retrieval based on keyword matching and semantics. |
|**`content`**<br><br> |**The body text of the post**. Includes core ideas and semantics. A large model will analyze this in depth for precise, semantic\-based item retrieval. |
|**`comments`**<br><br> |**Comment count**. Reflects the content's engagement level. Use it to filter highly discussed content or help gauge the community atmosphere. |
|**`likes`** |**Like count**. A core popularity metric for measuring content popularity. It often serves as an important weighted feature in recommendation and sorting models. |
|**`shares`**<br><br> |**Share count**. Represents the content's distribution value. High\-share content often has greater viral potential and can be used for weighted recommendations. |
|**`tags`**<br><br> |**A list of tags associated with the post**. Used for categorized content search, matching user interest tags, and cohort\-based item retrieval. |
|**`status`**<br><br> |The lifecycle status of the post (e.g., Published, Draft, Deleted). This is a fundamental control for the proper operation of the recommendation system. It is required for strict, low\-level filtering to avoid pushing invalid content to users. |
|**`is_audit`** |The security review status of the post (e.g., Machine\-approved, Under manual review, Rejected). A core risk management field that ensures content distributed to users is fully compliant. Non\-compliant content that has not passed the review is never recommended. |
|**`latitude`**` / `**`longitude`** |The geographical coordinates of the post (Latitude and longitude). The core of LBS (location\-based service) recommendations. Used for precise distance calculation and regional item retrieval on "Same city" and "Nearby" pages. |

## 2. User event dataset

User event data records a user's end\-to\-end interaction history within the community, such as browsing, Liking, and commenting. This data is key for the recommendation engine to dynamically capture the evolution of user interests and build personalized profiles.

The following is a list of recommended core fields for user event data in **content community/Social platform** scenarios. Including the following key information will help improve overall performance.

If some fields are missing, filter by your existing business fields and upload the data.


|**Example field name (Your actual field name does not need to match this exactly)**  |**Purpose and recommendation scenarios** |**Recommended attributes** |
|---|---|---|
|**`user_id`** |**User unique identifier**. Identifies who is performing the user event. The system uses this ID to link the user's historical user event sequence and build a personalized interest profile. |User ID |
|**`item_id`**<br><br> |**Item ID**. The system uses this ID to associate specific post content (such as text, tags) to understand what a user viewed or liked. |Item ID |
|**`event_type`** |**Event type**. The name of the action for user events, such as Exposure, Click, Favorite, and Purchase . **Must include the "Exposure" event and one positive user event other than exposure.**  |Event type<br><br> |
|**`event_timestamp`** |**Event timestamp**. A timestamp in milliseconds. Used to build a **chronological user event sequence**. Recommendation models heavily rely on chronological order to capture **real\-time changes** in user interest (e.g., user events in the last 10 minutes are weighted much higher than user events from 30 days ago). |Event time |
|**`event_scene`** |**Event scene**. Indicates the specific location where the user event occurred, such as `homepage` (homepage recommendation feed), `search` (search results page), and `detail` (details page). Helps the model provide more precise recommendation strategies for different scenarios. |Event scene |

## 4. Data specifications and recommendations


|Standard |Detailed description |
|---|---|
|**Cross\-table consistency** |All item_id values in the user event data must correspond to an item_id in the item data. Otherwise, the system considers the user event record invalid and discards it. |
|**Time field specifications** |Sync the latest business data; otherwise, the Last 7 days recommendation feature will not function. The event timestamp must be a 13\-digit Unix timestamp in milliseconds (Int64 type). The item release time supports ISO format, regular strings (e.g., 2026\-01\-12 09:30:00), or a timestamp, and the system automatically converts it to ISO format for storage. |
|**Nested structure limitations** |The system supports up to 3 levels of nested objects. Complex SKU data must be flattened. |
|**Schema consistency** |Fields with the same name within the same dataset must have the same data type; otherwise, index construction fails (e.g., the likes field cannot be both a number and a string). |
|**Sample file format** |Only JSONL files are currently supported. Support for CSV, JSON, and other formats will be added later. |

### 3. Recommendation feature integration logic

<div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div>


<div data-tips="true" data-tips-type="default">If you are a developer, see <a href="https://www.volcengine.com/docs/85296/1788543?lang=zh">Recommend \- Personalized Recommendation</a></div>


<div data-tips="true" data-tips-type="default">If you are a business user, see the following.</div>


To provide a smooth and accurate "feed" and "related reading" experience on your Social platform, we strongly recommend adopting the standardized Three\-tier architecture of  **"Frontend interaction \-\> Business backend relay \-\> AI Recommendation service"** .

<span id="fc94fad6"></span>
#### Complete data flow path


* **Frontend triggers a recommendation request**: a user opens the app's homepage (triggering a homepage recommendation) OR clicks to enter the details page of an article OR Video (triggering a details page recommendation). The frontend requests a new batch of content from the business backend.

* **Business backend encapsulation and state injection**: after the business backend intercepts the request, it sends a POST request to the AI Recommendation API. In this stage, in addition to attaching the API Key for authentication, the backend must explicitly inject critical system and user variables:

   * Inject the `user_id` Unique identifier of the current operator.

   * Inject the `session_id` of the current session.

   * For detail page scenarios, you must explicitly pass the ID of the content currently being viewed through `parent_items`.

* **Engine performs Item retrieval and Sorting**: The AI Recommendation engine performs complex two\-sided matching and Sorting based on user profiles, content features, and the Filter conditions passed from the backend, ultimately outputting a personalized content list.

* **Backend data formatting and frontend rendering**: After receiving the Recommendation results (`rec_results`), the business backend combines them with the platform's own interaction data (e.g., whether the user has liked or favorited the Item) and returns them to the frontend. After parsing the data, the frontend renders it as an infinite\-scroll waterfall feed or a Video list.


<span id="ecb3d63e"></span>
#### Why must transfers and controls be routed through the "business backend"?

In a Recommendation system, the business backend's role as a gateway is not only to hide the API Key but also serves as a central hub for ensuring Recommendation quality and controlling bandwidth costs:


*  **🛡️ Fraudulent traffic prevention and data reduction**

   * **Strictly limit the number of results per request**: To ensure an extremely fast API response, the platform enforces a `page_size` limit of 400. Strictly control this parameter on the business backend to avoid `InvalidParameter` errors and widespread blank screens caused by the frontend mistakenly passing an excessively large value.

   * **Extract fields on demand**: The underlying recommendation engine might contain hundreds of content feature fields. The backend should use `output_fields` to extract only the fields required for frontend rendering (such as `title`, `cover_url`, and `author_name`) to significantly reduce external network bandwidth consumption and parsing latency.

*  **🔄 Avoid content fatigue and repeat exposure **  **`(session_i`d control)** : For highly popular pinned content, the user experience is severely impacted if they see the same item after repeatedly refreshing the page. The backend should generate, maintain, and pass a unified `session_id` to the AI API. The platform will then automatically detect and skip previously exposed pinned content within the same session for 24 hours (see the `ForcedItems` activation logic).

*  **⚖️ Compliant responses and business rule fallbacks**:

   * **Privacy compliance**: When a user selects "Turn off personalized recommendations" in the app's privacy settings, the business backend can directly send `disable_personalize: true` in the request. The engine will then automatically downgrade to non\-personalized item retrieval of popular content, ensuring platform compliance.

   * **Content safety filtering**: The backend can use a `filter` to enforce recommendations for only content with an "approved" review status AND "public" visibility. This keeps the final line of defense for underlying data security on the backend.

*  **📍 Dynamic injection of scenario context **  **`(contex`t)** : For social circles with "same city" or "nearby" attributes, the business backend can securely parse the user's IP or base station location, convert it to `context.locatio`n, and pass it to the engine. This enables an automatic boost for local creators and content.

### 4. Recommendation results are not personalized enough.

When the recommended content does not meet this expectation, there might be an issue with the data configuration.

To achieve a strong personalized recommendation effect, check the following data in sequence for any issues:


1. User event data

   * Sufficiently large item count

   * Includes exposure and positive behaviors (such as Click, Purchase, play, etc.)

   * Item IDs in the user event dataset must be found in the item data.

2. Item data


Check if the "interest dimension" field automatically selected by Viking AI is suitable. A good field must satisfy the following three criteria:


   * **Business relevance:**  Must genuinely represent the user interests the business wants to capture (typically "Product category" or "News tags").

   * **High coverage:**  The vast majority of items must have a value for this field. It cannot be left blank on a large scale.

   * **Good differentiation:**  The distribution of the field's **enum values** must be even.

      * *Not too concentrated:*  Avoid having most items share the same tag (loses differentiation value).

      * *Not too sparse:*  Avoid having too many enum values, which results in each value applying to only a few items.

3. Document search field configuration: Check "core information" purity

* **Select only core fields:**  When configuring fields for **document search**, select only fields that contain key information (such as title and category).

* **Eliminate redundancy:**  Do not select non\-core information. Including too many irrelevant or messy fields dilutes the core information and causes the system to retrieve many irrelevant items.
