To effectively manage access for both human users and automated agents, it is essential to understand the platform's core concepts. This document provides a comprehensive glossary of terms related to user identity, agent (workload) identity, third\-party credential hosting, and permission control, helping you build a foundational knowledge of the system's architecture.

<span id="wyMYqPF4"></span>
## **General terms**


|Term (full name) |Definition |Role |
|---|---|---|
|TRN (Resource Name) |A globally unique resource identifier used to uniquely identify various resources (such as services, data, configurations, and more) within the system. |Supports cross\-service resource management and locating resources, serving as the foundation for authorization policy configuration, log audit tracking, and resource access control. |
|MFA (Multi\-Factor Authentication) |A security authentication mechanism that, in addition to a password known to the user, requires additional verification factors (such as SMS verification codes, hardware tokens, biometric features, and more) to confirm identity and enhance account security. |Effectively reduces the risk of account theft caused by the leakage of a single password and is widely used in scenarios with high security requirements (such as financial transactions and enterprise intranet logins, where it is typically enforced). |
|JWT (JSON Web Token) |A compact and URL\-safe lightweight token that securely transmits claim information (such as user identity, permission scope, token validity period, and more) in JSON format between web applications. |Supports stateless authentication and authorization, reduces server\-side storage pressure, and is commonly used for identity verification (such as OIDC ID Token) and resource access authorization (such as OAuth 2.0 Access Token) in distributed systems. |

## **User identity management**


|Term (full name) |Definition |Role |Example |
|---|---|---|---|
|User pool |A logical isolation unit for user identity management, containing user account information, authentication policy configuration (such as password rules and MFA), client registration data, and relationships with external identity providers (IdP). |Supports multi\-tenant user data isolation (for example, user pool management by different business lines), unified authentication processes and security policies, and simplifies user lifecycle management. |* E\-commerce user pool (ecommerce\-userpool, stores consumer accounts)<br><br>* Enterprise management pool (admin\-userpool, stores internal administrator accounts). |
|User |A user is a natural person or system account with a unique identity identifier (such as a user ID) that serves as the subject of authentication and authorization, and includes basic attributes (email, phone number, nickname, and so on) and security credentials (password hash, MFA key). |By entering credentials (such as a password plus a verification code), the user participates in the authentication process to generate an identity credential (such as a JWT token) that serves as the principal for resource access permissions. |User alice<br><br><br>* User ID: usr_12345<br><br>* Email: alice@example.com<br><br>* Phone number: +86138\*\*\*\*1234) |
|Client |An application entity registered with the user pool, including application type (such as web application, mobile app), authorization configuration (callback URL, authorization type), and other information, used to initiate user authorization requests and obtain tokens. |It is used to distinguish the access scope and token type (ID Token/Access Token) for different applications, and controls token issuance rules (for example, web applications allow refresh tokens, while mobile apps only support short\-term access tokens). |Client web\-client\-01<br><br><br>* Type: Web application<br><br>* Callback URL: https://app.example.com/callback |
|External identity provider (IdP, Identity Provider) |A third\-party service that provides user authentication capabilities (such as WeCom, Google, Azure AD), establishing federated login relationships with the user pool via OIDC/OAuth 2.0 protocols. |Enables cross\-platform identity federation, allowing users to log in with an existing IdP account without registering a separate account (for example, employees log in to the system by scanning a QR code with WeCom), simplifying the login process and enhancing user experience. |Configure `WeCom` as IdP<br><br><br>* Protocol: OIDC<br><br>* User attribute mapping: WeCom `userid` → user pool `username`; employees complete user pool authentication by scanning a QR code with WeCom. |
|OIDC (OpenID Connect) |An identity authentication protocol built on OAuth 2.0, defining the format of identity tokens (ID Token) and user information interfaces (UserInfo Endpoint), supporting secure transmission of user identity claims (such as unique identifier sub, email, picture). |Standardizes third\-party login processes, avoids redundant development of authentication logic, and ensures secure transmission and verification of identity information across applications (such as unified identity authentication in distributed systems). |An application obtains an ID Token via the OIDC authorization code flow, parses the user's sub (unique identifier: usr_12345) and email (alice@example.com), and recognizes the user's identity. |
|OAuth 2.0 (Open Authorization 2.0) |An authorization framework based on a token mechanism that allows third\-party applications to obtain limited access to specific resources under user authorization (without sharing user passwords), and supports multiple authorization flows (authorization code flow, client credentials flow, password flow, and more). |Controls the scope of resource access (such as read\-only or read/write permissions), protects the security of user resources (for example, only allowing applications to access "file read" permissions rather than all account permissions), and is suitable for API authorization and third\-party application integration scenarios. |Obtain Google Drive authorization through the OAuth 2.0 client credentials flow, enabling read\-only access to user cloud data. |

## **Agent identity management**


|Term |Definition |Purpose |Example |
|---|---|---|---|
|Workload pool (Workload Pool) |A logical grouping unit for managing workload identities, used to isolate collections of Agent or automation tool identities by environment (such as production or testing), business line, or team, and supports unified configuration and permission control. |It provides isolation for workload identities to avoid permission confusion across environments or teams (for example, managing production and testing environment Agents in separate pools to reduce the risk of operational errors), and simplifies permission policy configuration for multiple identities. |* `default` pool (default group, stores temporary workload identities that are not explicitly classified)<br><br>* `ai-agent-pool` (dedicated for the AI team, stores identities such as model training Agents and data processing tools). |
|Workload identity |The unique digital identity identifier for Agents or automation tools, using a standardized resource name format: `trn:id:{RegionCode}:{AccountId}:workload/{PoolName}/{Name}`, used to uniquely identify non\-user principals (such as tools or services). |Serves as the identity credential for non\-user principals (such as AI Agents, CI/CD tools, or monitoring scripts), participates in permission verification and audit tracking for resource access, and supports authorization for automated operations in unattended scenarios. |`trn:id:cn-beijing:123456:workload/default/test-agent` (identity of an automated testing tool in the testing environment) |
|Attribute tag (Attribute Tag) |Key\-value pair metadata associated with a workload identity (such as department:ai\-lab or env:production), used to identify the attributes of the identity (environment, department, function type, and so on). |It is used as a dynamic condition for access control policies to implement fine\-grained attribute\-based access control (ABAC). For example, restrict access to GPU resources to Agents with env:production and department:ai\-lab tags only, enhancing the flexibility and security of permission management. |Add the tags `env:production` and `task:model-training` to the Workload identity `trn:id:cn-beijing:123456:workload/ai-agent-pool/train-agent`, and configure the access control policy to allow only Agents with `env:production` and `task:model-training` tags to call the training cluster API. |

## **Third\-party credential hosting**


|Term |Definition |Purpose |Example |
|---|---|---|---|
|OAuth client credential |OAuth 2.0 client authentication credentials for third\-party services (such as Google and GitHub), including the client ID and client secret, used to identify the application and initiate authorization requests. These credentials should typically be stored in encrypted form. |To securely manage sensitive OAuth client credentials to avoid hardcoding or exposing them in plaintext (for example, when an Agent calls the Google API, the credential management module automatically injects the client ID and secret, eliminating the need for manual configuration), reducing the risk of credential leakage. |Store Google OAuth client credentials: `client-id=12345.apps.googleusercontent.com`, `client-secret=GOCSPX-xxxx` (encrypted storage via Key Management Service (KMS); only authorized processes can decrypt and access). |
|API key credential |Access keys for third\-party services (such as Alibaba Cloud and weather APIs) are unique strings that identify the caller. These must be stored in encrypted form (not plaintext) and are used for simple authentication between the server and client. |To simplify the authentication process for Agents calling external services (for example, Agents do not need to manually configure keys; they can directly obtain the encrypted API key from the credential management module, which is automatically populated in the request header), avoiding the risk of credential leakage due to manual key management. |Store Alibaba Cloud OSS API key credential: `key=AKIAEXAMPLE123456` (encrypted using AES\-256 in the credential management module; when calling the OSS API, the key is automatically decrypted and injected into the `Authorization: AccessKey AKIAEXAMPLE123456` request header). |
|Credential rotation |A mechanism for periodically or event\-driven updating of stored credential values (such as API keys and OAuth client secrets), supporting automatic (scheduled) or manual (for example, when a leak is detected) rotation. Old credentials become invalid after a transition period. |To reduce the risk of credential leakage caused by long\-term use of static credentials, meet security compliance requirements (such as PCI DSS requiring key rotation within 90 days and SOC 2 audits requiring regular credential updates), and prevent long\-term abuse after credential leakage. |OAuth Client Secret automatic rotation policy configuration: A new Secret is generated every 30 days, and the old Secret is retained for a 24\-hour transition period (allowing existing requests to complete). After the transition period, the old Secret automatically expires and is deleted. |

## **Permission control**


|Term |Definition |Purpose |Example |
|---|---|---|---|
|Cedar language |A declarative permissions policy language used to define the permissions of principals for operations on resources. It supports conditional logic (such as attribute matching and relationship evaluation) and the principle of least privilege. The syntax is concise and verifiable. |To write fine\-grained, auditable permission policies that support complex conditional authorization (for example, "only allow users from department A to edit documents they created themselves"), prevent excessive permission grants, and improve the security and maintainability of the authorization system. |Policy example:<br><br>`permit (principal == User::"alice", action == Action::"edit", resource: Document) where resource.owner == principal.name;`<br><br>(Allows user Alice to edit documents they themselves own) |
|Permission policy (Policy) |A set of rules written in the Cedar language that defines "who (principal) can perform what operation (Action) on what (resource)", including ALLOW/DENY rules and conditional judgments (such as principal attributes, resource attributes, and environment variables). It is the core basis for authorization decisions. |Serves as input to the permissions engine, controlling ALLOW/DENY decisions for resource access. Supports attribute\-based access control (ABAC), role\-based access control (RBAC), and other models, enabling centralized management and dynamic adjustment of permissions. |Policy combination example:<br><br>1. `allow (principal in Group::"editors", action == Action::"edit", resource: Document);`<br><br>2. `deny (principal, action == Action::"delete", resource: Document) where resource.category == "confidential";`<br><br>(Allows users in the editors group to edit documents, but prohibits deletion of confidential documents) |
|Authorization decision (Decision) |The result (ALLOW/DENY) of the permissions engine (such as Cedar Policy Engine) when evaluating an access request, including the list of matched policies, the reason for the decision (such as "matched ALLOW policy X" or "triggered DENY policy Y"), and contextual information (such as request time and IP address). |Serves as the final basis for resource access decisions, determining whether the principal is allowed to perform the operation (such as an agent invoking a tool or a user accessing an API), and supports audit tracking (recording the decision process for compliance checks). |Request example: Principal `Workload::"test-agent"` invokes operation `Action::"invoke"` to access resource `Tool::"payment"`.<br><br>Decision result: DENY<br><br>Decision reason: No matching ALLOW policy, and DENY policy triggered (`deny (principal == Workload::"test-agent", action == Action::"invoke", resource: Tool::"payment");`). |
|Principal |In a permission policy, the request initiator can be a user (User), a Workload identity, a user group (Group), or a service role (Role), using a standardized identifier format: `{type}::{unique identifier}` (for example, `User::"alice"`, `Workload::"ai-agent-01"`). |Defines "who" has permission to perform operations, supporting permission assignment at the individual, group (for example, `Group::"data-scientists"`), or role (for example, `Role::"admin"`) level, enabling bulk management and inheritance of permissions. |Principal matching examples:<br><br><br>* Individual: `principal == User::"bob"` (user Bob)<br><br>* Group: `principal in Group::"ai-team"` (all users in the AI team)<br><br>* Workload identity: `principal == Workload::"train-agent"` (training agent) |
|Resource (Resource) |The target object of operations in a permission policy can be a specific entity (such as a document, tool, or API endpoint) or an abstract resource (such as a user pool or Workload pool), using a standardized identifier format: `{type}::{unique identifier}` (for example, `Document::"doc-123"`, `Tool::"*"`), supporting wildcards (`*`) and hierarchical identifiers (for example, `Folder::"project-x/doc-123"`). |Defines "which" resources operations are performed on, supporting resource attributes (such as `owner`, `env`, `category`) for conditional evaluation (for example, "allow access only to production environment resources"), enabling resource\-level permission isolation. |Resource matching examples:<br><br><br>* Specific resource: `resource == Document::"doc-123"` (document 123)<br><br>* Wildcard: `resource in Tool::"*"` (all tools)<br><br>* Attribute condition: `resource.env == "production"` (production environment resource) |
