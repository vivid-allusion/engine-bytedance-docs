<span id="problem-description"></span>
## Problem description

When there are too many inactive logical replication slots due to not being cleaned up in time, WAL logs will continue to accumulate, occupying a large amount of storage space, and may even fill up the disk, causing the instance to be locked and unable to write data, thus affecting the business. Therefore, the production database must clean up the inactive logical replication slots in time.

<span id="troubleshooting-ideas"></span>
## Troubleshooting ideas

You can use the following ideas to troubleshoot and handle the inactive logical replication slots in the database:


1. Check whether there are invalid logical replication slots.

2. The business confirms whether the logical replication slot needs to continue to be used.

3. Delete the invalid logical replication slot.


<span id="solution"></span>
## Solution


1. Confirm whether there are inactive logical replication slots in the instance. You can judge in the following two ways:

   * View the replication slot list in RDS for PostgreSQL console to confirm whether there are inactive logical replication slots. For detailed information about viewing the replication slot list, see [View replication slot list](https://docs.byteplus.com/en/docs/RDS_for_PG/view_replication_slot_list).

   * Call Open API [DescribeSlots](https://docs.byteplus.com/en/docs/RDS_for_PG/describeslots) to query the replication slots under the instance. If the SlotStatus field returns the value of `INACTIVE` and the SlotType returns the value of `logical`, it means that there are inactive logical replication slots under the instance. The SlotName field is the name of the replication slot.

2. Contact the business party to check whether to continue to use the logical replication slot.

   * If it is no longer used, execute step 3 to delete the replication slot.

   * If you need to continue to use it and use the subscription feature of PostgreSQL, you can follow the following directions to troubleshoot:

      When creating a subscription on the subscription side, the replication of the logical replication slot is not enabled, and it is manually set to the disable state. Execute the following SQL on the subscription side to view the field return of the subenabled column.

      ```sql
      select subname,subenabled from pg_subscription;
      ```
      

      * If the field return of the subenabled column is `f`, it means that the subscription does not enable logical replication. Execute the following SQL to enable logical replication for the subscription.

      ```sql
      ALTER SUBSCRIPTION sub_name ENABLE;
      ```
      

      * If the subenabled column returns `t`, continue to troubleshoot according to the following steps.

   * The logical replication slot used when executing tasks using other tools is not automatically cleaned up due to task interruption or certain operations on the source or target database, such as backup, rebuilding indexes, and other unexpected situations.

   * Query the returned "Slot Name" field through RDS for PostgreSQL console on the publishing end to observe whether the value of the "Slot Name" field starts with `_volc_dts_logical_replica_`. If so, it means that the logical replication slot is generated by executing the DTS task. At this time, you can determine whether to perform step 3 to clean up the replication slot based on the task situation.

3. Delete the invalid logical replication slot. You can delete the replication slot in the following two ways:

   * Delete the replication slot in the replication slot list of RDS for PostgreSQL console. For detailed information about deleting replication slots, see [Delete replication slot](https://docs.byteplus.com/en/docs/RDS_for_PG/delete_replication_slot).

   * Call the Open API [DeleteSlot](https://docs.byteplus.com/en/docs/RDS_for_PG/deleteslot) to delete the replication slot under the instance. Specify the ID of the instance to which the replication slot belongs in the request parameter InstanceId, and specify the name of the replication slot to be deleted in the request parameter SlotName.


<span id="suggestions-for-reducing-the-impact-on-business"></span>
## Suggestions for reducing the impact on business


* In business, promptly clean up replication slots that are no longer needed.

* RDS for PostgreSQL provides two monitoring items for replication slots: **Number of inactive replication slots** and **Maximum WAL stacking volume of replication tank**. Creating alarm policies for the two monitoring items can promptly detect the occurrence of inactive replication slots and the storage space occupied by replication slots. For more information about creating alarm policies, see [Creating an alarm strategy](https://docs.byteplus.com/en/docs/cloudmonitor/Creating-an-alarm-strategy).
