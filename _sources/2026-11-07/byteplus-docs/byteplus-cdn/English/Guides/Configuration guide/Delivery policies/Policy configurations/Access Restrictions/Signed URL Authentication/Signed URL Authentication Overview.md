# URL Authentication Overview

URL authentication protects CDN content and reduces the risk of unauthorized use by validating the signature and validity period in each request.

<span id="prerequisites"></span>
## Prerequisites

Before using URL authentication, confirm that:


* You have identified the CDN resources that require protection and do not need to be directly accessible to any user.

* Your client or signing server can generate signatures using the same Key, algorithm, timestamp, and signing rules as the CDN configuration.

* You have defined the request scope to which URL authentication applies. Requests outside the scope are not authenticated. For a request within the scope that does not include a valid signature, CDN returns 403.


<span id="how-it-works"></span>
## How it works


1. The client or signing server generates a timestamp and signature that meet the CDN configuration requirements and adds them to the request.

2. When CDN receives the request, it first determines whether the request matches the applicable scope. CDN does not authenticate requests that do not match.

3. For a matching request, CDN recalculates the signature using the primary Key and the same rules, then checks its validity period. If primary\-Key validation fails and a Backup Key is configured, CDN validates the request again using the Backup Key.

4. If the signature is valid and the request has not expired, CDN continues to process it. Otherwise, CDN returns 403.


<span id="console-configuration"></span>
## Console configuration

The URL authentication console has the **Targets** and **Auth Configuration** tabs.

The **Targets** tab includes, by default, a **Path Directory** rule for `/`. This rule represents all files and cannot be deleted. The editable scope differs by type:


|Type |What you can edit in the default rule |Can you add rules? |
|---|---|---|
|A, D, E |You can change the rule type and rule content. File extension, file directory, full file path, and full\-path regular expression are supported. |Yes. You can configure up to 10 rules in total. |
|B, C |You can change the rule to a file extension and specify extensions. If you retain Path Directory, the rule content is fixed as `/` and cannot be changed. |No. |


Use the **Auth Configuration** tab to configure Keys, signature fields, validity periods, algorithms, and type\-specific parameters.

<span id="choose-an-authentication-type"></span>
## Choose an authentication type

First select a type based on where the authentication information is placed and whether the signing input must be extended. Then refer to the documentation for that type to complete configuration and signature generation.


|Type |Authentication information location |Timestamp |Signing input |Recommended when |
|---|---|---|---|---|
|A |A single query parameter |Decimal Unix timestamp, in seconds |`uri-timestamp-rand-uid-key` |You need one query parameter to carry the timestamp, random string, and signature. |
|B |URL path, with the timestamp before the signature |`YYYYMMDDHHMM` (UTC+8), decimal Unix timestamp, or hexadecimal Unix timestamp |`key + timestamp + uri` |Signature information must be in the path and multiple time formats are required. |
|C |URL path, with the signature before the timestamp |Hexadecimal Unix timestamp, in seconds |`key + uri + timestamp` |Signature information must be in the path and a fixed hexadecimal timestamp can be used. |
|D |Separate signature and time query parameters |Decimal or hexadecimal Unix timestamp, in seconds |`key + uri + timestamp` |Separate query parameters are required and the signing order is fixed. |
|E |Separate signature and time query parameters |Decimal or hexadecimal Unix timestamp, in seconds |Concatenate parameters in the order configured in CDN |Request parameters, request headers, or client information must be included in the signature in addition to the path and timestamp. |
|F |Query parameters, path segments, request headers, or cookies |Independently configurable retrieval method; octal, decimal, and hexadecimal Unix timestamps are supported |Combine keys, fixed strings, URI segments, request parameters, request headers, cookies, and client information; multiple algorithms can be chained |You need to customize signature or timestamp retrieval, signing input, or an algorithm chain, or to rewrite HLS or DASH manifests. |


In the formulas, `+` means that parameter values are concatenated directly; it is not a literal character.

<span id="signed-url-code-examples"></span>
## Signed URL code examples

A signed URL in a client request can be generated by a trusted signing server or by the client. The following examples show how to generate signed URLs for Types A–E in PHP, Go, Python, and Java. The Key, algorithm, timestamp format, parameter names, signing fields, and concatenation order must match your CDN configuration.

For Type E, the examples support combining the Key, client domain, `uri`, timestamp, request parameters, request headers, and client information in the configured order. Custom request parameters included in signature calculation are appended to the URL. Request headers are used only for signature calculation and must be included with the same values in the actual request.

## Cache key and origin requests

The following table describes the default cache\-key and origin\-request behavior for each type, and how to adjust it.


|Type |Default cache key |How to adjust the cache key |Default origin request |How to adjust the origin request |
|---|---|---|---|---|
|A, D |Excludes the signature and timestamp |Use the cache\-key feature to specify whether to include the signature and timestamp; they usually do not need to be retained. |Excludes the signature and timestamp |Cannot be changed. |
|B, C |Excludes the signature and timestamp |Cannot be changed. |Excludes the signature and timestamp |Cannot be changed. |
|E |Includes the signature and timestamp |In URL authentication configuration, use **Exclude Auth Params from Cache & Origin**. |Includes the signature and timestamp |In URL authentication configuration, use **Exclude Auth Params from Cache & Origin**. |
|F |Excludes the signature and timestamp |Adjust it in the cache\-key feature. |Excludes the signature and timestamp |Adjust it in URL authentication configuration. |


<span id="common-behavior"></span>
## Common behavior


* When comparing signatures, CDN converts both its calculated result and the signature in the request to lowercase.

* When authentication fails, you can determine that the request was rejected from HTTP 403. The error response body may change with service versions, so your application logic must not depend on its content.


<span id="usage-notes"></span>
## Usage notes


* A Key is used only to calculate signatures and must not be included in the request URL. Provide it only to trusted clients or signing servers. Clients or signing servers use the Key to generate signatures; CDN uses the configured primary Key or Backup Key to calculate and compare signatures by the same rules.

* The applicable scope determines whether authentication is performed. A scope that is too narrow can leave resources unprotected, while one that is too broad can cause requests that do not otherwise need a signature to return 403.

* The client or signing server must use exactly the same type, Key, algorithm, time format, parameter names, and concatenation order as the CDN configuration. For type E, the values of request parameters, request headers, and client information included in the calculation must also match.

* If your origin also needs to validate signatures, review the cache\-key and origin\-request behavior of the selected type to confirm whether the origin receives signature parameters.
