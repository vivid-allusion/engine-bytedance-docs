Torch Log Service (TLS) supports the scheduled SQL feature. This feature can query and analyze log data according to a preset time window and a scheduling cycle. The feature saves the query and analysis results to specified topics for scenarios such as data analysis, log aggregation, and information filtering. This topic describes the scheduled SQL feature and related limits.

<span id="背景信息"></span>
## Background

In scenarios where business log data is highly accurate and log content is complex: 1. long\-term storage of a large amount of log data brings high costs. 2. Real\-time query on massive data causes performance stress. TLS supports the scheduled SQL feature. This feature can perform scheduled query and analysis on log data within a specified range and save the results to specified topics. Scheduled SQL supports all query and analysis syntax of TLS. This feature can run analysis tasks according to preset time windows and scheduling cycles.

After you use scheduled SQL, you can set a short log storage period for a source topic that stores massive log data. The log data can expire and be deleted after you use scheduled SQL on the data. This reduces the storage costs of logs and indexes. You can set a long storage period for your target topic used to save the results generated by scheduled SQL. For example, you can set that the results are permanently saved.

In addition, TLS offers the service logs of scheduled SQL. You can view running information on scheduled SQL tasks through service logs. For more information, refer to [Service log fields](https://docs.byteplus.com/docs/tls/service_log_fields).

<span id="功能特性"></span>
## Feature

The scheduled SQL feature offers the following capabilities:


* Scheduled query and analysis on logs: According to a specified time window and a scheduling cycle, this feature executes the query and analysis statements of TLS in a scheduled manner. In addition, the feature saves the analysis results to a specified target topic. Scheduled query and analysis can be used in multiple periodic data collection scenarios, such as scheduled log data aggregation, key result extraction, and data report generation.

* Log aggregation: This feature aggregates information based on detailed original log content. This way, it can summarize massive log data into data with appropriate accuracy and reduce storage costs. The log aggregation capability is suitable for scenarios in which you want to perform storage cost control. For example, you can use this capability to aggregate logs based on a time window, which reduces log accuracy to save storage space.

* Log filtering: This feature filters log content according to specified rules, reserves only the important log fields that need attention, and saves the fields to specified topics. Log filtering is suitable for scenarios in you want to perform data cleansing. For example, you can use this capability to filter logs that contain fault information in operations and maintenance (O&M) scenarios.


<span id="注意事项"></span>
## Precautions


* Scheduled SQL tasks offered by TLS are currently in public preview and free of charge. You are charged by the standard billable items of TLS used during scheduled SQL tasks. For example, target topics used to store processed log data charge you for log storage.

* After a scheduled SQL task is created, TLS automatically adds the following reserved fields to each data entry each time it writes data. These fields are used to record the metadata information corresponding to the task. For more information on terms such as scheduling time, refer to [Terms](https://docs.byteplus.com/docs/tls/how_scheduled_sql_works#terms).

   
   |Field |Description |
   |---|---|
   |`__task_id__` |The ID of a scheduled SQL task. |
   |`__process_id__` |The ID of the instance in a scheduled SQL task for executing SQL analysis. |
   |`__process_start_time__` |The start time of a SQL time window for a scheduled SQL task. |
   |`__process_end_time__` |The end time of a SQL time window for a scheduled SQL task. |
   |`__process_time__` |The scheduling time of an instance. By default, the back\-end service starts generating a running instance at this time. |
   |`__schedule_time__` |The actual execution time of an instance. The instance of a scheduled SQL task actually starts execution at this time. |
   


<span id="使用限制"></span>
## Limits


|Category |Limited Item |Description |
|---|---|---|
|Resource management |Number of scheduled SQL tasks |* Up to 100 scheduled SQL tasks can be created in a project.<br><br>* Up to 15 scheduled SQL tasks can be created in a source topic. |
||Deletion of scheduled SQL tasks |The Trace feature of TLS is available when the scheduled SQL tasks run as expected. To ensure the availability of the Trace service, do not manually perform change operations on the scheduled SQL tasks corresponding to the Trace service. For example, do not modify the corresponding configuration or delete the scheduled tasks. To modify the configuration of the Trace service or deactivate the service, perform the operation on the pages of the Trace service. |
||Historical records for task execution |Historical records for task execution can be saved for up to seven days. We recommend that you create an alarm monitoring task for the service logs generated due to scheduled SQL tasks. This way, you can find issues and retry instances that report errors in a timely manner. |
||Task scheduling concurrency |A single account supports 10 concurrent operations. |
|Data write |Data latency |If data latency exists, the corresponding data may not be written to TLS during data query. If data at a point in time arrives after the corresponding scheduling instance completes execution, the next scheduling instance does not execute analysis on the data. |
||Instance concurrency |Up to 10 scheduling instances can run simultaneously in 1 project, and up to 1 scheduling instance in 1 task can be in the status that indicates the instance is scheduling. |
||Retry after write failures |After a data write operation fails, the system retries the operation 3 times with an interval of 60 seconds each time. If the operation still fails after the system retries it 3 consecutive times, the instance changes to the status that indicates failed execution. We recommend that you create an alarm monitoring task for the service logs generated due to scheduled SQL tasks. This way, you can find issues and retry instances that report errors in a timely manner. |
