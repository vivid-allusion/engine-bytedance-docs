Torch Log Service applies the following limits on using LogCollector.

<div data-tips="true" data-tips-type="tip">The limits described in this document are based on the latest official version of LogCollector. For the steps to view LogCollector version, refer to <a href="https://docs.byteplus.com/docs/tls/install_logCollector_on_a_host#.5p-l55yL6L2v5Lu254mI5pys">View software version</a>. ## Operating environment


|Limited Item |Description |
|---|---|
|Architecture |* LogCollector supports Linux x86_64 and ARM architectures<br><br>* LogCollector cannot be installed on Windows systems. |
|Operating system |Linux Kernel v 2.6.32 and later. |
|Kubernetes |* When collecting logs in the DaemonSet way, Kubernetes 1.10.0 or a later version should be used, that is, the version that supports Mount propagation: HostToContainer.<br><br>* When collecting container logs in the CRD (Custom Resource Definition) way, Kubernetes 1.16.0 and a later version should be used.<br><br>* The apiextensions.k8s.io/v1beta1 API provided by Kubernetes 1.7.0 and above versions also support the CRD capability. However, the stability of the beta version of the API depends on the specific Kubernetes version, and its stability remains unknown. |

## File collection


|Limited Item |Description |
|---|---|
|Log length |A single log entry can be up to 512 KiB.<br><br><br>* LogCollector 2.1.0 and subsequent versions: Support adjusting the maximum length of a single log through the startup parameter `log_max_bytes`, with the maximum not exceeding 8MiB.<br><br>* LogCollector 1.0.48 and subsequent versions: If a single log entry exceeds 512 KiB, the log entry will be split into multiple logs for collection. For example, if the size of a single log entry is 1048 KiB, it will be split into three logs. The first log entry is 512 KiB, the second log entry is 512 KiB, and the third log entry is 24 KiB.<br><br>* LogCollector versions before 1.0.48: LogCollector truncates log entries exceeding 512 KiB and discards the excess parts. If a log entry is more than 2 MiB, LogCollector discards it. |
|The log does not end with a newline character |When the LogCollector reads a log that does not end with a newline character, by default, the LogCollector will wait for 5 seconds and then upload this log. |
|Log file size |Unlimited. |
|Log file encoding |Support log files encoded in UTF\-8. |
|Log aggregation upload |LogCollector automatically aggregates log entries from the same file before uploading. Compared with the method of uploading logs one by one, aggregating logs can significantly reduce the number of network requests and improve the throughput of log uploads.<br><br>Aggregation conditions are more than 1024 logs, the total log size exceeds 512KiB, or the log aggregation time exceeds 3 seconds. Aggregation is triggered if either condition is met. |
|log file rotation |LogCollector supports log collection in the log file rotation scenario.<br><br><br>* (Recommended) rename log file rotation: When the log file reaches a certain size or time limit, rename the current log file to a new file name, such as adding a timestamp or serial number, and then create a new log file and write the new log. For example, the original log file is `bar.log`, after rotation will generate `bar.log.1`, `bar.log.2`and other log files.<br><br>   LogCollector automatically recognizes the log files before and after the rotation to ensure the integrity of the log.<br><br>   If the log file rotation is too frequent, resulting in the creation of a large number of log files in a short period of time, then LogCollector only collects 20 log files at the same time, and more than 20 log files cannot be collected, which may cause some log files to be deleted without being collected, resulting in log loss.<br><br>* Copytruncate log file rotation: When the log file reaches a certain size or time limit, copy the current log file to a new log file, for example by adding a timestamp or serial number, then empty the original log file and write the new log. For example, the original log file is `bar.log`, after rotation will generate `bar.log.1`, `bar.log.2`and other log files.<br><br>   Assuming that the configured collection path is `bar.log`, when there is a collection delay in the LogCollector, the copytruncate log file rotation will cause the delayed collection log to be lost.<br><br>   Assuming the configured collection path is `bar.log *`, the copytruncate log file rotation will cause duplicate collection of logs that have already been collected. |
|The location where the log file was first collected |LogCollector supports collecting both historical log files and new log files. LogCollector will regularly scan the log files that match the collection path, including historical log files and new log files, and then collect them concurrently. Meanwhile, LogCollector will monitor the writing events of new log files through inotify and then conduct concurrent collection as well.<br><br><br>* Historical log file: LogCollector will continue collecting from the position where the last collection ended.<br><br>* New log file: If the size of a new log file is less than or equal to the amount of incremental collection backtracking, then LogCollector will start the first collection from the starting position of the new log file. If the size of the new log file is greater than the amount of incremental collection backtracking, then LogCollector will start the first collection from the position obtained by subtracting the amount of incremental collection backtracking from the end position of the new log file. |
|Ignore historical log files |LogCollector ignores log files that have not been updated for 30 days by default. |
|Log file Identification |LogCollector uses the inode, device, and the checksum of the first 1,024 bytes to uniquely identify log files.<br><br><div data-tips="true" data-tips-type="tip" data-tips-is-title="true">tip</div><br><br><br><br>* <div data-tips="true" data-tips-type="tip">When modifying a log file using vim, vim will rebuild the log file, causing the inode of the log file to change. As a result, LogCollector will treat it as a completely new log file and start collecting the logs in it from the beginning.</div><br><br><br>* <div data-tips="true" data-tips-type="tip">When a log file is truncated, the content of the first 1024 bytes of the log file will change, leading to a change in the checksum of the first 1024 bytes of the log file. Therefore, LogCollector will also treat it as a completely new log file and start collecting the logs in it from the beginning.</div><br> |
|Number of Collected Files |LogCollector can collect a maximum of 10,000 log files simultaneously. When the number of log files to be collected exceeds 10,000, the excess log files cannot be collected temporarily. |
|Wildcards for Collection Paths |LogCollector collection path supports wildcards asterisk `*`, double asterisk `**`, question mark `?`.<br><br><br>* `*` represents any number of characters (except the directory separator `/`).<br><br>* `?` represents any single character (except the directory separator `/`).<br><br>* `**` represents any number of characters (including the directory separator `/`).<br><br>   * In the collection paths of LogCollector, only one double asterisk `**` wildcard can be configured at most one.<br><br>   * When the wildcard `**` is specified in the log collection path, it means matching multiple layers of directories. Only in this case will TLS listen to the subdirectories up to 8 levels deep under the specified directory. For example, the collection path is `/var/**/a.log`, LogCollector default to parsing it as `/var/a.log`, `/var/*/a.log`, `/var/*/*/a.log`, `/var /*/*/*/ a.log`, `/var /*/*/*/*/ a.log`, `/var /*/*/*/*/*/ a.log`, `/var /*/*/*/*/*/*/ a.log`, `/var /*/*/*/*/*/*/*/ a.log`, `/var/*/ */*/*/*/*/*/*/ a.log`. |
|Scanning cycle of Log Files |LogCollector scans every 10 seconds to discover log files that match the collection paths. |
|Number of Scanned Log Files |LogCollector can scan a maximum of 100,000 log files in a single scan. If the number of log files that match the collection paths exceeds 100,000, then only 100,000 log files will be scanned and the other log files cannot be scanned. |
|Number of inotify Instances |LogCollector can hold a maximum of 16 inotify instances.<br><br>One collection pipeline exclusively occupies one inotify instance. If the number of collection pipelines exceeds 16, then only 16 collection pipelines can successfully obtain inotify instances and use regular scanning and inotify real\-time monitoring to discover the log files to be collected. Other collection pipelines cannot obtain inotify instances and can only use regular scanning to discover the log files to be collected.<br><br><div data-tips="true" data-tips-type="tip" data-tips-is-title="true">tip</div><br><br><br><br>* <div data-tips="true" data-tips-type="tip">In the physical machine scenario, one collection pipeline represents one collection rule.</div><br><br><br>* <div data-tips="true" data-tips-type="tip">In the container scenario, one collection pipeline represents one collection rule and its corresponding one container.</div><br> |
|Number of log directories monitored by Inotify |The maximum number of log directories that a single inotify instance can monitor: <br><br><br>* LogCollector 2.3.x and later version: 1000 <br><br>* Versions before LogCollector 2.3.x: 200 <br><br><br>A single inotify instance can monitor up to 200 log directories. An inotify instance only monitors log directories, not log files. If the log that needs to be monitored has more than 200 directories, only 200 log directories will be monitored; the rest will not be monitored.<br><br><br>* When the number of directory entry caches (dentry caches) under the monitored directory reaches tens of millions, using inotify to monitor the directory may cause CPU performance lags that last several milliseconds. <br><br>* You can configure the startup parameter input.log.enable_inotify to disable the inotify mechanism. Once disabled, only periodic scanning can detect log files that need to be collected. In this case, logs that failed to be collected may exist. |
|Handle release strategy for log files |When the time that LogCollector continuously reads the end\-of\-file (EOF) marker of a log file exceeds 60 seconds, LogCollector will close the handle of the log file. LogCollector also supports other handle release strategies for log files, including:<br><br><br>* Closing the file handle when the log file is deleted.<br><br>* Closing the file handle when the log file is renamed.<br><br>* Closing the file handle when LogCollector reads the EOF of the log file.<br><br>* Closing the file handle when the time that LogCollector reads the log file exceeds a certain number of seconds. |
|One log file matches multiple Collection configurations |When a log file matches multiple collection configurations, by default, this log file will be collected by the collection configuration that was created most recently. |
|Soft links |In the physical machine deployment environment, LogCollector supports collecting soft links.<br><br><br>* In the scenario where a single collection configuration simultaneously matches a soft link and the actual file it points to, LogCollector will only collect either the soft link or the actual file it points to, not both simultaneously. Therefore, the `__path__` metadata carried by the logs may be the path of the soft link or the path of the actual file it points to.<br><br>* If the log files are discovered through regular scanning, then LogCollector will choose to collect the log file with the smaller lexicographical order of the collection path. Therefore, the `__path__` metadata may be the path of the soft link or the path of the actual file it points to.<br><br>* If the log files are discovered through inotify, then LogCollector will only choose to collect the actual file pointed to by the soft link. Therefore, the `__path__` metadata will only be the path of the actual file it points to. |
|Regular expressions |Support Perl\-compatible regular expressions. |
|JSON |Standard JSON ( [RFC7159](https://tools.ietf.org/html/rfc7159), [ECMA-404 ](https://ecma-international.org/publications-and-standards/standards/ecma-404/)) is supported. |

## Container log collection

When collecting container logs through LogCollector, in addition to the above limitations on file collection, there are also the following limitations.


|Category |Limited Item |Description |
|---|---|---|
|General Limitations |Kubernetes Container lifecycle |By default, the container lifecycle should be at least 10 seconds or more for LogCollector to collect the logs. If there is a need to collect logs for containers with a shorter lifecycle, please contact technical support through the ticket system. |
||Kubernetes pod destruction event |When receiving a Kubernetes Pod destruction event, LogCollector will not immediately stop collecting the container logs within the Pod. Instead, it will continue to collect for an additional 15 seconds before releasing the file handles of the containers inside the Pod, which may prolong the destruction time of the Pod.<br><br>You can adjust the additional collection time through the startup parameter cleanup_timeout. |
||Container runtimes |LogCollector supports two container runtimes: Docker and Containerd.<br><br><br>* Docker: LogCollector accesses the Docker container runtime through `/run/docker.sock`. Please ensure that this path exists and has the appropriate access rights.<br><br>* Containerd: LogCollector accesses the Containerd container runtime through `/run/containerd/containerd.sock`. Please ensure that this path exists and has the appropriate access rights. |
|Log files inside the container |Mounting methods |Currently, the collection paths of log files inside the container only support three methods: "no mounting", "emptyDir mounting", and "hostPath mounting". |
||Soft links |Soft links are not supported for log files inside the container. |
||Job workloads |For Kubernetes Pods of the Job workload type, before destroying the Pod, Kubernetes will first clean up the resources of the containers inside the Pod (such as file handles under rootfs). Since LogCollector does not receive the Kubernetes Pod destruction event, LogCollector will not release the handles of the log files being collected, resulting in a prolonged destruction time of the Kubernetes Pod. It is recommended to use "emptyDir mounting" and "hostPath mounting" instead of "no mounting". |
|Container standard output |Standard Output Log Driver |If Docker is used as the container runtime, `"log-driver": "json-file"` must be added to the Docker configuration file `daemon.json`. |
||Standard output log rotation |The standard output file of the container's standard output has its log files rotated by docker or kubelet. Among them, the default size for kubelet log file rotation is 10MB. If the rate of the container's standard output per second is greater than 10MB/s, it will cause the standard output file to rotate quickly. It is recommended to switch to collecting via the log files inside the container or modify the `containerLogMaxSize` parameter of kubelet to avoid log loss. |

## Collection configuration


|Limited Item |Description |
|---|---|
|Delay for the Effectiveness of Collection Configuration Updates |The delay from updating the collection configuration through the API or the console to the effectiveness of the LogCollector client configuration is approximately 60 seconds. |
|Dynamic loading of collection configurations |LogCollector supports dynamic loading of collection configurations, and the update of one of the collection configurations does not affect the other configurations. |
|Number of configurations that can be loaded by a single LogCollector |Theoretically, there is no limit. It is recommended that the number of LogCollector collection configurations in a single server does not exceed 100. |
|Multi\-account Collection |Please contact technical support through the ticket system. |
|Multi\-region Collection |Please contact technical support through the ticket system. |
