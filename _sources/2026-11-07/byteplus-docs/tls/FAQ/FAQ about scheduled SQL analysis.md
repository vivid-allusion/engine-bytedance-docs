## What are the differences between the scheduled SQL feature and the data transformation feature?

The scheduled SQL feature is designed for data simplification scenarios, allowing you to query and analyze large volumes of log data at a time. The data transformation feature is suitable for scenarios such as data distribution and data cleansing. It offers more fine\-grained data processing capabilities, allowing you to analyze and process field\-level data of each log entry in source topics.

## How do I trace the data that a scheduled SQL task writes to the destination topic?

Use the following method to view the raw log data of a topic:


1. After you create a scheduled SQL task, TLS automatically adds reserved fields such as `__process_id__` or `__task_id__` for each data entry each time data is written. You can get the corresponding scheduled SQL task ID and instance ID based on the reserved fields.

2. In the list of scheduled SQL tasks, find the instance based on the task ID and instance ID. TLS retains the instance run data generated within 7 days.

3. View the SQL time window, query and analysis statements, and execution information corresponding to the written data. Based on such information, you can find the data range in the source topic. You can also query and analyze service logs to view the detailed run information of a specified instance for tracing and troubleshooting.

## Why hasn't the scheduled SQL task started scheduling for a long time?

The possible reasons why the scheduled SQL task hasn't started scheduling for a long time are as follows:


* The scheduling cycle isn't met: The scheduling instance of the scheduled SQL task will only be generated when the scheduling time point is reached.

* Scheduling delay: If the previous instance is delayed, the newly generated scheduling instance will wait in the scheduling queue.

* Too many scheduling instances: Too many concurrent scheduling instances lead to a backlog in the execution queue, and the scheduling instances haven't been executed for a long time.

* Index isn't built: The call has actually been completed, but the index hasn't been built for the result data, resulting in the execution results generated by scheduling not being displayed.

## Why is the instance of a scheduled SQL task not executed?

Before executing an instance, TLS verifies whether the instance meets the execution conditions. If the previous instance is not running because not all data within the query time range is written, but the next instance already meets the execution conditions, then the next instance runs first.

<div data-tips="true" data-tips-type="tip" data-tips-is-title="true">tip</div>


<div data-tips="true" data-tips-type="tip">After an instance meets the execution conditions, TLS schedules resources in the back end to get ready, which may take more than 1 minute.</div>


Generally, the following conditions must be met to execute an instance:


* The scheduled time is reached. If you do not set a delay for a task, the back\-end service executes the instance at the scheduled time. If you set a delay for a task, the back\-end service delays executing the instance for the specified period after the scheduled time is reached.

* All the log data within the SQL time window of the instance is already written. If a topic contains log data written after the end of the query time range, it means all the data within the query time range is already written. Assume that the query time range is [10:00\-11:00). If a log entry is written at 11:01, it means all the data within the query time range is already written and the instance can be executed.

* The maximum number of concurrent instances is not reached. Only one instance can be in the running status in a task.
