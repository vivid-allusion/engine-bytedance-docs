An API Key is a simple and widely used user authentication mechanism. The client adds a unique API key to the request header or request parameter. After the server or proxy obtains the API key, it checks whether the corresponding Consumer or Client identity exists. If so, the corresponding authentication can be completed. The API gateway uses the Key Auth plugin to implement authentication and authorization based on API Key. This document describes how to configure API Key authentication for an API gateway.

<span id=".5YmN5o-Q5p2h5Lu2"></span>
## Prerequisites


* An APIG instance has been created. For details, refer to [Create an instance](https://docs.byteplus.com/en/docs/apig/Creating_an_instance).

* The APIG instance has been upgraded to version 3.1.0 or later. For details, refer to [Version Management](https://docs.byteplus.com/en/docs/apig/Version_Management).

* The Service has been created. For details, refer to [Create Service](https://docs.byteplus.com/en/docs/apig/Creating_a_service#.5Yib5bu65pyN5Yqh).

* The consumer has been created, and the API Key information has been generated or uploaded. For details, refer to [Generate credential](https://docs.byteplus.com/en/docs/apig/Generating_credentials).


<span id=".5L2_55So6ZmQ5Yi2"></span>
## Limi


* The same plugin can only be bound once to the same resource.

* When the same plugin is bound to resources at different levels, only the resource with the highest effective priority takes effect. The priority order from highest to lowest is: route \> service.

   For example, Service I has two routes: route A and route B. When the plugin is configured on both Service I and route A, the effective rules for route A follow the plugin configuration of route A, while the effective rules for route B follow the plugin configuration of Service I.


<span id=".5pON5L2c5q2l6aqk"></span>
## Procedure


1. Log in to the [API Gateway console](https://console.byteplus.com/veapig).

2. In the left navigation bar, select **Plugin Management \> Key Auth**, click **Create Plugin**, and configure plugin parameter.

   
   |Configuration Item |Descriptions |
   |---|---|
   |Effective level |Select the effective level of the Key Auth plugin, including:<br><br><br>* **Service level**: Key Auth authentication takes effect within the Service and requires specifying the target instance and target Service for which it will be effective.<br><br>* **Routing level**: Key Auth takes effect at the route level. You need to specify the target instance, target Service, and target route. |
   |Notes/comments |Enter notes/comments about the current Key Auth plugin; this field can be left empty. |
   |Authentication configuration |Select the location where the Key Auth credential needs to be included.<br><br><br>* **header**: The Key Auth credential is included in the request header, with the default source being Authorization.<br><br>* **querystring**: Key Auth credentials are passed in the request parameters. When this option is selected, you need to specify the source of the credential in the request parameter. |
   |Hide credentials |Configure whether to hide credential from Upstream.<br><br><br>* Check **enable**: hides the credential from the backend Upstream.<br><br>* Do not check **enable**: This means that credentials are not hidden from the backend Upstream. The relevant key will be transparently passed to the backend. |
   |Allow anonymous access |Configure whether anonymous access is allowed, that is, whether to permit requests that do not contain Key Auth credential.<br><br><br>* Check **enable**: This allows anonymous access, and the gateway will allow requests without Key Auth credentials.<br><br>* If **enable** is not checked: anonymous access is prohibited, and the gateway will block requests that do not contain Key Auth credentials. |
   |Ignore options |Configure whether to ignore Options.<br><br><br>* Check **enable**: indicates that Options will be ignored.<br><br>* If **enable** is not checked: means that Options are not ignored. |
   |Consumer |Specify the consumer for the plugin. The plugin will use the API Key generated by the consumer for authentication and authorization.<br><br>When **All** is selected, the plugin will apply to both existing consumers and any consumers created in the future. After a user generates a new credential, it will be automatically added to the authentication and authorization scope of the plugin. |
   

3. Click **Add** to complete the configuration.

## Result validation

<span id="1GcktZ5b"></span>
### View configuration

After completing the configuration, in the plugin list, select the **Service level** or **Route level** tab to view the configured Key Auth plugin. If the plugin status is **enabled**, this indicates that the plugin has taken effect, and only requests carrying API Key credentials can successfully access the backend Upstream of the API gateway.

<span id="vPJGFZ4r"></span>
### Certification testing

After configuring the Key Auth plugin in the APIG instance and generating the API Key credential using the consumer, you can use the API Key credential to authenticate requests. Only access requests that carry only this credential can access the backend upstream through the API gateway.


1. Access the service using the domain name configured in the APIG instance when API Key credential information is not provided.


```Bash
curl -H "Host: apig-example.com" http://14.xxx.xxx.xxx
```


The expected result is as follows: it indicates authentication failure, and the backend Service cannot be accessed through the API gateway.

```Bash
Consumer authentication failed.
```



2. Access the service using the domain name configured in the APIG instance when API Key credentials are provided.


```Bash
curl -H "Host: apig-example.com" http://14.xxx.xxx.xxx -H "Authorization: Bearer e8cc8b4f-***"
```


The expected result is as follows: it means that the backend Service can be accessed through the API gateway.
