When calling message queue RocketMQ version of OpenAPI, the client side may retry multiple times if there are problems such as request timed out or server level internal errors. To ensure the idempotence of the request, you can set the ClientToken parameter when calling OpenAPI to avoid repeated resource creation due to multiple retries.

<span id="e19421b6"></span>
## How to ensure the requested idempotence

Request idempotence means that the same request is executed once and has the same effect as multiple consecutive executions, that is, idempotent methods do not have side effects other than statistical purposes.

When creating cloud resources through OpenAPI, the client side may retry repeatedly if problems such as request timed out or server level internal errors occur. If both the original request and subsequent retried requests execute successfully, a resource is created for each request, resulting in more resources actually created than expected. The message queue RocketMQ version supports OpenAPI request idempotent identifiers. The backend service will perform a series of judgment checks on the idempotent identifiers set by the client side in the request and identify whether the current request is a retry request, so as to proceed to the next step.

When the client side sends a request, it can add the optional parameter ClientToken to the request parameters as the idempotence identifier. If the client side retries when it encounters an error such as 500, the server level will determine whether the request is a retry request according to the idempotence identifier after receiving the request.

The basic information of the idempotence flag is as follows:


|Name |Type |Is it required |Example value |Description |
|---|---|---|---|---|
|ClientToken |String |No |testClientToken |An identifier that guarantees client side request idempotency.<br><br>The identifier is a 1\-64\-bit ASCII string, case\-sensitive, generated by the client side, and should ensure that the identifier is unique between different requests. |


Idempotence logo instructions:


* Uniqueness: idempotent identifiers are unique across requests. If you provide an already used identifier but the request parameters change, the server level returns an InvalidIdempotency error code.

* Valid time: The idempotent flag is 8 hours. If you provide an invalid flag, the server level returns an InvalidIdempotency error code.

* After retrying with the idempotent flag:

   * The return result status code is 2xx, and the client side will get the same result as the previous request, such as the instance ID and other information when the create instance request is successful.

   * When the return result status code is 4xx, the client side retry request fails. It is recommended to retry the request after troubleshooting the problem according to the error message.

## API that supports idempotent

The following message queue RocketMQ OpenAPI supports setting the idempotence flag:


* [CreateInstance](https://docs.byteplus.com/en/docs/kafka/CreateInstance-v2)

* [ModifyInstanceSpec](https://docs.byteplus.com/en/docs/kafka/ModifyInstanceSpec-v2)
