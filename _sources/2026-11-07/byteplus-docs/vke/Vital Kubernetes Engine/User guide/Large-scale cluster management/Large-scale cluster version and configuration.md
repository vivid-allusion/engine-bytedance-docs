When you set up a production environment for large\-scale clusters, refer to this topic to select cluster versions and configure add\-ons. This topic covers key aspects such as Kubernetes version selection, control plane configuration, data plane optimization, and container network and DNS configuration.

## Version selection

When the number of nodes in a cluster exceeds 500, the recommended Kubernetes versions for the cluster and the versions of important add\-ons in the cluster are as follows.


|Category |Name |Recommended version |Reason for recommendation |
|---|---|---|---|
|Kubernetes version |Kubernetes version |≥ 1.34 |The cache consistency read and streaming List response features are generally available. For List requests that involve a large number of resources, the features can effectively reduce kube\-apiserver memory usage and improve system stability. For more information, see [Kubernetes version release notes](https://docs.byteplus.com/en/docs/vke/Kubernetes-version-release-notes). |
|Important add\-on version |vpc\-cni |≥ v1.9.3 |* client\-go supports streaming List responses.<br><br>* The informer filters Headless Services and their corresponding EndpointSlices. |
||vpc\-cni\-controlplane |≥ v1.4.5 |* client\-go supports streaming List responses.<br><br>* The default number of workers has been increased. |
||core\-dns |≥ 1.10.1\-vke.200 |Optimized default CPU and memory resource requests and limits. |
||csi\-ebs |≥ 1.3.1 |client\-go supports streaming List responses. |
||csi\-nas |≥ v1.3.2 |client\-go supports streaming List responses. |
||csi\-tos |We recommend using csi\-fsx instead of csi\-tos |The csi\-tos has entered the deprecation phase. Therefore, we recommend using csi\-fsx instead of csi\-tos. |
||csi\-vepfs |≥ v0.17.0 |client\-go supports streaming List responses. |
||fsx |csi\-fsx ≥ v0.7.0<br><br>fsx\-service ≥ v0.10.2 |client\-go supports streaming List responses. |

## Control plane configuration


|Category |Description |Observability method |Recommendation |
|---|---|---|---|
|Control plane specifications |VKE provides the managed Kubernetes control plane. Within the limits described in [Large-scale cluster limits and suggestions](https://docs.byteplus.com/en/docs/vke/Large-scale_cluster_limits_and_suggestions), VKE automatically scales up the Kubernetes control plane based on its load. Typically, this operation is complete within 15 minutes, with a rolling update policy strictly followed. During the process, persistent connections may be disconnected and reconnected, and the response latency of the kube\-apiserver may experience some jitters. Theoretically, this does not affect your business. |For the instructions on how to enable cloud\-native observability for the cluster, see [Enabling observability](https://docs.byteplus.com/en/docs/vke/Enabling-cloud-native-observability). |* Make sure that the cluster operates within the limits described in [Large-scale cluster limits and suggestions](https://docs.byteplus.com/en/docs/vke/Large-scale_cluster_limits_and_suggestions). Exceeding the limits may affect cluster stability.<br><br>* When the cluster scales out by more than 500 nodes in a short period, to prevent jitters caused by bursty traffic, [submit a ticket](https://console.byteplus.com/workorder/create?step=1) or contact your BytePlus account manager to upgrade the specifications. |
|APIServer CLB upgrade |Kubernetes data plane add\-ons access the APIServer through CLB. As the scale of cluster nodes and Pods increases, the inbound traffic to the APIServer will significantly increase. The CLB bandwidth capacity may become a bottleneck, which will result in increased latencies or even timeouts in communication between data plane add\-ons and the control plane.<br><br>VKE uses CLB instances that use the **Billing by specification** method by default. The instances provide a maximum bandwidth of 2000 Mbps. For large\-scale clusters or high\-concurrency scenarios, you need to upgrade the CLB bandwidth specification in a timely manner based on actual traffic monitoring data. |View monitoring data for the bandwidth of the CLB instance associated with the APIServer. For details, see [Viewing monitoring data](https://docs.byteplus.com/en/docs/clb/Viewing-monitoring-data). |* Configure alerts related to CLB bandwidth utilization. For details, see [Configuring alert policies](https://docs.byteplus.com/en/docs/clb/Configuring-an-alert-policy).<br><br>* When the number of cluster nodes exceeds 1,000 or CLB bandwidth utilization continuously exceeds 70%, you need to upgrade the specification or switch to **Usage\-based billing** in a timely manner. For more information, see [Changing instance billing methods](https://docs.byteplus.com/en/docs/clb/Billing-06). |
|kube\-controller\-manager configuration |The automatic scaling of the VKE control plane dynamically adjusts the parameters of kube\-controller\-manager. Therefore, no additional attention is required. |Enable cloud\-native observability for the cluster and view information, such as the controller queue length and latency, by using the kube\-controller\-manager monitoring dashboard. For details, see [Enabling observability](https://docs.byteplus.com/en/docs/vke/Enabling-cloud-native-observability) and [Control plane observability](https://docs.byteplus.com/en/docs/vke/Control-plane-service-observability). |* When the default reconciliation performance of the cluster cannot meet your business requirements, you can adjust the kubeApiQps and KubeApiBurst parameters of kube\-controller\-manager to tune cluster performance. For detailed steps, see the content described on the **Control plane parameter configuration** tab in the [Viewing cluster information](https://docs.byteplus.com/en/docs/vke/Cluster-basics) topic.<br><br>* More worker nodes and higher QPS/Burst values will impose higher pressure on kube\-apiserver. Apply these settings to production only after being tested. |

## Data plane configuration


|Category |Description |Recommendation |Recommended value |
|---|---|---|---|
|kubelet configuration |The default QPS/Burst values for VKE kubelet are 5/10. When a large number of Pods with frequent changes exist on a node, significant performance issues may occur, such as slow Pod status updates, scheduling delays, and slow volume mounting. We recommend increasing the values of the `--kube-api-qps` and `--kube-api-burst` parameters. If you increase the values of these parameters, the QPS between kubelet and kube\-apiserver will be significantly increased. Pay close attention to the kube\-apiserver load and gradually increase the value of the kube\-apiserver parameter. |* Adjust the `--kube-api-qps` and `--kube-api-burst` parameters of kubelet. For details, see [Configuring Kubelet parameters for node pools](https://docs.byteplus.com/en/docs/vke/Configuring-kubelet-parameters-for-a-NodePool?lang=en).<br><br>* Gradually increase the values of `--kube-api-qps` and `--kube-api-burst`, monitor the performance and resource usage of kube\-apiserver, and then apply the configuration to production after testing. |Recommended values for kubelet parameters are as follows:<br><br><br>* kubeAPIQPS: 50<br><br>* kubeAPIBurst: 100<br><br>* eventRecordQPS: 50<br><br>* eventBurst: 100<br><br>* registryPullQPS: 10<br><br>* registryBurst: 20 |
|Node startup acceleration |Node startup mainly involves ECS instance creation, node initialization, system add\-on image downloading, and node status refresh. Startup duration varies based on different ECS instance types, and the end\-to\-end startup duration is usually within 5 minutes. |For users who require faster node startup, disk snapshots can be used for acceleration. For details, see [Accelerating node scale-out by using data volume snapshots](https://docs.byteplus.com/en/docs/vke/Accelerating_node_scale-out_by_using_data_volume_snapshots). |None |
|Configuring container image acceleration |In large\-scale clusters, when application images reach several GB or even tens of GB, image pull time becomes the main bottleneck for Pod startup. Centralized image registries can easily become a network bandwidth bottleneck when images are being concurrently pulled. VKE provides two acceleration solutions:<br><br><br>* P2P acceleration uses the internal bandwidth of nodes to distribute images among nodes. It applies to concurrent pull scenarios in large\-scale clusters.<br><br>* Image lazy loading (Nydus) loads hot regions of image data on demand. This achieves readiness in seconds.<br><br><br>The two solutions can be used together for the optimal result. |* On the **Overview** page of the target cluster in the [VKE console](https://console.byteplus.com/vke/), click the **Control plane parameter configuration** tab and make sure that [AlwaysPullImages](https://kubernetes.io/docs/reference/access-authn-authz/admission-controllers/#alwayspullimages) is disabled. For details, see [Viewing cluster information](https://docs.byteplus.com/en/docs/vke/Cluster-basics).<br><br>* For image acceleration solutions, see [P2P acceleration](https://docs.byteplus.com/en/docs/vke/P2P-acceleration-solution) and [Image lazy loading solutions](https://docs.byteplus.com/en/docs/vke/Container-image-lazy-loading-solution). |None |

## Network planning


|Category |Description |Recommendation |Recommended value |
|---|---|---|---|
|Network model |Two network models are available:<br><br><br>* **VPC\-CNI**: the default network model of VKE. Based on the native VPC, it supports more nodes and higher workloads. In VPC\-CNI mode, the VPC allocates an IP address range for all Pod IP addresses. Each node is assigned a subnet from this range to allocate IP addresses to the Pods running on it. This approach features high performance and scalability.<br><br>* **Flannel**: adds a new custom route to the route table of the VPC for each new node. The VPC route table supports up to 1,000 rules. Therefore, Flannel clusters support up to 1,000 nodes and are not suitable for large\-scale workloads. For more information, see [Limits of VPC routes](https://docs.byteplus.com/en/docs/vpc/Limits?lang=en). |The network model cannot be changed after being selected. To ensure cluster scalability, use the VPC\-CNI network model. |None |
|Cluster CIDR block planning |In large\-scale Kubernetes clusters, the size of the IP address CIDR block for the container network determines the maximum number of nodes and Pods that the cluster can support. |* When the number of nodes exceeds 1,000, we recommend using a VPC with the `10.0.0.0/8` CIDR block to ensure sufficient IP addresses for subnet division.<br><br>* Estimate the planned capacity of the Service CIDR block in advance. The CIDR block size cannot be adjusted after being created. |None |
|Cilium Operator configuration |Cilium Operator periodically reclaims CiliumIdentity, which has an upper limit of 65,535. When not deployed independently, Cilium Operator is integrated with the Cello DaemonSet with one replica per node. As the number of nodes increases, all replicas perform leader election by using the Lease mechanism. This generates a large number of access requests to kube\-apiserver. For large‑scale clusters, Cilium Operator needs to be decoupled from the DaemonSet and deployed as an independent Deployment with an appropriate number of replicas. |On the **Addons** page of the target cluster in the [VKE console](https://console.byteplus.com/vke), configure the **vpc\-cni** add\-on to adjust the Cilium Operator settings.<br><br><br>* For clusters with more than 500 nodes, we recommend enabling the independent deployment of Cilium Operator.<br><br>* For clusters with more than 50,000 Pods, we recommend upgrading the resource settings of Cilium Operator.<br><br><br> |* For the number of replicas for the independently deployed Cilium Operator, we recommend setting the value to 3 or more.<br><br>* For the memory limit of Cilium Operator, we recommend setting the value to at least 8 GiB.<br><br><br><span>![图片](https://portal.volccdn.com/obj/volcfe/cloud-universal-doc/upload_f7424c484f56ccaac77190e295761412.png) </span> |
|VPC\-CNI IP pooling settings |Cello uses a pooling mechanism to cache VPC ENIs and IPs to accelerate Pod startup. With the default pooling parameters (for example, `poolTarget=3`), a cluster with 800 nodes caches about 2,400 idle IPs. For large\-scale clusters or scenarios with limited subnet capacity, you need to perform an evaluation based on your business requirements and adjust the pooling parameters accordingly. |On the **Addons** page of the target cluster in the [VKE console](https://console.byteplus.com/vke), configure the **vpc\-cni** add\-on to adjust pooling parameters based on your business requirements.<br><br><br>* Increasing the values of the pooling parameters increases Pod creation throughput and reduces requests to VPC APIs during sudden traffic spikes. However, it will lead to pre‑allocation and waste of IP resources.<br><br>* Decreasing the values of the pooling parameters saves IPs but may affect Pod startup speed. |<span>![图片](https://portal.volccdn.com/obj/volcfe/cloud-universal-doc/upload_3232bac91697561a3ba662d1b7d3b844.png) </span> |
|NetworkPolicy limit |If NetworkPolicy is enabled for the cluster to control access among Pods, the Cello add\-on on each node will perform List and Watch operations on all CiliumEndpoints in the cluster. When the number of nodes exceeds 1,000, access pressure will be imposed on the APIServer. |* If you do not need to use NetworkPolicy, make sure that NetworkPolicy is disabled in the vpc\-cni add\-on settings. NetworkPolicy is disabled by default.<br><br>* If you use NetworkPolicy, we also recommend configuring the labels of Cilium to prevent NetworkPolicy from participating in CiliumIdentity allocation, which causes CiliumIdentity to reach its upper limit. For more information, see [Cilium official documentation](https://docs.cilium.io/en/stable/operations/performance/scalability/identity-relevant-labels/#excluding-labels). |None |
|Service and NetworkPolicy counts |In VPC\-CNI clusters, the Service and NetworkPolicy are implemented based on the BPF Map mechanism of Cilium, and their counts are related to the BPF Map size. For each Service, its corresponding Pods generate unique entries in the Backend Map. Each Pod selected by a NetworkPolicy corresponds to a Policy Map, and each NetworkPolicy rule generates a record in the Map. As the number of Services, Pod rules, and NetworkPolicy rules in the cluster increases, the associated BPF Maps may reach their capacity limits. This can lead to the following issues: ineffective Services or NetworkPolicy rules, abnormal Service status, access issues, and unexpected access control behavior. |Based on the expected cluster size, you can [submit a ticket](https://console.byteplus.com/workorder/create?step=1) to contact the VKE team to plan and properly configure BPF Map parameters. This prevents business operations from being affected due to insufficient capacity. You can also use VMP to observe the BPF Map capacity with the following metrics:<br><br><br>* Service Metrics: `max(cilium_bpf_map_pressure{map_name=~"lb.*"}) by (map_name)`<br><br>* NetworkPolicy Metrics: `max(cilium_bpf_map_pressure{map_name=~"policy.*"}) by (map_name)` |None |

## Cluster DNS planning


|Category |Description |Observability method |Recommendation |
|---|---|---|---|
|CoreDNS replica adjustment |CoreDNS functions as a DNS resolution service in the cluster. The number of CoreDNS replicas directly impacts the processing capacity for DNS queries. In large\-scale clusters or scenarios with high DNS request load, the default settings may not meet your business requirements. You need to manually adjust the number of CoreDNS replicas based on the actual load. |Enable cloud\-native observability for the cluster and use the core\-dns monitoring dashboard to view information, such as the error rate and request latencies. For details, see [Enabling observability](https://docs.byteplus.com/en/docs/vke/Enabling-cloud-native-observability) and [DNS service observability](https://docs.byteplus.com/en/docs/vke/DNS-service-observability). |For a cluster with more than 500 nodes, increase CoreDNS to 6 or more. For details, see [CoreDNS best practices](https://docs.byteplus.com/en/docs/vke/CoreDNS-best-practices). |
|Node\-local\-dns deployment |NodeLocal DNSCache deploys a local DNS cache DaemonSet on each node. This allows Pod DNS queries to be resolved locally and distributes the centralized DNS load across nodes while reducing query latencies. |None |For a cluster with more than 500 nodes, we recommend enabling NodeLocalDNS deployment. For details, see [Using NodeLocal DNSCache as a DNS caching agent](https://docs.byteplus.com/en/docs/vke/Using-NodeLocal-DNSCache?lang=en). |
