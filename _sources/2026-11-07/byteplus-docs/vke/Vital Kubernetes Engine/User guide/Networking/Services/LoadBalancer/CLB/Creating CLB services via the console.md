Vital Kubernetes Engine can provide LoadBalancer services. This topic describes how to create a LoadBalancer Service via the console.

> **warning**

> Before configuring a LoadBalancer Service, be sure to carefully read [Considerations for using LoadBalancer services](https://docs.byteplus.com/en/docs/vke/LoadBalancer_service_usage_precautions).

## Limits

* We recommend configuring CLB parameters directly in the VKE console. For settings unavailable in the console, use annotations to complete the configuration. Configuring annotations by **editing Yaml** is recommended.

* Only the VPC\-CNI network model supports the LB\-to\-pod direct access mode, which allows direct binding of the auxiliary Pod ENI to the backend of a CLB instance.

   > **tip**

   > In LB\-to\-pod direct access mode, the number of backend servers allowed by a CLB instance is limited and must be planned appropriately. For details about the limitations, see [Constraints and limits of CLB](https://docs.byteplus.com/en/docs/clb/Product-Overview-07).

## Prerequisites

* A workload has been created. For details, see [Creating Deployments](https://docs.byteplus.com/en/docs/vke/Creating-a-Deployment), [Creating StatefulSets](https://docs.byteplus.com/en/docs/vke/Creating-a-StatefulSet), and [Creating DaemonSets](https://docs.byteplus.com/en/docs/vke/Creating-a-DaemonSet).

   > **tip**

   > Currently, only the following workloads can be associated: Deployment, StatefulSet, and DaemonSet.

## Procedure

1. Log in to the [VKE console](https://console.byteplus.com/vke).

2. In the left navigation bar, click **Cluster**.

3. On the cluster list page, click the cluster you want to configure.

4. In the left navigation pane of the cluster management page, click **Services and Ingresses** \> **Service**. On the page that appears, click **Create Service** to configure a Service.

   * **Basic information**

      |**Parameter** |**Description** |
      |---|---|
      |Name |Enter a name for the Service. Make sure the name is unique under the same namespace. |
      |Namespace |Select the namespace to which the Service belongs. It is recommended that you select the namespace created by yourself or the **default** namespace created by the system. For details about namespaces, see [Namespace overview](https://docs.byteplus.com/en/docs/vke/Namespace-overview). |
      |Tag |Click **Add new** to add labels to the service. Labels are used to define various attributes of services, facilitating batch filtering and other operations. |
      |Annotation |Click **Add annotation** to add a key\-value pair as an annotation to the Service. Alternatively, you can configure annotations in the YAML file describing routing rules to achieve more capabilities of Layer 4 load balancers. For details, see [Using annotations to configure LoadBalancer services](https://docs.byteplus.com/en/docs/vke/Configuring-a-LoadBalancer-Service-using-annotations). |

   * **Access configuration**

      |**Parameter** |**Description** |
      |---|---|
      |Access type |Configure the access type for the Service. For this example, select **LoadBalancer**. |
      |Load balancing type |Specify the load balancer type. In this example, select **CLB**. |
      |Communication protocol |[[Beta - apply for trial](https://docs.byteplus.com/en/docs/vke/How-do-I-apply-for-beta-features)] For IPv4/IPv6 dual\-stack clusters, you can configure the service communication protocol as needed to support scenarios in which services are accessed over IPv6 addresses. The options include:<br><br><br>* **IPv4**: IPv4 addresses only.<br><br>* **IPv4&IPv6**: Both protocols are allowed, but the IPv4 addresses will be used by default.<br><br>* **IPv6&IPv4**: Both protocols are allowed, but the IPv6 addresses will be used by default.<br><br><br>> **tip**<br><br><br>> For details about how to create IPv4/IPv6 dual\-stack clusters, see [Creating IPv4/IPv6 dual\-stack clusters with VKE](https://docs.byteplus.com/en/docs/vke/Deploying-an-IPv4_IPv6-dual-stack-cluster-using-VKE).<br> |
      |LB\-to\-pod direct access mode |This parameter is shown only in clusters using the VPC\-CNI network model. It is enabled by default. When it is enabled, the Pod ENI is directly bound to the backend of the load balancer. Note that the CLB cannot handle too many backend servers. Therefore, you need to make sure the number of servers is acceptable to the CLB in the topology. For details about the limitations, see [Constraints and limits of CLB](https://docs.byteplus.com/en/docs/clb/Product-Overview-07). |
      |Load balancer |Configure the load balancer instance for the Service. You can select an instance or have one automatically created as needed. There are two access modes: **Public NAT for internet endpoint** and **Private network**.<br><br>> **tip**<br><br><br>> A LoadBalancer service running with the protocol set to IPv4&IPv6 or IPv6&IPv4 can only be accessed within a private network by default. However, you can expose it on the Internet by:<br><br><br><br>* > If Internet access over IPv4 is required, you can bind a public IPv4 address to the service on the CLB console page.<br><br><br>* > If Internet access over IPv6 is required, you can enable IPv6 Internet bandwidth for the service on the CLB console page.<br><br><br>* **Use existing**: Use an existing CLB instance that is not used by VKE. Using an existing CLB instance will not bring any changes to the existing listener rules of that instance.<br><br>   We recommend creating a new CLB instance unless it is required to use the existing ones.<br><br>* **auto create**: Automatically create a new CLB instance. You need to configure the following parameters. For detailed parameter descriptions, see [Creating LoadBalancer instances](https://docs.byteplus.com/en/docs/clb/CLB-instances-01).<br><br>   > **warning**<br>   <br><br>   * > Do not use the CLB instances automatically created with other Ingress or Service resources. Otherwise incomplete reclamation of resources might happen.<br>   <br><br>   * > The CLB instances automatically created will be deleted if the service is removed. Do not manually modify the listeners of these CLB instances.<br>   <br><br>   * > Only the CLB instances of **Pay\-as\-you\-go** will be created.<br>   <br><br>   * > In the case of using existing CLB instances, those created through the LoadBalancer console are the only instances supported, instead of the ones created through the Vital Kubernetes Engine console.<br>   <br><br>   * > The CLB created through Vital Kubernetes Engine console features multiple availability zones. If the CLB in the current region supports cross\-availability zone fault tolerance, a primary and a standby availability zone will be attached to the CLB instance. It allows traffic to be switched to the standby zone as soon as the primary one fails.<br>   <br><br>   * **Name**: Enter a name for the CLB instance.<br><br>   * **Availability zone**: Select a primary availability zone and a standby availability zone for the CLB instance to ensure high availability. If you do not select any zone, the following logic will be applied:<br><br>      * For a region that only has a single availability zone, a CLB instance with that zone is created.<br><br>      * For a region that has more than one availability zone, a CLB instance with a primary and standby availability zone is created according to the zones available in that region.<br><br>   * **Billing type**: Select a billing type for the CLB instance. **Pay\-as\-you\-go** is supported.<br><br>   * **Billing method**: Select a billing method for the CLB instance. **Billing by specification** is supported.<br><br>   * **Instance specification**: the specification of the CLB instance. You can choose a specification according to the performance requirements of different business scenarios. For details, see [Product types and specifications](https://docs.byteplus.com/en/docs/clb/Product-Overview-02).<br><br>   > **tip**<br>   <br><br>   * > To update configurations of CLB instances, you need to enable the option **Updating instance** first.<br>   <br><br>   * > Before updating the CLB in the console, ensure that the specification you are about to use is no lower than the current one to provide sufficient capacity for business traffic.<br>   <br><br>   * **Write protection**: Specify whether to enable modification protection for the CLB instance. If enabled, the configurations of the CLB instance cannot be modified through the console or API.<br><br>   * **Subnet**: Select a subnet in a private network to deploy the CLB instance and allocate a private IP. The private IP of a CLB instance cannot be changed after being created successfully.<br><br>   * **IP version**: Select an IP version for the CLB instance. IPv4 is the only version currently supported. This setting cannot be modified.<br><br>   * **Line type**: Select the line type of the public IP. Different line types vary in performance and billing. Supported line types include **BGP (multi\-line)** , **BGP convergence**, **China Mobile**, **China Telecom**, and **China Unicom**.<br><br>   > **warning**<br>   <br><br>   > Line types except **BGP (multi\-line)** are beta features of the EIP product. To apply for these types, please contact your account manager.<br>   <br><br>   * **Billing method**: billing methods for Internet access include:<br><br>      * **Pay\-as\-you\-go \- bandwidth limit**: It will be charged based on usage duration with an upper limit on bandwidth.<br><br>      * **Pay\-as\-you\-go \- actual traffic**: It will be charged based on the actual amount of traffic flowing to the Internet instead of usage duration.<br><br>   * **Bandwidth limit**: Specify the maximum bandwidth for the public IP. Unit: mbit/s. The upper limit of bandwidth can be changed anytime as needed.<br><br>   * **Shared bandwidth package**: disabled by default. You can enable **Add to shared bandwidth package** and select an existing shared bandwidth package if necessary.<br><br>   > **tip**<br>   <br><br>   > A shared bandwidth package is a reusable cloud resource for sharing bandwidth. It aggregates multiple public IPs and IPv6 public bandwidths from the same region into a shared bandwidth pool, reducing public bandwidth costs through bandwidth sharing. For details, see[What is a shared bandwidth package](https://docs.byteplus.com/en/docs/bandwidthpackage/What-is-Bandwidth-Package).<br>    |
      |Listeners |The listener is responsible for monitoring the requests on the Load Balancer and distributing traffic. You need to select a scheduling algorithm for the listener and decide whether to enable health check:<br><br><br>* **Scheduling algorithm**: These are the rules that the listener follows when forwarding requests.<br><br>   * **Weighted Round Robin**: Traffic is forwarded based on weight values. The higher the weight of the backend server, the more frequently (probabilistically) it is selected as the forwarding destination.<br><br>   * **Weighted Least Connection**: Traffic is forwarded first to the backend with the smallest real\-time ratio of connections to weight.<br><br>   * **Source Hashing**: Requests from the same source IP are forwarded to the same backend server based on consistent hashing on the source IP address.<br><br>* **HTTPS listening**: Select whether to enable HTTPS listening as needed. To enable HTTPS listening, you need to specify the following parameters:<br><br>   * **Certificate source**: Select the certificate source. BytePlus Certificate Center and the certificate management module in the CLB console are supported.<br><br>      > **tip**<br>      <br><br>      * > When you use a certificate from BytePlus Certificate Center for the first time, complete the authorization for cross\-service access requests based on the on\-screen prompts.<br>      <br><br>      * > To facilitate centralized certificate management, CLB is integrated with BytePlus Certificate Center. In the Certificate Center, you can perform all certificate\-related operations, including purchasing, uploading, renewing, and deleting certificates.<br>      <br><br>   * **Select a server certificate**: Select a server certificate from the drop\-down list.<br><br>   * **TLS security policy**: Select whether to enable the Transport Layer Security (TLS) security policy.<br><br>   * **Select policy**: Select a TLS security policy. Valid values:<br><br>      * **tls_cipher_policy_1_0**: Supports TLS v1.0, TLS v1.1, and TLS v1.2.<br><br>      * **tls_cipher_policy_1_1**: Supports TLS v1.1 and TLS v1.2.<br><br>      * **tls_cipher_policy_1_2**: supports TLS v1.2.<br><br>      * **tls_cipher_policy_1_2_strict**: supports TLS v1.2.<br><br>      * **tls_cipher_policy_1_3**: Supports TLS v1.3.<br><br>      * **tls_cipher_policy_1_2_strict_with_1_3**: Supports TLS v1.2 and TLS v1.3.<br><br>      > **tip**<br>      <br><br>      > The **tls_cipher_policy_1_3** and **tls_cipher_policy_1_2_strict_with_1_3** policies are beta features of the CLB service. Contact your account manager for a trial. Make sure that these policies can be selected in the CLB console before use.<br>      <br><br>   * **Two\-way authentication**: Select whether to enable two\-way authentication. Two\-way authentication means that both the client and the server verify the legitimacy of each other. If it is enabled, select a CA certificate from the CA certificate drop\-down list. For more information about two\-way authentication, see [Two-way authentication](https://docs.byteplus.com/en/docs/clb/HTTPS_listener_mutual_authentication).<br><br>* **Health check**: Set whether to enable health checking as needed. If enabled, the following parameters are available:<br><br>   * **Response timeout**: The waiting time for a health check response. If the backend server does not respond correctly within the specified time, it is considered anomalous.<br><br>   * **Detection interval**: the time interval between health check requests. The default interval is 2 seconds, which means the back\-end server is checked every 2 seconds.<br><br>      > **warning**<br>      <br><br>      > The time interval of health check needs to be longer than the response timeout.<br>      <br><br>   * **Health threshold**: The number of health check requests required to determine that the backend server is running as expected. The default value is 3, meaning a backend server is marked "healthy" if all 3 requests return normal responses.<br><br>   * **Unhealthy threshold**: The number of consecutive health check failures required to mark a backend server as unhealthy. The default value is 3, meaning a backend server is marked "unhealthy" if all 3 requests return abnormal responses. |
      |Port mapping |Create the mapping between the Service port and the container port:<br><br><br>* **Name**: Enter a name for the port mapping.<br><br>* **Service level port**: Enter a port used to access the Service. Duplicate ports are not allowed for Services using the same protocol.<br><br>* **Protocol**: select **TCP** or **UDP**.<br><br>* **Container port**: Specify the port of the container, which is a port number through which the workload provides services externally. e.g., the default port number for Nginx is 80. |
      |External traffic policy |The policies that the service will use to forward inbound traffic: <br><br><br>* **Cluster**: Traffic is forwarded evenly to each Pod of the workload.<br><br>* **Local**: Traffic can only be forwarded to the local pods on the current node, which may cause an unbalanced traffic distribution. However, the source IPs can be retained. |
      |Label selector |Services are bound to backend pods through label selectors.<br><br><br>* **Add new**: Specify the label on the workload to which the Service will be bound. You can find workload labels by clicking **Workload** in the left navigation pane of the cluster management page.<br><br>* **Associated workload**: Select the deployment with which the service will be associated. In this case, the **LB\-to\-pod direct access mode** is enabled by default and cannot be disabled.<br> |
      |Session persistence |Whether to enable session persistence.<br><br><br>* Disabled by default.<br><br>* Check **Configure timeout** to enable session persistence and set its duration. 5. Click **Confirm** to finish.

## Validate results

### Viewing the services

The LoadBalancer service you created successfully can be found in the service list. The **External endpoint** column shows the public or private IP address of the CLB instance connected to this service.

The option **Edit Yaml** in the **Actions** column allows you to view the detailed configurations of the LoadBalancer service, including the CLB instance ID mapped to the service. You can use the ID to find the corresponding CLB instance in the [LoadBalancer console](https://console.byteplus.com/clb).

> **tip**

> For details about the annotations involved in LoadBalancer service configurations, see [Configuring LoadBalancer services using annotations](https://docs.byteplus.com/en/docs/vke/Configuring-a-LoadBalancer-Service-using-annotations).

### Testing the services

To test the services, you can send requests to the public or private IP provided in the **External endpoint** column.
