After a node pool is created, you can leverage the resource monitoring feature to view its resource usage, such as CPU utilization, memory utilization, network, and TCP connections. This topic describes how to view node pool resource monitoring and explains the charts in the resource monitoring dashboard for the node pool.

<span id="jvYC5WN5"></span>
## Prerequisites


* A node pool has been created. For details, see [Creating a managed node pool](https://docs.byteplus.com/en/docs/vke/Creating-a-managed-NodePool?lang=en).

* Cloud\-native observability has been enabled. For details, see [Enabling observability](https://docs.byteplus.com/en/docs/vke/Enabling-cloud-native-observability).

## Observability dashboards


1. Log in to the [VKE console](https://console.byteplus.com/vke).

2. In the left navigation bar, click **Cluster**. Click the target cluster name to go to the management page of this cluster.

3. In the left navigation pane, click **Node pool**. In the node pool list, click the target node pool name to go to the node pool details page.

4. Click the **Resource monitoring** tab to view the resource usage of the node pool. You can specify a custom time range for querying information and set the information refresh mode to manual or automatic refresh.

   The following table describes the charts in the node pool resource monitoring dashboard.

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">Description   </div>
   

   <div data-tips="true" data-tips-type="default" data-wrapper-indent="1">For the method of obtaining the PromQL statements that correspond to the charts, see <a href="https://docs.byteplus.com/en/docs/vke/Using_dashboard">Using dashboards</a>.   </div>
   

   
   |Chart name |Unit |Chart description |
   |---|---|---|
   |Total CPU cores |cores |The total amount of CPU resources across all nodes in the node pool. It is mainly used for capacity evaluation and validation before and after scaling. You can evaluate whether the node pool can handle workload growth or whether resources are overprovisioned based on Pod CPU requests, CPU utilization, and node pool specifications.<br><br>If the total core count is lower than expected, possible causes include an insufficient number of nodes, nodes that failed to join the cluster, scaling not yet complete, or monitoring data not reported for some nodes. |
   |Total memory |Bytes |The total amount of memory resources across all nodes in the node pool. It is mainly used for memory capacity checking, node specification verification, and scaling effect validation. You can evaluate whether memory capacity meets workload requirements based on Pods' memory requests, memory utilization, and OOM events.<br><br>If total memory is lower than expected, node specifications may be incorrect, the number of nodes may be insufficient, nodes may be offline unexpectedly, or monitoring data may be missing. If total memory is sufficient but workloads still run out of memory, possible causes include memory usage growth of workloads, unreasonable resource configuration, or uneven load distribution. |
   |Total number of nodes |Count |The number of nodes in the node pool. It is used to verify whether the node pool size meets expectations. It is mainly used for node pool size verification and node status troubleshooting. After you create a node pool, change its size, or enable autoscaling, first check whether the total node count changes as expected.<br><br>If the total node count does not match expectations, possible causes include unfinished scaling operations, failed node joining, node removals, abnormal node status, or the monitoring system's failure to cover all nodes. If the total node count is normal but total cores or total memory is abnormal, possible causes include inconsistent node specifications or abnormal resource data reporting. |
   |CPU average utilization |% |The average CPU utilization of nodes in the node pool over the past 5 minutes. It is used to determine whether compute resources are under pressure or underutilized. You can combine the total core count, total number of nodes, business traffic, and Pod CPU requests to determine whether to scale out, scale in, or rebalance the workload distribution.<br><br>If the average CPU utilization remains consistently high, possible causes include increased business traffic, uneven Pod distribution, hotspots on a small number of nodes, or CPU requests set too low. If it remains consistently low over a long period, possible causes include resource redundancy, decreased workload, oversized node specifications, or idle resources not being reclaimed by autoscaling promptly. |
   |GPU average utilization |% |Average GPU utilization of nodes in the node pool. This metric applies to node pools that contain GPU\-type nodes. It is mainly used to analyze whether GPU resources are fully utilized. You can determine whether GPUs are idle, overloaded, or unevenly distributed based on the number of GPU workloads, job queues, Pod resource requests, and per\-node GPU usage.<br><br>If average GPU utilization stays low, possible causes include jobs not being scheduled to this node pool, insufficient parallelism, I/O bottlenecks, or unreasonable GPU resource requests. If it stays high, possible causes include insufficient GPU\-type nodes in the node pool, queued jobs, or jobs being concentrated on a small number of nodes. |
   |CPU utilization |% |The CPU utilization of nodes in the node pool over the past 5 minutes. It is mainly used to determine whether the overall workload is busy and whether single\-node hotspots exist.  <br><br><br>* **Average utilization**: Reflects overall CPU usage of the node pool. If this value is high, overall compute resource pressure in the node pool is high.<br><br>* **Peak utilization**: Reflects the CPU level of the nodes with the highest utilization. If this value is significantly higher than the average utilization, resource pressure may be concentrated on a small number of nodes. If this value remains close to the upper limit for a long time, the possible causes include concentrated compute\-intensive tasks, uneven Pod distribution, or node hotspots.<br><br><br><div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div><br><br><br><div data-tips="true" data-tips-type="default">If both average and peak utilization increase, possible causes include increased overall business traffic or insufficient node pool capacity.</div><br> |
   |Memory usage |% |The memory utilization of nodes in the node pool. It is mainly used to check whether memory resources are sufficient and to identify OOM risks early.  <br><br><br>* **Average utilization**: Reflects overall memory utilization of the node pool. If this value keeps increasing, overall memory pressure in the node pool is high. This may be caused by workload growth, memory leaks, or insufficient node pool capacity.<br><br>* **Peak utilization**: Reflects the utilization of the nodes with the highest memory usage. If this value is much higher than the average utilization, memory pressure may be concentrated on a small number of nodes. If this value remains close to the upper limit for a long time, possible causes include concentrated memory\-intensive tasks, uneven Pod distribution, application memory leaks, or a high risk of single\-node OOM.<br><br><br><div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div><br><br><br><div data-tips="true" data-tips-type="default">If both average utilization and peak utilization rise, possible causes are an overall increase in business load or insufficient memory capacity for the node pool.</div><br> |
   |CPU usage |cores |CPU usage of nodes in the node pool over the past 5 minutes. It is mainly used to determine the overall CPU consumption of the node pool and whether a single node has excessive CPU consumption.  <br><br><br>* **Average usage**: Reflects the average CPU usage of nodes in the node pool. If this value keeps increasing, the overall CPU consumption of the node pool rises.<br><br>* **Peak usage**: Reflects actual CPU consumption of the node with the highest CPU usage. If this value is significantly higher than the average usage, CPU consumption may be concentrated on a small number of nodes.<br><br><br><div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div><br><br><br><br>* <div data-tips="true" data-tips-type="default">If both the average and peak usage increase, the overall business traffic has increased, or the node pool's capacity may be insufficient.</div><br><br><br>* <div data-tips="true" data-tips-type="default">If only the peak usage increases, we recommend troubleshooting node hotspots and Pod distribution first.</div><br> |
   |Memory usage |Bytes |Memory usage of nodes in the node pool. It is mainly used to determine overall memory consumption and whether a single node uses excessive memory.  <br><br><br>* **Average usage**: Reflects the average memory usage of nodes in the node pool at the current time. If this value keeps increasing, the overall memory consumption increases.<br><br>* **Peak usage**: Reflects actual memory consumption of the node with the highest memory usage. If this value is significantly higher than the average usage, memory pressure may be concentrated on a small number of nodes.<br><br><br><div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div><br><br><br><br>* <div data-tips="true" data-tips-type="default">If both average and peak usage increase, possible causes include increased overall load or insufficient memory in the node pool.</div><br><br><br>* <div data-tips="true" data-tips-type="default">If only the peak usage increases, we recommend checking whether a single workload uses excessive memory or whether workloads are unevenly distributed.</div><br> |
   |CPU allocation rate (request) |% |The CPU request allocation ratio of the node pool. It is mainly used to determine whether the CPU resources declared by workloads are close to the CPU capacity that the node pool can provide.  <br><br><br>* **Average allocation ratio**: Reflects the average proportion of CPU requests on nodes in the node pool at the current time. A higher value indicates less schedulable CPU capacity remaining in the node pool.<br><br>* **Peak allocation ratio**: Reflects the allocation on the node with the highest CPU request proportion. If this value is significantly higher than the average allocation ratio, some nodes may be close to the allocatable limit.<br><br><br><div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div><br><br><br><br>* <div data-tips="true" data-tips-type="default">If both the average and peak allocation ratios are high, you may need to scale out the node pool or adjust workloads' requests.</div><br><br><br>* <div data-tips="true" data-tips-type="default">If only the peak allocation ratio is high, we recommend checking whether Pod scheduling is concentrated on a small number of nodes.</div><br> |
   |Memory allocation rate (request) |% |The memory allocation ratio of the node pool. It is mainly used to determine whether the memory resources declared by workloads are close to the total memory capacity of the node pool.  <br><br><br>* **Average allocation ratio**: Reflects the average proportion of memory requests on nodes in the node pool at the current time. A higher value indicates less schedulable memory capacity remaining in the node pool.<br><br>* **Peak allocation ratio**: Reflects the allocation on the node with the highest memory request proportion. If this value is significantly higher than the average allocation ratio, some nodes may have scheduling pressure.<br><br><br><div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div><br><br><br><br>* <div data-tips="true" data-tips-type="default">If both the average and peak allocation ratios are high, you may need to scale out the node pool or adjust workloads' requests.</div><br><br><br>* <div data-tips="true" data-tips-type="default">If only the peak allocation ratio is high, we recommend checking whether memory\-intensive Pods are scheduled to a small number of nodes.</div><br> |
   |Network inbound and outbound traffic rate |Bytes/s |Real\-time inbound and outbound traffic rate of each network interface in the node network. It is used to observe inbound and outbound traffic changes on different interfaces. Each curve in the chart corresponds to a network interface and a traffic direction, such as eth0_receive, eth0_transmit, lo_receive, and cilium_host_transmit.<br><br><br>* If inbound or outbound traffic on a network interface spikes, possible causes include an access volume increase, large data transfers, many image pulls, or excessive traffic on a single node.<br><br>* If traffic on the lo interface rises abnormally, the possible cause is frequent communication between internal components on the node.<br><br>* If traffic on virtual interfaces such as cilium_host or ipvl is abnormal, we recommend further troubleshooting based on the container network path and Pod distribution. |
   |Inbound and outbound packet rate |pps |The real\-time packet sending and receiving rates for each network interface in the node network. It is used to view changes in packet counts across different interfaces in both the inbound and outbound directions. Each curve in the chart corresponds to a network interface and a traffic direction, such as eth0_receive, eth0_transmit, lo_receive, and cilium_host_transmit.<br><br><br>* If the packet rate on a specific interface increases sharply but the traffic rate shows little change, possible causes include a large number of small packet requests, increased short\-lived connections, or abnormal probe traffic.<br><br>* If the packet rate is abnormal on interfaces such as lo, cilium_host, or ipvl, we recommend further investigation in combination with intra\-node communication, the container network path, and Pod distribution. |
   |Inflow and outflow packet loss rate |% |The packet loss ratio in inbound and outbound directions on a node. It is used to determine whether network transmission is stable. The dashboard splits curves by node IP address and traffic direction, such as 192.168.2.152_transmit and 192.168.2.152_receive. It is mainly used to locate node\-level network quality issues. You can identify the node with packet loss based on the node IP address, and then check the inbound or outbound direction to determine whether the issue is more likely on the receiving path, sending path, container network, or upstream or downstream network.<br><br><br>* If the packet loss ratio on a node IP address increases, possible causes include network congestion, high network interface pressure on the node, container network anomalies, or degraded upstream/downstream link quality.<br><br>* If both the outbound and inbound directions show an increase, we recommend checking the node network, container network, and link congestion first.<br><br>* If only one direction increases, we recommend identifying upstream or downstream issues in that direction. |
   |TCP connection |count/s |TCP connection count, connection status, and connection establishment on a node. These metrics are mainly used to determine whether the node is under abnormal connection pressure.  <br><br><br>* **TCP_sock_inuse**: The number of TCP sockets currently in use. A sustained increase may indicate growing connection counts or connections not being released promptly.<br><br>* **TCP_sock_alloc**: The number of allocated TCP sockets, including sockets that have not yet established a connection. A significant increase may indicate that the system is allocating a large number of connection resources.<br><br>* **TCP_sock_tw**: the number of connections in the TIME_WAIT state. A persistently high value may indicate too many short\-lived connections or insufficient connection reuse.<br><br>* **CurrEstab**: The number of connections currently in the ESTABLISHED state. It is used to monitor the scale of active connections.<br><br>* **TCP_ActiveOpens / TCP_PassiveOpens**: The number of actively initiated and passively accepted TCP connections. It is used to distinguish between connection growth on the client side and the server side.<br><br>* **TCP_ext_ListenDrops**: The number of drops caused by listen queue overflow. An increase in this value indicates that connection requests may have exceeded the service's processing capacity. |
