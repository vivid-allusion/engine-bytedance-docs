This topic describes checks performed for a cluster upgrade in Vital Kubernetes Engine (VKE).

<span id="JpolIxK3"></span>
## Control plane checks


|**Category** |**Check item** |Exception detected |**Impact description** |**Fix suggestions** |
|---|---|---|---|---|
|Cluster resource quotas |VPC subnet status |No VPC subnet is found. Please confirm whether the cluster network has been deleted. |A subnet exception can cause the cluster to become unavailable. |Confirm whether the network configuration of the cluster is correct. For details, see [Basic cluster information](https://docs.byteplus.com/en/docs/vke/Cluster-basics). |
||Remaining number of IP addresses in VPC\-CNI subnets |The remaining number of IP addresses within the subnet of the VPC\-CNI network is insufficient. |A low remaining number of IP addresses in the subnet can cause an upgrade failure. |Add a new subnet or release some used IP addresses. For details, see [Changing API Server subnets](https://docs.byteplus.com/en/docs/vke/Modifying-API-server-subnets). |
|Node health |Node status |The cluster contains abnormal nodes. |When a cluster contains abnormal nodes, cluster upgrades are not allowed in order to prevent cluster abnormalities. |Fix abnormal nodes to restore the status to Ready. You can follow the on\-screen prompts to restore nodes. |
|Deprecated APIs |Deprecated pod groups |The cluster contains deprecated pod groups. |In Kubernetes v1.28 and later, the apiGroups for PodGroup have been updated from `scheduling.sigs.Kubernetes.io` to `scheduling.x-Kubernetes.io`. After a cluster upgrade, services that use these resources will become unavailable. |Recreate the required PodGroup resources based on `scheduling.x-Kubernetes.io` apiGroups after the cluster is upgraded to v1.28 or later. For details, visit [GitHub](https://github.com/kubernetes-sigs/scheduler-plugins/pull/526). |
||Deprecated Kubernetes API resources |The cluster is using a deprecated Kubernetes API. |Some services in the cluster are using deprecated Kubernetes APIs, which will cause these services to become unavailable after an upgrade. |Align your applications with Kubernetes API deprecations by reviewing the **API version changes and deprecation notices** documented in the [VKE release notes](https://docs.byteplus.com/en/docs/vke/Kubernetes-version-release-notes). |
||Records of deprecated Kubernetes APIs in audit logs |No cluster audit log topics are found. Check whether cluster auditing is enabled. |Some services in the cluster may use deprecated Kubernetes APIs, which can cause those services to become unavailable after the cluster is upgraded. |Align your applications with Kubernetes API deprecations by reviewing the **API version changes and deprecation notices** documented in the [VKE release notes](https://docs.byteplus.com/en/docs/vke/Kubernetes-version-release-notes). You can ignore this alert if you have made valid changes. |
||Records of removed Kubernetes APIs in audit logs<br><br> |No cluster audit log topics are found. Check whether cluster auditing is enabled. |Some services in the cluster may use deprecated Kubernetes APIs, which can cause those services to become unavailable after the cluster is upgraded. |Align your applications with Kubernetes API deprecations by reviewing the **API version changes and deprecation notices** documented in the [VKE release notes](https://docs.byteplus.com/en/docs/vke/Kubernetes-version-release-notes). You can ignore this alert if you have made valid changes. |
||Deprecated APIs for Kubernetes clusters over the past 30 days |The cluster has used a deprecated or removed Kubernetes API in the past 30 days. |Some services in the cluster may use deprecated Kubernetes APIs, which can cause those services to become unavailable after the cluster is upgraded. |Align your applications with Kubernetes API deprecations by reviewing the **API version changes and deprecation notices** documented in the [VKE release notes](https://docs.byteplus.com/en/docs/vke/Kubernetes-version-release-notes). You can ignore this alert if you have made valid changes. |
||VPC\-CNI compatibility |No cluster audit log topics are found. Check whether cluster auditing is enabled. |The vpc\-cni add\-on uses API resources that will be removed in the target Kubernetes version. If you do not handle this exception, the vpc\-cni add\-on will not work as expected after the upgrade, causing pod creation to fail. |[Connect to the cluster](https://docs.byteplus.com/en/docs/vke/Connecting-to-a-cluster) and run the `kubectl rollout restart daemonset cello -n kube-system` command to restart the vpc\-cni add\-on. This ensures that the add\-on gets the latest EndpointSlices resources. After the add\-on restarts, you can ignore this alert. |
||Audit log status |Cluster auditing is not enabled. You need to enable cluster auditing first. |If auditing is not enabled or has been enabled for less than 24 hours, checks for removed or deprecated Kubernetes APIs will be affected. Calls to these APIs may exist, leading to service unavailability after the upgrade. |Enable [cluster auditing](https://docs.byteplus.com/en/docs/vke/Cluster-auditing) and perform control plane checks after 24 hours. |
|Cluster component status |Kubernetes version |The current cluster version does not qualify for an upgrade. |Upgrading is not permitted if the cluster's current version is too low or is already the latest version. |The current Kubernetes version of the cluster must meet the following version requirements to qualify for an upgrade:<br><br><br>* The current Kubernetes version is v1.20 or later.<br><br>* The current version is earlier than the target version of the upgrade. |
||Cluster status |The cluster status is abnormal.<br><br> |Restore the cluster status to Running first. A cluster state other than **Running** can cause the upgrade to fail.<br><br><div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div><br><br><br><div data-tips="true" data-tips-type="default"> <code>Updating</code> is a special status. <code>Updating[ClusterVersionUpgrading]</code> indicates that the cluster is currently undergoing a version upgrade, while <code>Updating[Progressing]</code> means the cluster is being updated. When the cluster is in one of the states, you cannot perform another upgrade.</div><br> |[Submit a ticket](https://console.byteplus.com/workorder/create) to restore the cluster status.<br><br> |
||kube\-apiserver status |The kube\-apiserver component on the control plane of the cluster is abnormal. |The cluster cannot provide API services. |[Submit a ticket](https://console.byteplus.com/workorder/create) to restore the kube\-apiserver status. |
||etcd status |The status of etcd on the control plane is abnormal. |The cluster may not be able to provide API services. |[Submit a ticket](https://console.byteplus.com/workorder/create) to restore the etcd status. |
||kube\-controller\-manager status |kube\-controller\-manager on the control plane is abnormal. |The issue will cause ReplicationController exceptions.<br><br> |[Submit a ticket](https://console.byteplus.com/workorder/create) to restore kube\-controller\-manager status. |
||cloud\-controller\-manager status |cloud\-controller\-manager on the control plane is abnormal. |The cluster cannot manage BytePlus cloud resources and therefore cannot function as expected. |[Submit a ticket](https://console.byteplus.com/workorder/create) to restore the cloud\-controller\-manager status. |
||kube\-scheduler status |kube\-scheduler on the control plane is abnormal. |Resource scheduling within the cluster is abnormal, and pods cannot be created. |[Submit a ticket](https://console.byteplus.com/workorder/create) to restore the kube\-scheduler status. |
||kube\-proxy status |kube\-proxy in the cluster using the Flannel network is abnormal. |The cluster upgrade will fail due to cluster network problems. |[Submit a ticket](https://console.byteplus.com/workorder/create) to restore the kube\-proxy status. |
||vpc\-cni status |The cluster uses the VPC\-CNI network model but the cello container of the vpc\-cni add\-on is abnormal. |The cluster upgrade will fail due to cluster network problems.<br><br><div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div><br><br><br><div data-tips="true" data-tips-type="default">cello is a container in the pod corresponding to the vpc\-cni add\-on. cello is used to manage auxiliary elastic network interfaces of a node and allocate private IP addresses to pods.</div><br> |In the kube\-system namespace, view the runtime information of cello, and attempt to restore the cello status based on the obtained information. If the issue persists, [submit a ticket](https://console.byteplus.com/workorder/create) to contact technical support for resolution. |
||scheduler\-controller\-manager status |scheduler\-controller\-manager on the control plane is abnormal. |The cluster cannot provide API services. |[Submit a ticket](https://console.byteplus.com/workorder/create) to restore the scheduler\-controller\-manager status. |
||general\-webhook status |general\-webhook on the control plane is abnormal. |API requests to the cluster may not be properly handled. |[Submit a ticket](https://console.byteplus.com/workorder/create) to restore the status of general\-webhook. |
||Add\-on compatibility |Add\-on compatibility check failed. |Upgrade relevant add\-ons before upgrading the cluster to prevent possible issues afterwards. |Upgrade add\-ons to their latest versions. For details, see [Upgrading add-ons](https://docs.byteplus.com/en/docs/vke/Upgrading-an-add-on). |
||Add\-on status |* If the cluster has nodes, its managed or unmanaged add\-ons are abnormal.<br><br>* If the cluster has no available nodes, unmanaged add\-ons are abnormal. |Cluster upgrades are not allowed when abnormal add\-ons exist in the cluster. |Restore abnormal add\-ons first. For details, see [Add-on FAQs](https://docs.byteplus.com/en/docs/vke/Add-on-FAQs). |
||Cluster CLB instance status |Classic Load Balancer (CLB) instances associated with the cluster are abnormal. |An abnormal CLB instance association with the cluster can cause the cluster to become unavailable, resulting in a cluster upgrade failure. |Restore the CLB instances associated with the cluster in the [CLB console](https://console.byteplus.com/clb). |
||Resource usage of control plane components |The resource usage of control plane components is too high. |Errors may occur during cluster upgrade and therefore affect your applications. |[Submit a ticket](https://console.byteplus.com/workorder/create) to perform scale\-out or wait until the resource usage returns to a normal level before upgrading the cluster. |
||Upgrade blocking for deprecated add\-ons |The upgrade is blocked because the system detects add\-ons that are no longer supported starting from Kubernetes v1.36. |Add\-ons no longer supported by the target Kubernetes version are installed in the cluster. A direct upgrade may cause related features or subsequent security fixes to become unavailable. |Before upgrading the control\-plane Kubernetes version, migrate to the recommended alternative capabilities, or delete or replace the relevant add\-ons. To continue using the add\-ons, [submit a ticket](https://console.byteplus.com/workorder/create) to confirm compatibility and risks.<br><br>For example, starting from Kubernetes v1.36, the ingress\-nginx add\-on is no longer supported. For migration solutions, see the [product announcement](https://docs.byteplus.com/en/docs/vke/Product_announcement_NGINX_Ingress_EOM). |
|Cluster configurations |Special cluster maintenance status |The cluster is in a special maintenance state, and the debug mode is enabled. |Verify whether any special operation and maintenance actions have been performed. If the cluster is still in that special state, the cluster upgrade may fail. |[Submit a ticket](https://console.byteplus.com/workorder/create) to cancel any special cluster state. |
||Node pool autoscaling |Autoscaling is enabled for the node pool. |During a cluster upgrade, autoscaling becomes temporarily unavailable. You need to disable autoscaling before upgrading the cluster. |Disable autoscaling for all node pools of the cluster. For details, see [Modifying node pool settings](https://docs.byteplus.com/en/docs/vke/Managing-NodePools#.57yW6L6R6IqC54K55rGg). |
||kubelet version |The kubelet version does not match the cluster version. |If the kubelet version on a node is inconsistent with the cluster version, upgrading the control plane may cause node issues. |Make sure that the kubelet version on nodes matches the cluster version before upgrading the control plane. For details, see [Upgrade nodes](https://docs.byteplus.com/en/docs/vke/Upgrading-a-cluster#.6IqC54K55Y2H57qn). |
||kubelet configuration parameters |Deprecated parameters are included in node pool configurations. |Invalid kubelet parameter configuration may cause newly created nodes to become unavailable after a cluster upgrade. |Remove deprecated parameters and modify your kubelet configurations. For details, see [Configuring kubelet parameters](https://docs.byteplus.com/en/docs/vke/Configuring-kubelet-parameters-for-a-NodePool). |
||Node pool configuration parameters |Node pools that use veLinux 2.0 or Ubuntu 22.04 use cgroup v1 for node initialization in Kubernetes versions earlier than v1.30. |New nodes in node pools that use veLinux 2.0 or Ubuntu 22.04 are initialized with cgroup v2 when they are scaled out in Kubernetes v1.30 or later, which may cause workloads on the new nodes to become unavailable. |If you want new nodes running veLinux 2.0 or Ubuntu 22.04 to continue using cgroup v1 for node initialization, [submit a ticket](https://console.byteplus.com/workorder/create). |
||Node cgroup version |The node cgroup version check did not pass. |Kubernetes v1.36 does not support cgroup v1 nodes. Upgrading the control plane directly may cause node or service anomalies. |Before performing the control\-plane upgrade, migrate the matching nodes to cgroup v2 and confirm that kubelet metrics for all non\-VCI nodes are accessible. For the current node migration solutions supported by VKE, see [FAQ](https://docs.byteplus.com/en/docs/vke/How-are-data-plane-nodes-upgraded). If you have a different solution, [submit a ticket](https://console.byteplus.com/workorder/create) for confirmation. |
||Node pool and node configuration compatibility |The node or node pool configurations are incompatible with the target Kubernetes version. |Incompatibility with the target Kubernetes version has been detected in cluster node or node pool configurations. Upgrading the control plan directly may cause existing nodes, subsequently provisioned nodes, or node upgrades to become unavailable. |Before upgrading the control plane, modify the configurations of matching nodes or node pools. To retain the existing configurations, [submit a ticket](https://console.byteplus.com/workorder/create) to confirm compatibility and risks. |

## Node checks


|**Category** |**Check item** |Exception detected |**Impact description** |**Fix suggestions** |
|---|---|---|---|---|
|Node health |Node status |The current node is abnormal. |Node status is abnormal. Upgrades are not allowed. |Restore the node to the **Running** status and try again. You can follow the on\-screen prompts to restore the node. |
|Node upgrade |Node\-level Kubernetes version |The current node version cannot be upgraded. |The Kubernetes version of the node did not pass validation. Upgrades are not permitted. |The Kubernetes version of the current node must be less than the target version of the upgrade. |
||containerd version |containerd version verification failed. |The containerd version on the node failed verification, preventing upgrade. |The containerd version on the current node must be less than the target containerd version of the upgrade. |
||Operating system |The operating system (OS) of the current node is not supported for a cluster upgrade. |A failed node OS check prevents a cluster upgrade. |Make sure that the node OS is Debian, Ubuntu, Devuan, veLinux, CentOS, Fedora, or RHEL. If your node OS is not one of them, [submit a ticket](https://console.byteplus.com/workorder/create). |
||Kernel parameters |Kernel parameter verification failed. |A failed kernel parameter check prevents cluster upgrades. |Disable the kernel swap parameter for the node. You can run the `swapoff -a` command to disable it. |
||Mount points checks |Inaccessible mount points are found on the node. |File read/write operations are affected during node upgrade. Upgrades are not permitted. |Fix the permissions of all mount points on the node so that they can be accessed normally. |
||Key directory permissions |The `/upgrade` directory does not support read or write operations. |File read/write operations are affected during node upgrade. Upgrades are not permitted. |Fix the permissions of the `/upgrade` directory to enable read and write access. |
||Memory usage |Memory usage exceeded the threshold of 90%. |The issue affects distribution of node upgrade tasks and backup of data, preventing upgrades. |Reduce node memory usage below 90%. You can evict some Pod workloads or upgrade the node during an off\-peak period. |
||Available disk space of key directories |The available space of the `/tmp` directory is insufficient. |The issue affects distribution of node upgrade tasks and backup of data, preventing upgrades. |Clean up files in the `/tmp` directory on the node to ensure that its available space is greater than 500 MiB. |
||Package dependencies |Required package dependencies are not installed. |The cluster may not provide basic functionality as expected, and therefore upgrades are not allowed. |Use the `yum` or `apt` command to check whether package dependencies such as socat, ebtables\-nft, and conntrack are properly installed, and resolve any issues based on the check results. |
||Basic services |Basic node services are abnormal. |Anomalies in the basic services on nodes can cause failures of essential cluster features. Therefore, upgrades are not permitted. |Check whether systemd, journald, chronyd, kubelet, Containerd, yum/apt\-get, and other basic services are functioning properly. If not, fix any issues. |
||DNS resolution |DNS resolution failed for the node. |The current node DNS configuration cannot properly resolve TOS addresses. Upgrades are not permitted. |Check the node DNS configuration to ensure that the host can properly resolve the TOS address: `https://<bucket_name>.<tos_endpoint>`.<br><br><div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div><br><br><br><br>* <div data-tips="true" data-tips-type="default"><code><bucket_name></code>: Bucket name.</div><br><br><br>* <div data-tips="true" data-tips-type="default"><code><tos_endpoint></code>:</div><br><br><br><br><div data-tips="true" data-tips-type="default">The TOS endpoint that allows external access. For details, see <a href="https://docs.byteplus.com/en/docs/tos/docs-region-and-endpoint">Regions and endpoints</a>.</div><br><br><br><div data-tips="true" data-tips-type="default">The following is an example of a TOS endpoint: <code>https://vke-sh.tos-cn-shanghai.ivolces.com</code>.</div><br> |
||TOS connectivity |The node cannot connect to TOS. |The node upgrade package cannot be properly downloaded. Therefore, upgrades are not allowed. |Check the [security group](https://docs.byteplus.com/en/docs/vke/Security-group-settings) for the node and allow access to the target TOS address: `https://<bucket_name>.<tos_endpoint>`. |
||InPlacePodVerticalScaling feature |The cluster has the InPlacePodVerticalscaling feature enabled. The current upgrade is blocked to prevent conflicts with the node upgrade process.<br><br> |When the cluster has the InPlacePodVerticalscaling feature enabled, upgrades are forcibly blocked to prevent conflicts with the node upgrade process.<br><br><div data-tips="true" data-tips-type="default" data-tips-is-title="true">tip</div><br><br><br><div data-tips="true" data-tips-type="default">This occurs only if Kubernetes is upgraded from v1.30 to v1.32.</div><br> |If you do not want the upgrade to be blocked, use node rotation. For example, provision new nodes, migrate workloads without recreating Pods by leveraging the InPlacePodVerticalScaling feature, then scale in the nodes (namely, replacing "in\-place modification" with "rolling replacement"). If you have any questions, [submit a ticket](https://console.byteplus.com/workorder/create) to contact technical support. |
|Node loads |Allocatable node resources |The allocatable CPU or memory resources of the node are insufficient. |Insufficient schedulable resources on a node (CPU < 100 millicores or memory < 200 MiB) will cause the node upgrade to fail. |Clean up unnecessary or abnormal workloads to free up node request resources, ensuring that pods for upgrades are scheduled normally. For details, see [Deleting pods](https://docs.byteplus.com/en/docs/vke/Managing-pods). |
||Maximum pods per node |The maximum pod limit configured for the node has been reached. |No more pods can be created. This causes failures in deploying pods for the upgrade. |Delete some pods on the node to ensure that the pod for the node upgrade can be properly scheduled. For details, see [Deleting pods](https://docs.byteplus.com/en/docs/vke/Managing-pods). |
||Available node resources |The available CPU or memory resources on the node are insufficient. |Insufficient resources on a node (CPU < 100 millicores or memory < 200 MiB) will cause the node upgrade to fail. |Clean up pods that consume too many resources on the node to release resources so that pods for upgrades can run normally. |
