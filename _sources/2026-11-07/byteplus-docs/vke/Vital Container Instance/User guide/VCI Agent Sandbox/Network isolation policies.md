This topic describes the network isolation policies of VCI Agent Sandbox, including the related mechanisms, limits, two creation methods, and the steps for each scenario.

## Background information

Network isolation is a core component of the Sandbox security model. It uses the NetworkPolicy capability to control inbound (Ingress) and outbound (Egress) traffic for Sandbox instances at the Pod network layer. This mechanism ensures that only authorized add\-ons can access Sandbox and restricts the outbound access scope of Sandbox.

## Limits

* NetworkPolicy is not yet supported when regular nodes (ECS nodes) and virtual nodes are deployed together. Specifically:

   * When you set `namespaceSelector` or `podSelector` allowlist rules in NetworkPolicy, the policy does not apply to Pods on ECS nodes.

   * Requests from and to Pods on ECS nodes are still blocked. To allow such traffic, explicitly declare the Pod IP addresses by using ipBlock.

* If you enable the E2B capability when you install the [agent-sandbox](https://docs.byteplus.com/en/docs/vke/agent-sandbox) add\-on in VKE, we recommend deploying the add\-on on VCI.

* For Pods that require network isolation, in addition to setting NetworkPolicy, you need to add `vci.volcengine.com/network-policy-enabled: "true"` to the Pod annotations to enable network isolation. Otherwise, the isolation policy does not take effect.

## Usage methods

You can establish network isolation policies in two ways: using SandboxTemplate Managed and creating NetworkPolicy directly. This section describes the two network isolation methods in detail.

**SandboxTemplate Managed (recommended)**

SandboxTemplate (API version: `extensions.agents.x-k8s.io/v1alpha1`) is a resource that defines the template of Sandbox instances. When the Sandbox Controller creates sandboxes in batches or dynamically based on a SandboxTemplate, it automatically generates the corresponding native Kubernetes NetworkPolicy resources behind the scenes.

In a SandboxTemplate, use the `networkPolicyManagement` field and the `networkPolicy` field to control the NetworkPolicy management mode.

|**Parameter** |Required |**Description** |
|---|---|---|
|networkPolicyManagement |Yes |NetworkPolicy management mode. Valid values:<br><br><br>* **Managed**: The controller automatically creates and updates NetworkPolicy.<br><br>* **Unmanaged**: The controller does not create or manage NetworkPolicy. An external system takes over NetworkPolicy creation and management. |
|networkPolicy |Optional in this scenario |It defines inbound and outbound rules and fully reuses the semantics and structure of standard Kubernetes NetworkPolicy. The mechanism controls traffic in the following two directions:<br><br><br>* `spec.networkPolicy.ingress`: The value is of the Object type and specifies inbound rules. It restricts which external resources can connect to and access sandboxes. For example, only specific agent routing Pods can access specific ports of a sandbox.<br><br>* `spec.networkPolicy.egress`: The value is of the Object type and specifies outbound rules. It restricts which external networks the code in a sandbox can access. You typically use egress rules to block sandboxes from accessing other services in a cluster or to create an allowlist for public network access.<br><br><br>> **warning**<br><br><br><br>* > If you enable `networkPolicyManagement` but do not set `networkPolicy`, SandboxController automatically generates a default NetworkPolicy. This default policy allows only Ingress traffic from `sandbox-router` and `data-plane` and does not restrict Egress traffic. We recommend against using this method in production.<br><br><br>* > The NetworkPolicy generated by the Sandbox Controller covers both Ingress and Egress. If you set rules for only one direction, the other direction is denied by default. To allow all traffic in the corresponding direction (Ingress/Egress), set its value to `- {}`.<br><br><br>* > Do not manually modify the automatically generated underlying policies, because the reconciliation mechanism of the controller overwrites and resets them.<br> |

**Creating NetworkPolicy directly**

A Sandbox is still a VCI Pod, and NetworkPolicy for VCI Pods still applies to Agent Sandbox. For more information, see [Using NetworkPolicy to implement network access control for VCI Pods](https://docs.byteplus.com/en/docs/vke/Using_a_NetworkPolicy_to_implement_network_access_control_for_VCI_Pods?lang=en).

The following table compares the two methods.

|**Comparison dimension** |**SandboxTemplate Managed (recommended)**  |**Creating NetworkPolicy directly** |
|---|---|---|
|Policy lifecycle |Synchronized automatically with the SandboxTemplate. |You need to maintain NetworkPolicies manually, which can easily lead to orphaned policies. |
|podSelector maintenance |The Sandbox Controller manages them automatically, so you do not need to manage internal labels. |This method requires manual Sandbox label matching, which is prone to errors. |
|Default ingress rules |Automatically generates entry points for `sandbox-router` and `data-plane`. |You need to manually add them one by one. This process is prone to omissions. |
|Risk of being overwritten |None. The controller uses the SandboxTemplate as the source of truth. |In Managed mode, manual changes can be overwritten by the controller. |
|Applicable scenarios |This is the standard way to claim a Sandbox through SandboxClaim.<br><br> |* Create Sandboxes directly without relying on SandboxTemplate.<br><br>* Maintain and manage workloads at the cluster level, regardless of workload type. |

## Prerequisites

* A cluster required by the VCI service has been created. For details, see [Using VCI in VPC-CNI clusters](https://docs.byteplus.com/en/docs/vke/Using-VCI-in-Vital-Kubernetes-Engine) and [Using VCI in Flannel clusters](https://docs.byteplus.com/en/docs/vke/Using-VCI-in-Flannel-cluster).

* The vci\-virtual\-kubelet add\-on has been installed in the cluster. For detailed instructions, see [vci-virtual-kubelet](https://docs.byteplus.com/en/docs/vke/vci-virtual-kubelet-add-on).

* The agent\-sandbox add\-on has been installed in the cluster. For more information, see [agent-sandbox](https://docs.byteplus.com/en/docs/vke/agent-sandbox).

## Procedure

> **tip**

> The following steps describe how to create a custom NetworkPolicy through SandboxTemplate Managed.

### Step 1: (Optional) Create a workload deployed on VCI

Create a VCI Pod to test access connectivity. If a VCI Pod is already available, skip this step.

1. Use kubectl to connect to the target VCI cluster. For details, see [Connecting to a cluster](https://docs.byteplus.com/en/docs/vke/Connecting-to-a-cluster).

2. Create the YAML file of a workload. The code of the sample file `vci-deployment-demo.yaml` is as follows:

   ```yaml
   apiVersion: apps/v1
   kind: Deployment
   metadata:
     name: vci-deployment-demo # The Deployment name.
     namespace: default # The namespace where the Deployment resides.
   spec:
     replicas: 1 # Number of replicas (Pods) managed by the Deployment.
     selector:
       matchLabels:
         app: vci-deployment-demo
     template:
       metadata:
         annotations:
           vke.volcengine.com/burst-to-vci: enforce  # Force the use of VCI.
           vci.vke.volcengine.com/preferred-instance-family: vci.u1 # Specify the instance family of VCI.
         labels:
           app: vci-deployment-demo
       spec:
         containers:
         - name: vci-demo # The container name.
           image: doc-cn-beijing.cr.volces.com/vke/nginx-demo:v1.0 # The address and version of the container image. Replace the value with your actual information. If you need to use a public image, make sure that the cluster can access the public network.
           ports:
           - containerPort: 80 # The exposed port number of the container.
           resources:
             requests:  # Specify the container vCPU and memory.
               cpu: "500m"      
               memory: "1024Mi"
             limits:
               cpu: "1"      
               memory: "2048Mi"
   ```

3. Run the following command to create the workload.

   ```bash
   kubectl apply -f vci-deployment-demo.yaml
   ```

4. Run the following command to obtain the Pod's IP address and name for later connectivity tests.

   ```bash
   # Replace vci-deployment-demo with the actual Deployment name.
   kubectl get pods -o wide |grep ^vci-deployment-demo
   ```

   The expected output is as follows:

   ```bash
   vci-deployment-demo-****   1/1   Running   0   2d3h   10.xx.xx.xx   node-1
   ```

### Step 2: create NetworkPolicy

This section provides three scenarios for using NetworkPolicy. They cover the most common combinations of inbound and outbound allowlists. Choose the one that fits your business needs:

* **Scenario 1**: Allow inbound access by application label. This scenario applies when the caller has a stable label.

* **Scenario 2**: Allow inbound access by source IP address. This scenario applies when the caller cannot be reliably selected by label but has a known and stable IP address.

* **Scenario 3**: Allow outbound access by application label or IP address. This scenario applies when you need to restrict the external access scope of sandboxes.

**Scenario 1**

In this scenario, the inbound rules allow only Pods with specific labels to access the Sandbox. All other sources are denied.

1. Create a SandboxTemplate, and enable NetworkPolicy in the annotations of podTemplate via `vci.volcengine.com/network-policy-enabled`. The content of the sample SandboxTemplate YAML file `sandbox-template-demo1.yaml` is as follows:

   ```YAML
   apiVersion: extensions.agents.x-k8s.io/v1alpha1
   kind: SandboxTemplate
   metadata:
     name: sandbox-template-demo1  # SandboxTemplate name.
     namespace: default  # The namespace of the SandboxTemplate.
   spec:
     networkPolicyManagement: Managed  # NetworkPolicy management mode. Valid values: Managed (the controller manages the creation and update of NetworkPolicy) and Unmanaged (an external system takes over NetworkPolicy management).
     networkPolicy:
       ingress:
         - from: 
             - podSelector:   # Allow access from the VCI Pod created in Step 1 via the specified label.
                 matchLabels:
                   app: vci-deployment-demo
       egress:
         - {}
     podTemplate:
       metadata:
         annotations:
           vke.volcengine.com/burst-to-vci: enforce  # Forced scheduling to VCI.
           vci.volcengine.com/network-policy-enabled: "true"  # Whether to enable the VCI NetworkPolicy feature. Values: true (enabled) and false (disabled).
         labels:
           app: sandbox-demo
       spec:
         containers:
         - image: doc-cn-beijing.cr.volces.com/vke/nginx-demo:v1.0 # The address and version of the container image. Replace the value with your actual information. If you need to use a public image, make sure that the cluster can access the public network.
           imagePullPolicy: IfNotPresent
           name: sandbox
           ports:
           - containerPort: 80
         dnsPolicy: ClusterFirst
         restartPolicy: Always
   ```

2. Execute the following command to create the SandboxTemplate.

   ```Bash
   kubectl create -f sandbox-template-demo1.yaml
   ```

3. Create a YAML file for the SandboxClaim. The content of the sample YAML file `sandbox-claim-demo1.yaml` is as follows:

   ```YAML
   apiVersion: extensions.agents.x-k8s.io/v1alpha1
   kind: SandboxClaim
   metadata:
     name: sandbox-claim-demo1        # SandboxClaim name.
     namespace: default               # Namespace of the SandboxClaim.
   spec:
     sandboxTemplateRef:
       name: sandbox-template-demo1   # The name of the SandboxTemplate used to claim sandboxes.
   ```

4. Execute the following command to create SandboxClaim.

   ```Bash
   kubectl apply -f sandbox-claim-demo1.yaml
   ```

5. Run the following command to obtain the IP address of the Sandbox Pod from `status.sandbox.podIPs` of the SandboxClaim resource.

   ```Bash
   # Replace sandbox-claim-demo1 with the actual SandboxClaim name.
   kubectl get sandboxclaim sandbox-claim-demo1 -oyaml
   ```

6. Access the Sandbox Pod from the allowed Pod to verify connectivity.

   ```Bash
   # Replace vci-deployment-demo-**** with the actual Pod name.
   kubectl exec -it vci-deployment-demo-**** -- /bin/sh
   
   # Replace xx.xx.xx.xx with the IP address of the Sandbox Pod obtained in the previous step.
   curl --connect-timeout 5 --max-time 10 xx.xx.xx.xx:80 
   ```

   The expected output is as follows:

   ```Bash
   <!DOCTYPE html>
   <html>
   <head>
   <title>Welcome to nginx!</title>
   <style>
   html { color-scheme: light dark; }
   body { width: 35em; margin: 0 auto;
   font-family: Tahoma, Verdana, Arial, sans-serif; }
   </style>
   </head>
   <body>
   <h1>Welcome to nginx!</h1>
   <p>If you see this page, the nginx web server is successfully installed and
   working. Further configuration is required.</p>
   
   <p>For online documentation and support please refer to
   <a href="http://nginx.org/">nginx.org</a>.<br/>
   Commercial support is available at
   <a href="http://nginx.com/">nginx.com</a>.</p>
   
   <p><em>Thank you for using nginx.</em></p>
   </body>
   </html>
   ```

7. Create a sample Pod that is not allowed and send an inbound request to the target Sandbox.

   ```Bash
   kubectl run -it --rm --image=doc-cn-beijing.cr.volces.com/vke/nginx-demo:v1.0  nginx-tmp -- /bin/sh
   
   # Replace xx.xx.xx.xx with the IP address of the Sandbox Pod obtained above.
   curl --connect-timeout 5 --max-time 10 xx.xx.xx.xx:80
   ```

   The expected output is as follows:

   ```Bash
   curl: (28) Connection timed out after 5000 milliseconds
   ```

**Scenario 2**

If the caller cannot be reliably selected by label but has a known IP address, use `ipBlock` instead to specify a single IP address or CIDR block to allow inbound access. To exclude specific IP addresses in a subnet, add the `except` field to `ipBlock`. For more information, see the [Kubernetes documentation](https://kubernetes.io/zh-cn/docs/reference/kubernetes-api/policy-resources/network-policy-v1/). In this scenario, the IP address of the test Pod created in Step 1 is the only allowed source.

1. Create a SandboxTemplate, and enable NetworkPolicy in the annotations of podTemplate via `vci.volcengine.com/network-policy-enabled`. The content of the sample SandboxTemplate YAML file `sandbox-template-demo2.yaml` is as follows:

   ```YAML

   kind: SandboxTemplate
   metadata:
     name: sandbox-template-demo2  # SandboxTemplate name.
     namespace: default  # The namespace of the SandboxTemplate.
   spec:
     networkPolicyManagement: Managed  # NetworkPolicy management mode. Valid values: Managed (the controller manages the creation and update of NetworkPolicy) and Unmanaged (an external system takes over NetworkPolicy management).
     networkPolicy:
       ingress:
         - from: 
             - ipBlock:   # Explicitly declare the VCI Pod IP created in Step 1 through ipBlock.
                 cidr: xx.xx.xx.xx/32
       egress:
         - {}
     podTemplate:
       metadata:
         annotations:
           vke.volcengine.com/burst-to-vci: enforce  # Forced scheduling to VCI.
           vci.volcengine.com/network-policy-enabled: "true"  # Whether to enable the VCI NetworkPolicy feature. Values: true (enabled) and false (disabled).
         labels:
           app: sandbox-demo
       spec:
         containers:
         - image: doc-cn-beijing.cr.volces.com/vke/nginx-demo:v1.0 # The address and version of the container image. Replace the value with your actual information. If you need to use a public image, make sure that the cluster can access the public network.
           imagePullPolicy: IfNotPresent
           name: sandbox
           ports:
           - containerPort: 80
         dnsPolicy: ClusterFirst
         restartPolicy: Always
   ```

**Scenario 3**

Unlike the previous two scenarios that focus on inbound traffic, this scenario focuses on outbound traffic. In the following example, `ingress` allows all traffic, and `egress` restricts the external access scope of Sandbox.

1. Create a SandboxTemplate, and enable NetworkPolicy in the annotations of podTemplate via `vci.volcengine.com/network-policy-enabled`. The content of the sample SandboxTemplate YAML file `sandbox-template-demo3.yaml` is as follows:

   ```YAML
   apiVersion: extensions.agents.x-k8s.io/v1alpha1
   kind: SandboxTemplate
   metadata:
     name: sandbox-template-demo3  # SandboxTemplate name.
     namespace: default  # The namespace of the SandboxTemplate.
   spec:
     networkPolicyManagement: Managed  # NetworkPolicy management mode. Valid values: Managed (the controller manages the creation and update of NetworkPolicy) and Unmanaged (an external system takes over NetworkPolicy management).
     networkPolicy:
       ingress:
         - {}
       egress:
         - to: 
             - podSelector:
                 matchLabels:
                   app: nginx   # Allow outbound addresses based on label matching.
             - ipBlock:
                 cidr: xx.xx.xx.xx/32  # Allow outbound addresses by IP block.
     podTemplate:
       metadata:
         annotations:
           vke.volcengine.com/burst-to-vci: enforce  # Forced scheduling to VCI.
           vci.volcengine.com/network-policy-enabled: "true"  # Whether to enable the VCI NetworkPolicy feature. Values: true (enabled) and false (disabled).
         labels:
           app: sandbox-demo
       spec:
         containers:
         - image: doc-cn-beijing.cr.volces.com/vke/nginx-demo:v1.0 # The address and version of the container image. Replace the value with your actual information. If you need to use a public image, make sure that the cluster can access the public network.
           imagePullPolicy: IfNotPresent
           name: sandbox
           ports:
           - containerPort: 80
         dnsPolicy: ClusterFirst
         restartPolicy: Always
   ```

2. Execute the following command to create the SandboxTemplate.

