## Background

<span id=".5peg5Li76ZSu6KGo"></span>
### Tables without primary keys

Creating tables without primary keys in a MySQL database introduces significant risks to a high\-availability architecture:


* **Binlog synchronization failure** When full table updates or range delete operations occur, each row\-based binlog event requires a full table scan to locate data during replay on the secondary instance due to the lack of a clustered index. Tests show that these operations on tables with millions of rows cause the primary\-secondary synchronized latency to increase exponentially.

* **Storage engine feature conflict** The clustered index feature of the InnoDB engine requires a unique row identifier. When a table lacks an explicit primary key:

   * The implicit `ROW_ID` automatically generated by the engine lacks index visibility.

   * Secondary index leaf nodes are forced to point to the implicit `ROW_ID`, making the data location path invisible and increasing maintenance costs.

   * Each DML operation effectively becomes a full table scan.

* **Avalanche effect on high\-availability links**: Latency from tables without primary keys is self\-worsening:

   * The primary database continuously generates new binlog events.

   * The replica database cannot consume the event queue in time due to full table scans.

   * This eventually interrupts synchronization.

   * This creates a risk of data inconsistency during failover.


<span id=".6Kej5Yaz5Yqe5rOV"></span>
### Solutions


* Reactive approach: Rebuild the standby database

   After a table without a primary key has been created, a reactive solution is to handle the issue without changing the table structure. This involves setting up primary\-replica latency alerts, manually checking if the table without a primary key is the cause, and rebuilding the replica database through a work order. This approach creates an additional manual workload and is unsustainable.

* Proactive approach: Use hidden primary keys

   **MySQL Community Edition** 8.0.30 introduces the [Generated Invisible Primary Key (GIPK)](https://dev.mysql.com/doc/refman/8.0/en/create-table-gipks.html) feature. It identifies tables without primary keys in `CREATE TABLE` statements and adds a user\-invisible primary key index to the table by using MySQL's "[invisible column](https://dev.mysql.com/doc/refman/8.4/en/invisible-columns.html)" attribute. This approach solves the problem of tables without primary keys without affecting user operations, ensuring that newly created tables always have a primary key.


<span id=".5LqR5pWw5o2u5bqTLW15c3FsLeeJiC1ncGlrLeiDveWKm-eugOS7iw=="></span>
### Introduction to the GIPK capabilities of RDS for MySQL

RDS for MySQL optimizes the community's invisible primary key based on the community version 8.0 and implements a GIPK\-like function in MySQL 5.7 by using a unique index. The following compares the invisible primary key capabilities that RDS for MySQL provides for MySQL 8.0, MySQL 8.4, and MySQL 5.7.


|GIPK attribute |MySQL 8.0/MySQL 8.4 |MySQL 5.7 |
|---|---|---|
|KEY type |Primary key index (Primary Key)<br><br>bigint(20), auto_increment |Unique Index<br><br>bigint(20), auto_increment |
|Primary key column name |`my_row_id` |`byte_rds_ai_uk_row_id` |
|Conditions for creating a GIPK |The CREATE TABLE statement has no primary key |CREATE TABLE statement without a primary key or unique key |
|Whether to automatically drop the primary key column after a user adds a primary key. |Yes |Yes |
|Whether a user can select GIPK with a ``SELECT *`` query |No |No |
|Control parameter (session) |sql_generate_invisible_primary_key |loose_sql_generate_invisible_primary_key |
|Show GIPK Parameter |show_gipk_in_create_table_and_information_schema |loose_show_gipk_in_create_table_and_information_schema |

## Usage

<span id=".5omT5byA6ZqQ6JeP5Li76ZSu"></span>
### Enable invisible primary key

Modify the instance parameter to `ON`.


* MySQL 8.0、MySQL 8.4：`sql_generate_invisible_primary_key`

* MySQL 5.7：`loose_sql_generate_invisible_primary_key`


<div data-tips="true" data-tips-type="tip" data-tips-is-title="true">tip</div>



* <div data-tips="true" data-tips-type="tip">The two parameters above are not open for modification. If you need to modify them, <a href="https://console.byteplus.com/workorder/create/">submit a ticket</a> to contact technical support.</div>


* <div data-tips="true" data-tips-type="tip">For instances with kernel minor version 20241215 or later, the value of these two parameters is <code>ON</code> by default.</div>

### Viewing the invisible primary key

<span id="mysql-5-7"></span>
#### MySQL 5.7

After enabling the `loose_show_gipk_in_create_table_and_information_schema` parameter at the session level, you can see the invisible primary key `byte_rds_ai_uk_row_id` in `show create table`.

```sql
mysql> set loose_show_gipk_in_create_table_and_information_schema=on;

mysql> show variables like '%gipk%';
+--------------------------------------------------------+-------+
| Variable_name                                          | Value |
+--------------------------------------------------------+-------+
| loose_show_gipk_in_create_table_and_information_schema | ON    |
+--------------------------------------------------------+-------+
1 row in set (0.01 sec)

mysql > show create table tt1;
+-------+----------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| Table | Create Table                                                                                                                                                               |
+-------+----------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| tt1   | CREATE TABLE tt1 (
       `byte_rds_ai_uk_row_id` bigint unsigned NOT NULL AUTO_INCREMENT COMMENT 'BYTE_RDS_INVISIBLE',
       `f1` int DEFAULT NULL,
       `f2` int DEFAULT NULL,
      UNIQUE KEY (`byte_rds_ai_uk_row_id`)
    ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb3 |
+-------+-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
1 row in set (0.01 sec)
```
