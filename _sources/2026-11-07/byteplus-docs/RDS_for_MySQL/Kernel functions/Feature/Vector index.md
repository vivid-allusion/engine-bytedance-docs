This topic describes the vector index feature of RDS for MySQL.

## Supported version

* MySQL 8.0, with a kernel minor version of MySQL 8.0.43_20251015 or later.

* MySQL 8.4, with a kernel minor version of MySQL 8.4.7_20260415 or later.

## Background

In recent years, the database field has shifted from strict exact\-match queries to a more ambiguous and context\-aware model. The core of this paradigm shift is vector search technology, which enables databases to understand and query data based on its semantics (its inherent meaning) rather than its literal representation.

After data is represented as vectors, the basic task of vector retrieval is to find the ***k\-nearest neighbors***  **(K\-Nearest Neighbor, KNN)**  for a given query vector. This requires calculating the distance between the query vector and all other vectors in the dataset to identify the k most similar entries. The SQL representation is as follows.

```SQL
SELECT id
FROM   tv
ORDER  BY L2_distance(vector, To_vector('[1,2,3,4]'))
LIMIT  10; -- top K, K=10
```

This process is conceptually simple but faces a problem known as the "Curse of dimensionality". The vector embeddings generated by models are typically high\-dimensional, often containing hundreds or even thousands of dimensions. As the number of dimensions increases, the volume of the vector space grows exponentially. In such a vast and sparse space, the concept of "proximity" becomes less meaningful, as nearly all points become equidistant from one another.

For large\-scale Online applications, performing a "brute\-force" KNN search is computationally infeasible. The time complexity of this Search is linear, O(N), where N is the number of vectors in the dataset. For datasets containing millions or billions of vectors, this method causes unacceptably high business Latency. The "Curse of dimensionality" is a core Problem that has driven innovation and diversification in vector Search algorithms across academia and industry. Everyone is trying to answer the same problem:  **"How can we efficiently find the most similar vectors in a vast, sparse space while avoiding a brute\-force search?"**

To overcome the performance limitations of the "Curse of dimensionality", most modern vector search systems rely on **Approximate Nearest Neighbor (ANN)**  algorithms. The core principle of ANN is to sacrifice a small, often negligible, amount of accuracy for significant improvements in search speed and scalability. ANN algorithms do not guarantee finding the absolute nearest neighbor, but instead use heuristic methods and optimized data structures to find  **"good enough"**  matches in a very short time.

## Feature description

RDS for MySQL supports building and using ANN indexes to Search stored vectors by building vector indexes with the 'Hierarchical Navigable Small World', or [HNSW](https://en.wikipedia.org/wiki/Hierarchical_navigable_small_world), algorithm. This is an efficient ANN algorithm based on memory graphs.

### Syntax description

**CREATE TABLE**

Create a table with a vector column and a vector index using the CREATE TABLE syntax.

### Syntax

```SQL
CREATE TABLE table_name [IF NOT EXISTS] ( 
    [(create_definition,...)]
    vector_column_name VECTOR(N) NOT NULL,  
    VECTOR {INDEX | KEY} [index_name] (vector_column_name)
    [USING HNSW]
    [SECONDARY_ENGINE_ATTRIBUTE= {...}]
) ENGINE = InnoDB;
```

### Parameter description

   * Vector index keyword (Required): `VECTOR INDEX(column_name)` or `VECTOR KEY(column_name)`.

   * Algorithm type (Optional):

      * Method 1: Use `USING [ANN_ALGORITHM]` to specify an ANN algorithm, such as `HNSW`.

      * Method 2: Use the `algorithm` field of `SECONDARY_ENGINE_ATTRIBUTE` to specify the index.

   * Distance calculation method (Optional): `EUCLIDEAN`, `L2`, `COSINE`.

   * Algorithm parameters (Optional): Use `SECONDARY_ENGINE_ATTRIBUTE` to adjust parameters for the corresponding ANN algorithm, such as:

      * HNSW: `M` value; `ef_construction` value.

### Sample

* Example 1: Using the default system algorithm and parameters.

   ```SQL
   CREATE TABLE tv (
    pk INT,
    embedding VECTOR(4) NOT NULL,
    VECTOR INDEX (embedding) 
   ) ENGINE=InnoDB;
   ```

* Example 2: Specifying the index algorithm and using the default algorithm parameters.

   ```SQL
   CREATE TABLE tv (
    pk INT,
    embedding VECTOR(4) NOT NULL,
    VECTOR INDEX (embedding) USING HNSW  
   ) ENGINE=InnoDB;
   ```

* Example 3: Specifying the index algorithm and parameters.

   ```SQL
   CREATE TABLE tv (
    pk INT,
    embedding VECTOR(4) NOT NULL,
    VECTOR INDEX (embedding) SECONDARY_ENGINE_ATTRIBUTE='{"algorithm": "hnsw", "M": "16", "distance": "cosine"}'
   ) ENGINE=InnoDB;
   ```

**Approximate Nearest Neighbor (ANN) search**

RDS for MySQL provides vector distance functions that you can use to perform **Approximate Nearest Neighbor** (ANN) and **K\-Nearest Neighbor** (KNN) vector similarity searches on an instance. When you run a query, the system compares vectors with the vectors in your dataset by using a vector index. The distance function uses similarity metrics, such as cosine, to calculate the distance between vectors. Vectors with the shortest distance have the highest similarity and are returned in the search results.

To perform an ANN search, use the distance function dist_expr in the SELECT and ORDER BY clauses. You must use the LIMIT clause in an ANN search. You can also obtain the distance value by including the distance function dist_expr in the SELECT list.

### Syntax

```SQL
SELECT {col_name} 
        FROM table_name [FORCE INDEX (vector_column_name)] 
        [WHERE where_condition]
ORDER BY { dist_expr }
LIMIT N;
```

### Precautions

* `dist_expr`: the distance function. For HNSW vector indexes, two distance metrics are supported: `L2_DISTANCE`/`EUCLIDEAN_DISTANCE` (Euclidean distance) and `COSINE_DISTANCE` (cosine distance).

* Use `ORDER BY ...` When you use `LIMIT` and sort by a distance function, the system attempts to recall approximate results through the ANN vector index.

* A user can use `FORCE INDEX` to specify a vector index. If no index is specified, the optimizer automatically determines whether to use an index (full table scan vs. ANN)。

* If an ANN query and the index use different distance metrics, MySQL prioritizes the distance metric used when the index was created.

### Distance function `dist_expr` example

* Example 1: Comparing the query vector [1,2,3,4] with the vectors in the vector column by using the Euclidean distance.

```SQL
 L2_distance(vector, To_vector('[1,2,3,4]'))
```

* Example 2: Comparing the query vector [1,2,3,4] with the normalized vectors in the vector column by using the Euclidean distance.

```SQL
 L2_distance(vector_normalize(vector), To_vector('[1,2,3,4]'))
```

### ANN query example

* Example 1: Searching for the primary key IDs of the 10 vectors in the tv table that are closest to the vector [1, 2, 3, 4].

```SQL
SELECT id
FROM tv
ORDER  BY L2_distance(vector, To_vector('[1,2,3,4]'))
LIMIT  10; 
```

* Example 2: Using FORCE INDEX to specify a vector index.

```SQL
SELECT id
FROM   tv FORCE INDEX(vector)
ORDER  BY  L2_distance(vector, To_vector('[1,2,3,4]')) 
LIMIT  10; 
```

* Example 3: Combining the dist_expr distance function with a WHERE condition that uses scalar predicates to filter the query results for post\-filtering.

```SQL
SELECT id
FROM   tv FORCE INDEX(vector)
WHERE  id > 1000
ORDER  BY  L2_distance(vector, To_vector('[1,2,3,4]')) 
LIMIT  10; 
```

### Vector Index DDL Behavior

A vector index consists of two parts: index metadata on the primary table, and a one\-to\-one corresponding InnoDB auxiliary table for persisting the HNSW graph structure. The following describes the restrictions and behavior of relevant DDL statements.

#### Precautions

* he auxiliary table is invisible to users by default and does not appear in `SHOW TABLES` or `INFORMATION_SCHEMA.TABLES`. To view it, filter records in `INFORMATION_SCHEMA.INNODB_TABLES` using the condition `name LIKE 'db/__bytevec%_hnsw_graph'`.

* When querying vector index information, the `index` argument in the `VECTOR_INDEX_INFO(db, table, index)` syntax specifies the **index name**, not the column name. `runtime_stats.graph_size` in the returned information indicates the count of nodes loaded in memory. Its value is 0 until the index is loaded upon query trigger, and it cannot be used in place of the row count.

* Recall results for approximate search depend on the graph structure. After index rebuilding, the return order may differ from that before rebuilding. This is a normal characteristic of the HNSW algorithm and does not indicate data loss. To verify data integrity, perform comparisons using full table scans with `IGNORE INDEX` specified.

**Create index**

|**DDL statement** |**Supported or not** |**Algorithm Used** |**Behavior description** |
|---|---|---|---|
|CREATE TABLE ... VECTOR INDEX (col) |Support |— |The vector index and its corresponding auxiliary table are created synchronously during table creation. |
|CREATE VECTOR INDEX ... ON tbl(col) |Support |INPLACE<br><br> |Enforce the use of the INPLACE algorithm. |
|ALTER TABLE ... ADD VECTOR INDEX |Support |INPLACE |The `INPLACE` algorithm is enforced. |
|ALTER TABLE ... ADD VECTOR INDEX, ALGORITHM=COPY |Not support |— |Returns an error message: `ERROR 1845 (0A000): ALGORITHM=COPY is not supported for this operation.` `Try ALGORITHM=INPLACE.`。 |
|ALTER TABLE ... ADD VECTOR INDEX, ALGORITHM=INSTANT |Not support |— |Return error message: `ERROR 1845: ALGORITHM=INSTANT is not supported for this operation.` `Try ALGORITHM=INPLACE.`。 |
|Add VECTOR Index in the Same Table Rebuild Statement |Not support |— |Return error message: `ERROR 1845: Adding a VECTOR index while rebuilding the table is not supported for this operation.` `Try separate ALTER TABLE statements.`。 |

**Table-rebuilding DDL**

> **tip**

> Performing regular column modifications (adding or dropping non\-vector columns) on tables with vector indexes is not subject to the restrictions below. The INPLACE or INSTANT algorithm can still be used normally with no additional syntax required.

The following statements trigger primary table rebuilding, which requires the HNSW graph to be rebuilt synchronously. The `COPY` algorithm is enforced during execution. After rebuilding completes, the auxiliary table is replaced with an entirely new table (both its table name and table_id change). The old auxiliary table is dropped within the same transaction.

|**DDL statement** |**Supported or not** |**Algorithm Used** |**Behavior description** |
|---|---|---|---|
|OPTIMIZE TABLE |Support |Force COPY |It returns `Table does not support optimize, doing recreate + analyze instead`. The COPY algorithm is enforced, and the HNSW graph is rebuilt together with the primary table. |
|ALTER TABLE ... FORCE |Support |Force COPY |It returns `Table does not support optimize, doing recreate + analyze instead`. The COPY algorithm is enforced, and the HNSW graph is rebuilt together with the primary table. |
|ALTER TABLE ... ENGINE=InnoDB |Support |Force COPY |It returns `Table does not support optimize, doing recreate + analyze instead`. The COPY algorithm is enforced, and the HNSW graph is rebuilt together with the primary table. |
|ALTER TABLE ... ADD COLUMN <VECTOR column\> |Support |Force COPY |Adding a vector column cannot be executed online. The server automatically uses the COPY algorithm, and ALGORITHM does not need to be specified explicitly. |
|The SQL statements above explicitly specify ALGORITHM=INPLACE or INSTANT |Not support |— |Returns an error message: `ERROR 1845: Rebuilding a VECTOR table is not supported for this operation.` `Try ALGORITHM=COPY.` No silent downgrade to the COPY algorithm occurs. |
|Rebuild with RENAME TO / Partition Changes / RENAME INDEX |Not support |— |The statement fails and returns the error message: `ERROR 1845: ...` `Try an ALTER without RENAME or partition changes.`。 |
|Engine Fallback from INPLACE to COPY |Not support |— |Returns an error message: `ERROR 1845: Implicit ALGORITHM=COPY is not supported for this operation.` `Try explicit ALGORITHM=COPY.` The algorithm will not switch implicitly. Retry after explicitly setting ALGORITHM=COPY.<br><br>> **tip**<br><br><br>> This scenario is triggered only after the engine enters the INPLACE execution phase and determines mid\-execution that online completion is not possible.<br> |

**Index and column modifications**

|**DDL statement** |**Supported or not** |**Algorithm Used** |**Behavior description** |
|---|---|---|---|
|DROP INDEX / ALTER TABLE ... DROP INDEX |Support |INPLACE |The auxiliary table is dropped within the same transaction, leaving no orphaned objects. |
|ALTER TABLE ... RENAME INDEX old TO new |Support |INPLACE |Only the index is renamed; the auxiliary table name stays unchanged, and HNSW graph rebuilding is not required. |
|RENAME INDEX and ADD VECTOR INDEX within the same statement |Not support |— |Return error message: `ERROR 1845: RENAME INDEX combined with ADD VECTOR INDEX is not supported ...` `Try separate ALTER TABLE statements.`。 |
|Drop and ADD the same VECTOR index in one statement |Not support |— |Return error message: `ERROR 1845: DROP and ADD of the same VECTOR index is not supported ...` `Try separate ALTER TABLE statements.`。 |
|Modification of vector column type |Support (COPY algorithm only)<br><br> |COPY |If the `COPY` algorithm is used, the following error is returned: `ERROR 1846: ALGORITHM=INPLACE is not supported.` `Reason: Cannot change column type INPLACE.` `Try ALGORITHM=COPY.`。 |
|Modification of Index SECONDARY_ENGINE_ATTRIBUTE |Condition Support<br><br> |INPLACE |Attribute values are persisted after normalization. Invalid values return errors directly during parameter validation. |

**Table-level operations**

|**DDL statement** |**Behavior description** |
|---|---|
|TRUNCATE TABLE |he primary table and auxiliary table are truncated synchronously, clearing all HNSW graph data. This operation executes atomically. If truncation of the auxiliary table fails, the entire transaction rolls back, and auxiliary table metadata remains intact. |
|RENAME TABLE (including cross\-database) |The auxiliary table is migrated together with the primary table. The index works normally after renaming. |
|DROP TABLE |The auxiliary table is dropped together with the primary table. |
|DROP DATABASE |All auxiliary tables in the database are deleted together with the primary table, with no orphaned objects left behind. |

**Behavior under primary-replica replication**

|**Scenario** |**Behavior description** |
|---|---|
|Auxiliary Table Data |Data for auxiliary tables is not written to binlog. The primary and replica nodes build their respective HNSW graphs locally based on row change events from the primary. |
|CREATE VECTOR INDEX / DROP INDEX |The DDL replicates normally to replicas, and replicas create or drop their auxiliary tables locally. |
|OPTIMIZE TABLE / ALTER ... FORCE |The DDL replicates normally. The primary and replica rebuild separately. After rebuilding, auxiliary table names on the primary and replica may differ, as the names contain their respective temporary table identifiers. |
|RENAME TABLE |The replica renames its own auxiliary table instead of receiving the auxiliary table from the primary. |
|Failed Vector DDL |It is not written to binlog. Replicas remain unaffected, and the replication link stays intact. |
|Graph topology |The level of each node is determined by random numbers. Differences in graph structure between primary and replica are normal. Only consistency of row sets and auxiliary table counts needs to be guaranteed. |

## Precautions

* External Embeddings: the database does not perform text vectorization. Vectors must be computed in advance at the application layer using external embeddings.

* Storage engine and index restrictions: Only InnoDB is supported. Partitioned tables and generated columns are not supported.

* Index usage: use `FORCE INDEX` to ensure ANN; set `force_index=False` to allow the optimizer to choose; use EXPLAIN to verify whether `Using ANN Search` appears in the query plan.

* Distance metric: the metrics for index creation and querying should be consistent (e.g., `l2`); if they are inconsistent, the metric used during index creation prevails.

* Delete and recycle bin: base tables with vector indexes are not moved to the recycle bin; `DROP TABLE` directly deletes the base table.

* Copy and enabling: Vector data is copied to all read\-only nodes. Vector indexes are automatically created only on nodes where `loose_vector_index_enabled` is enabled.

* Durability and transactions: Consistent with the base table and provides ACID properties. When the primary transaction is rolled back, the index data is also rolled back synchronously.

* Memory limit: The memory usage of a single HNSW is limited by the `loose_hnsw_max_cache_size` parameter. Set this value appropriately to avoid out\-of\-memory errors.

## Performance data

We conduct a horizontal comparison between MySQL, MariaDB 13.1 (within the MySQL ecosystem), and pgvector 0.8.2 (the most popular vector index extension in the PostgreSQL ecosystem) from three dimensions: index construction speed, index size, and index query performance. The detailed results are shown below.

### Test specifications

* Performance benchmark: VectorDBBench.

* Dataset: Performance1536D50K (1,536 dimensions and 50,000 rows of data) and Performance768D1M (768 dimensions and 1 million rows of data).

* Test CPU specifications: Intel(R) Xeon(R) Platinum 8457C CPU @ 2.60GHz, 16 cores.

* HNSW index cache parameter configuration: loose_hnsw_max_cache_size = 2GB.

### The test results are as follows.

#### Index build speed: 4 to 6 times faster

MariaDB adopts serial construction for all vector indexes, which results in extremely long construction time when building large\-scale vector indexes. RDS for MySQL leverages its self\-developed high\-performance parallel construction engine to break the bottleneck of vector index construction, supporting fast vector index creation even for million\-scale vector datasets.

This test adopts the HNSW index configuration with parameters m=16 and ef_construction=128. Two datasets with distinct vector dimensions are selected, and the overall time consumption from vector data loading to index construction is counted.

![图片](https://portal.volccdn.com/obj/volcfe/cloud-universal-doc/upload_a997613851d8ad51100323aca809d553.png)

Based on the comparison data in the bar chart, the following conclusions can be drawn:

* **For the dataset of 50,000 vectors of 1536 dimensions**, MariaDB takes 126 seconds, pgvector takes 27.76 seconds, and RDS for MySQL takes 22 seconds for index construction. The RDS for MySQL builds indexes about **6** times faster than MariaDB.

* **For the dataset of 1 million 768\-dimensional vectors**: MariaDB takes 2524.5 seconds, pgvector takes 378.5 seconds, and RDS for MySQL takes 645.6 seconds for index construction. The RDS for MySQL builds indexes about **4** times faster than MariaDB.

The larger the vector dataset, the more obvious the efficiency improvement brought by parallel vector index construction. For scenarios involving million\-scale vector index construction, the index building time is shortened from 42 minutes to within 11 minutes.

#### Index size: Reduced by 2–4 times

Native pgvector only supports Float32 vector storage, resulting in large disk occupation of constructed indexes. In contrast, RDS for MySQL provides two scalar quantization modes, SQ16 and SQ8, which store vector indexes in a more compact manner.

![图片](https://portal.volccdn.com/obj/volcfe/cloud-universal-doc/upload_ef0d187d8304d8a74a7f359601af5d6d.png)

Based on the comparison data in the bar chart, the following conclusions can be drawn:

* **For the dataset of 50,000 vectors of 1536 dimensions**, MariaDB reaches 218.1 MB, pgvector reaches 391 MB, and VolcEngine RDS MySQL reaches 220.4 MB for index size.

* **For the dataset of 1 million 768\-dimensional vectors**, MariaDB measures 2.135 GB, pgvector measures 3.906 GB, and RDS for MySQL measures 2.219 GB for index size.

Compared with pgvector, the index size can be reduced to half after enabling SQ16 quantization and further cut to a quarter with SQ8 quantization, which effectively lowers the disk space occupied by vector indexes and reduces storage costs.

#### Index Query Performance: Query Throughput Surges 2–3 Times Under High Recall

This performance test is conducted with VectorDBBench, an industry\-standard benchmark tool. We count the vector retrieval throughput (QPS) metrics of each database within the practical business range with high recall rate.

Based on the comparison data in the bar chart, the following conclusions can be drawn:

* **For the dataset of 50,000 vectors of 1536 dimensions at a recall rate of 97 percent, ** MariaDB delivers 5326, pgvector delivers 3600, and RDS for MySQL delivers 8334 for vector retrieval throughput (QPS). In comparison, the vector retrieval throughput (QPS) of RDS for MySQL is approximately **1.6** times that of MariaDB and **2.3** times that of pgvector.

* **For the dataset of 1 million 768\-dimensional vectors at a recall rate of 95 percent**, MariaDB delivers 3703, pgvector delivers 2100, and RDS for MySQL delivers 4838 for vector retrieval throughput (QPS). In comparison, the vector retrieval throughput (QPS) of RDS for MySQL is approximately **1.3** times that of MariaDB and **2.3** times that of pgvector.
