## 1 Delta Lake introduction

Delta Lake is a table storage format launched by Databricks, serving as a fundamental component for building the Lakehouse architecture. Delta Lake supports ACID transactions, updates and deletes, multi\-version history tracking, schema validation and evolution, streaming writes and reads, as well as compatibility with multiple open\-source ecosystem engines.

The table format of Delta Lake is an intermediate form between the data lake and data warehouse models. It combines the advantages of native data storage and openness found in data lakes, while also incorporating features such as transactions and data validation that are exclusive to data warehouses. This approach addresses the challenges of disorganized and difficult\-to\-govern data in data lakes, as well as the issues of closed data, information loss, and lack of timeliness in data warehouses.<span>![图片](https://portal.volccdn.com/obj/volcfe/cloud-universal-doc/upload_9836840de2f68db4cab6447b7d7cfbf8.png) </span>

Lakehouse definition (image source: Spark\-Submit 2022)

Based on Delta Lake, Lakehouse solutions can be built. Raw data is written into Delta Lake in either streaming or batch mode, and the transformation process from Bronze Table to Gold Table is completed within Delta Lake (analogous to the process from ODS to ADS in data warehouses). Whether it is the raw table, intermediate table, or result table, all support various query engines, and the data is stored in big data storage or object storage.

<span>![图片](https://portal.volccdn.com/obj/volcfe/cloud-universal-doc/upload_0e79142468e7fcb902df9fb9ebbb7b2b.png) </span>

Lakehouse architecture (image source: Delta Lake official website)

Table format storage similar to Delta Lake includes Iceberg and Hudi, both of which are also available on E\-MapReduce (EMR). Users can refer to related articles.

## 2 Delta Lake principles

The biggest difference between Delta Lake and directly using lake storage is that Delta Lake introduces a metadata layer on top of lake storage. All additional features of Delta Lake are related to the design of this metadata. In short, this metadata records multi\-version information of the table. Any change to the table generates a new version, and the old versions are retained for a period of time and can be deleted after expiration.

The principle is illustrated in the following diagram:

<span>![图片](https://portal.volccdn.com/obj/volcfe/cloud-universal-doc/upload_3181ec808c304cc5dd568bd9e7900a91.png) </span>

In the metadata layer on the left, when we execute insert for the first time, the metadata records the files File1 and File2 generated by the local insert. During the second update operation, the file File1 containing the relevant data to be updated is deleted. The updated data, together with the data from the deleted file that is not involved in the update, is used to generate a new file File3, which is written into the metadata, and a new version is created at the same time.

## 3 Delta Lake use cases

Delta Lake use cases are as follows:


* Requirements for updates and deletions

* Requirements for schema evolution

* Requirements for streaming read and write

* Requirements for data validation

* Requirements for CDC

* Requirements for building a data warehouse on cloud object storage


Delta Lake is not suitable for


* Scenarios with frequent updates and deletions. In such scenarios, Delta Lake experiences severe performance degradation due to write amplification.

* Scenarios with high\-concurrency writes. Delta Lake's transaction implementation uses an optimistic locking mechanism, and high\-concurrency writes result in significant consumption of write resources but ultimately result in write failures.

* Scenarios with very high real\-time requirements (at the second or even sub\-second level). In such scenarios, Delta Lake generates a large number of small files, which in turn affects query performance.

## 4 Delta Lake and Spark compatibility list

Delta Lake has a strong dependency on Spark: for example, Delta 2.0.x depends on Spark 3.2.x and above, Delta 2.1.x depends on Spark 3.3.x and above, and so on.

|1.1.x |3.2.x |
