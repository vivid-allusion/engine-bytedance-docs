# Data overwrite risks and mitigation recommendations

Whether custom code or maintenance operations performed by open\-source components are involved, there is always a risk of accidental deletion when data changes or deletions occur. To ensure data security, it is recommended to follow these principles:


1. **TOS storage protection: When using TOS, tiered buckets must enable the recycle bin feature, and flat buckets must enable version control.** 

2. Understanding engine behavior: In addition to enabling underlying storage recovery, users must understand the operating principles of the compute engine and carefully evaluate the write mode to avoid accidental data overwrites and loss.


The table below briefly describes the data overwrite risks and key mitigation recommendations for common big data engines.


|**Engine/component** |**Summary of key risks and mitigation recommendations** |
|---|---|
|HDFS |* **Risk**:<br><br>   * Overwrite operations: Actions such as `create(overwrite=true)` and `rename(OVERWRITE)` directly overwrite or replace the target file or directory, resulting in data loss.<br><br>   * DistCp misuse: `distcp -overwrite` forcibly overwrites target data; `distcp -delete` deletes files on the target side that exceed those on the source side. Improper use can lead to large\-scale data deletion.<br><br>   * Committer concurrency conflicts: The default commit mechanism of `FileOutputCommitter` may overwrite files with the same name when merging task outputs, causing concurrent write conflicts.<br><br>   * Trash not enabled: By default, `fs.trash.interval=0`. Accidental deletions cannot be directly recovered from the trash.<br><br>* **Recommendations**:<br><br>   * Path isolation: Assign a unique output directory for each job. First write data to a temporary directory, then switch to the final directory using atomic `rename` after success.<br><br>   * Enable protection mechanisms: Enable trash (set `fs.trash.interval` to a nonzero value) and snapshot functionality for critical directories as the last line of defense for data recovery.<br><br>   * Use DistCp with caution: Strictly limit the use of `-overwrite` and `-delete`. Prefer `-update` for incremental synchronization, or use `-atomic` to ensure atomicity for full data switching. |
|Hive |* **Risk**:<br><br>   * INSERT OVERWRITE clears partitions: When executing `INSERT OVERWRITE` on non\-ACID tables, the target partition is cleared before new data is written. If the partition is incorrectly specified, this can result in extensive data loss.<br><br>   * Expanded scope of dynamic partition overwrite: In `nonstrict` mode, if partition columns are not strictly limited, `INSERT OVERWRITE` may accidentally overwrite the entire table or unintended partitions.<br><br>   * Accidental deletion during external table directory cleanup: When deleting external partitions (`DROP PARTITION`), if external scripts are used to clean HDFS paths, physical directories shared by multiple engines may be mistakenly deleted.<br><br>   * Risk of ACID table changes: Excessively broad `UPDATE/DELETE` operations on ACID tables may cause many row versions to become invalid, relying on Compaction for cleanup. Improper manual operations can compromise transactional consistency.<br><br>* **Recommendations**:<br><br>   * Maintain strict mode: Set `hive.exec.dynamic.partition.mode=strict` to require dynamic partition writes to include static partitions, preventing full table overwrites.<br><br>   * Prioritize ACID transactional tables: For scenarios requiring updates, deletions, or `MERGE`, prioritize the use of ACID transactional tables to leverage their row\-level change and version control capabilities.<br><br>   * Strict partition constraints: All DML operations, especially overwrite writes (`INSERT OVERWRITE`), must bind business partition keys for filtering to prevent scope expansion.<br><br>   * External table read\-only management: Treat external tables as read\-only views, with physical data managed and written by a single upstream owner to avoid conflicts from multiple writers. |
|Spark |* **Risk**:<br><br>   * The parameter `spark.sql.sources.partitionOverwriteMode` has a default value of static in the open\-source community. When performing overwrite writes on DataSource\-type tables (such as Parquet/ORC), static mode removes all data in matched partitions, rather than only overwriting the written portion. This can easily result in accidental clearing of historical data in incremental update scenarios.<br><br>   * Hive SerDe table behavior inconsistency: When using Hive SerDe tables (`STORED AS ...`), overwrite behavior is always dynamic (DYNAMIC), which is inconsistent with the default static mode of DataSource tables and makes behavior prediction more difficult.<br><br>   * Complete mode full table overwrite in streaming: Structured Streaming's `outputMode="complete"` requires the Sink to support `truncate`, causing each micro\-batch to trigger clearing and rewriting of the entire table or target.<br><br>* **Recommendations**:<br><br>   * Unified dynamic overwrite configuration: Set `spark.sql.sources.partitionOverwriteMode` to `DYNAMIC` at the platform or job level, so that partition overwrites only replace the partitions involved in the current write.<br><br>   * Prioritize DML for data lakes: For Iceberg, Hudi, Delta, and other data lake tables, use dedicated DML such as `MERGE INTO`, `UPDATE`, and `DELETE` for fine\-grained changes, rather than `SaveMode.Overwrite`.<br><br>   * Idempotent streaming writes: In Structured Streaming, use Checkpoint and the batchId provided by `foreachBatch` to achieve idempotent operations when writing to external systems, avoiding data duplication or inconsistency caused by retries. |
|Presto/Trino |* **Risk**:<br><br>   * Hive Connector partition overwrite: Through the session property `insert_existing_partitions_behavior`, the `INSERT` behavior can be changed from the default `APPEND` to `OVERWRITE`, which carries the risk of accidental partition overwrites.<br><br>   * Uncontrolled DML scope in data lakes: When performing `MERGE`, `UPDATE`, or `DELETE` on Iceberg/Delta tables, overly broad `WHERE` conditions may cause large\-scale invalidation of data versions or logical deletion.<br><br>   * Delta CREATE OR REPLACE atomic replacement: The Delta Connector supports `CREATE OR REPLACE TABLE`, which is an atomic full\-table replacement operation. If misused, old table data will be logically removed and require snapshot recovery.<br><br>   * JDBC Connector multi\-statement non\-atomicity: Executing multiple write operations on downstream databases via JDBC Connector (such as `DELETE` followed by `INSERT`) is not atomic. If a failure occurs between statements, it may result in inconsistent data states.<br><br>* **Recommendations**:<br><br>   * Restrict DML scope: When performing `MERGE`, `UPDATE`, or `DELETE` operations on Iceberg/Delta tables, you must strictly limit partitions and primary keys (or unique keys) using the `WHERE` clause to ensure the scope of changes is controllable.<br><br>   * Prohibit REPLACE on production tables: Strictly prohibit or control permissions for using `CREATE OR REPLACE TABLE` on Delta tables in production environments. Use safer update methods such as `INSERT OVERWRITE` or `MERGE` instead.<br><br>   * Configure snapshot retention: Set a reasonable snapshot retention policy for tables that support time travel, such as Iceberg/Delta, to ensure there is sufficient time window for data recovery after erroneous operations.<br><br>   * Leverage native database transactions: For scenarios requiring atomicity across multiple statements, use stored procedures or application\-side transaction encapsulation on the target database (when connecting via JDBC), rather than relying on multiple independent DML statements on the Trino side. |
|Ray |* **Risk:** <br><br>   * Unpredictable write mode semantics: The `write_*` `OVERWRITE` behavior varies depending on the data source. For example, Iceberg supports conditional overwrite, while Parquet is mapped to `overwrite_or_ignore` at the underlying layer, which can easily lead to unexpected results.<br><br>   * Lack of atomicity in concurrent writes: Data is written directly to the target path without a "temporary directory + atomic commit" mechanism. If some tasks fail, incomplete files may remain.<br><br>   * Missing Write UUID may overwrite files: If a custom `FilenameProvider` does not include `write_uuid`, files may be silently overwritten in `OVERWRITE` mode.<br><br>* **Recommendations**:<br><br>   * Clarify write mode behavior: Consult the official documentation of the data source before use. For Iceberg tables, use `overwrite_filter` to precisely control the overwrite scope.<br><br>   * Use unique identifiers to ensure idempotency: Introduce `dataset_uuid` or a custom `FilenameProvider` in write tasks to prevent mutual overwrites during concurrent or retry operations.<br><br>   * Adopt two\-phase commit: For critical writes, first write to a temporary directory, then perform atomic `rename` after validation; or leverage the native transaction capabilities of data lake tables (Iceberg/Delta) to avoid direct overwriting of the target path. |
|StarRocks / Doris |* **Risk**:<br><br>   * Primary key model UPSERT overwrite: By default, writing to primary key tables or update tables uses UPSERT semantics, where later data for the same key overwrites previously written data. If a full snapshot or out\-of\-order CDC is imported multiple times, only the last batch of data is retained, and historical details are not visible.<br><br>   * INSERT OVERWRITE partition clearing: By default, `INSERT OVERWRITE` performs 'rebuild and atomic replacement' on the table or partition. If `dynamic_overwrite` is not enabled, partitions not involved in the current batch may also be cleared. Mistakenly writing incremental overwrites based on the dt dimension as full\-table or wide\-range overwrites can easily cause large\-scale data loss.<br><br>   * Repeated import into aggregation/detail tables: In aggregation tables, SUM/REPLACE for the same key will accumulate or overwrite results, while detail tables do not deduplicate. Rerunning jobs or consuming logs repeatedly will amplify metrics in aggregation tables and generate multiple duplicate records in detail tables.<br><br>   * Partial column updates and default value overwrites: If `partial_update` or column lists are not correctly enabled or configured for primary key tables, writing only some columns will be treated as a full\-row UPSERT, and columns not present will overwrite old values with default values or NULL. In column mode, incomplete column lists or improper default value settings can easily generate 'pseudo\-overwrite' data.<br><br>   * DELETE conditions too broad: When deleting via `DELETE` statements or importing `__op='delete'`, if `WHERE` conditions are not strictly limited by primary key or partition, it may trigger wide\-range scans and batch logical deletions, requiring upstream replay to recover.<br><br>* **Recommendations**:<br><br>   * Select models as needed: Use detail tables when historical details need to be retained. When updates and overwrites are required, explicitly use primary key tables and reasonably use version columns and `merge_condition` to prevent out\-of\-order old data from overwriting new values.<br><br>   * Dynamic overwrite with explicit partitions: When using `INSERT OVERWRITE`, enable `dynamic_overwrite` and explicitly specify the `PARTITION` range to ensure only the target partitions are overwritten.<br><br>   * Idempotent import: All import tasks should use a unique label to ensure idempotency in case of failed retries and avoid duplicate data.<br><br>   * Strict DELETE conditions: When executing `DELETE`, strict `WHERE` conditions such as primary key or partition must be included, and operations should be verified on small data volumes before proceeding.<br><br>   * Caution: Operations such as `TRUNCATE` and `DROP PARTITION` must only be executed when the scope is clearly defined and backup or snapshot protection is in place. |
