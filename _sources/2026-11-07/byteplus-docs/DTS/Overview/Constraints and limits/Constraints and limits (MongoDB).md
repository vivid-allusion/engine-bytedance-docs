This topic outlines the supported databases and limits when the target database for migration is Document Database for MongoDB, for example, the BytePlus Document Database for MongoDB or self\-managed Document Database for MongoDB.

<span id=".5pSv5oyB55qE5pWw5o2u5bqT"></span>
## Supported databases


|Source database |Target database |Supported version |Migration type |Synchronization type |
|---|---|---|---|---|
|* BytePlus Document Database for MongoDB<br><br>* Public network MongoDB<br><br>* MongoDB connected over express network |* BytePlus Document Database for MongoDB<br><br>* Public network MongoDB<br><br>* MongoDB connected over express network |* MongoDB 3.4<br><br>* MongoDB 3.6<br><br>* Document Database for MongoDB 4.0<br><br>* Document Database for MongoDB 4.4<br><br>* MongoDB 5.0<br><br>* Document Database for MongoDB 6.0<br><br>* Document Database for MongoDB 7.0<br><br>* Document Database for MongoDB 8.0 |* Schema migration<br><br>* Full data migration<br><br>* Incremental data migration |* Schema initialization<br><br>* Full initialization<br><br>* Incremental synchronization |


<div data-tips="true" data-tips-type="tip" data-tips-is-title="true">tip</div>


<div data-tips="true" data-tips-type="tip">Incremental data migration and incremental data synchronization are not supported when the source database is a MongoDB single\-node instance. To use incremental data migration or incremental data synchronization, you can convert the single\-node MongoDB to a replica set. Refer to <a href="https://docs.byteplus.com/en/docs/DTS/how_to_perform_incremental_migration_or_incremental_synchronization">How to implement incremental migration or incremental synchronization if the source database is a single\-node MongoDB instance</a> for more information.</div>

## Limits


|Type |Description |
|---|---|
|Source database limits |Bandwidth requirements: Adequate egress bandwidth is required on the source database server. Failure to meet this prerequisite will lead to suboptimal migration performance. |
||If the migration object is at the collection level and needs to be edited (e.g., collection name mapping), each migration task only supports migrating up to 1,000 collections. If the number limit is exceeded, a request error will be displayed after the task is submitted. In this case, it is recommended that you split the collections to be migrated and configure the task in batches. |
||To perform incremental migration, the source Oplog settings must meet the following requirements:<br><br><br>* The Oplog must be enabled. Otherwise, an error will be reported during the pre\-check phase, and the data migration task can not be started successfully.<br><br>* It is recommended that the Oplog be retained for at least 7 days during full migration. To adjust the Oplog size, refer to [Changing the size of the Oplog](https://www.mongodb.com/docs/v4.0/tutorial/change-oplog-size/). Alternatively, wait until the full migration is completed before cleaning up the Oplog generated by the source database after the DTS task starts. |
||The account used for data migration must have the following permissions:<br><br><br>* If the source database is a sharded cluster instance, you need to have the `root` account privileges of the source database.<br><br>   <div data-tips="true" data-tips-type="tip" data-tips-is-title="true" data-wrapper-indent="1">tip   </div><br>   <br><br>   <div data-tips="true" data-tips-type="tip" data-wrapper-indent="1">When incrementally migrating sharded cluster data and the incremental data acquisition method is <code>ChangeStream</code>, the source database account needs the <code>ChangeStream</code> permission.   </div><br>   <br><br>* If the source database is a replica set instance, the following permissions are required.<br><br>   * `FIND`, `buildInfo`, `serverStatus`, and `listDatabases` permissions of the object to be migrated from the source database.<br><br>   * The source database account must have read permissions for the database to be synchronized, the `Config` database, the `admin` database, and the `local `database.<br><br>* The target database account must have read and write permissions for the target database, and read permissions for the `local` database. |
||Operation limits of the source database:<br><br><br>* During the schema migration and full migration phases, do not perform schema changes to databases or collections. Otherwise, the data migration task will fail.<br><br>* If only full data migration is performed, do not write new data to the source database, or the source and target data will be inconsistent.<br><br>* To maintain real\-time data consistency, it is recommended to select schema migration, full data migration, and incremental data migration simultaneously. |
|Other limits |It is recommended that the source and target Document Database for MongoDB databases be the same version, or migrate from a lower version to a higher one to ensure compatibility. If migrating from a higher version to a lower version, there may be database compatibility issues. |
||Migrating data from admin and local databases is not supported. |
||Transaction information is not retained, that is, transactions in the source database are converted into single records when migrated to the target database. |
||Prior to executing data migration, assess the performance of both source and target databases. It is also advised to perform the migration during off\-peak business hours. Otherwise, during full data migration, DTS consumes certain read/write resources on both source and target databases, which may lead to an increase in database load. |
||Since full data migration performs concurrent insert operations, the collection in the target database generates fragments. Therefore, the storage space of the collection in the target database will be larger than that of the collection in the source database after the full migration is complete. |
||The storage space of the target Document Database for MongoDB database must be greater than the storage space occupied by the source Document Database for MongoDB database. |
||Confirm whether the migration precision for FLOAT or DOUBLE columns in DTS meets your business expectations. DTS reads the values of these two types of columns through `ROUND(COLUMN, PRECISION)`. If its precision is not explicitly defined, the migration precision of FLOAT is 38 bits and that of DOUBLE is 308 bits in DTS. |
|Special cases |When the source database is a self\-managed Document Database for MongoDB, if the source database switches to the primary during migration, the task will fail. |
