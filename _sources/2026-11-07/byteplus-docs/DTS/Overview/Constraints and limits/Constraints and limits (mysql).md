This topic outlines the supported databases and limits when the target database for migration is RDS for MySQL, for example, the BytePlus RDS for MySQL or self\-managed RDS for MySQL.

## Supported databases

|Source database |Target database |Supported version |Migration type |Synchronization type |
|---|---|---|---|---|
|* BytePlus RDS for MySQL<br><br>* BytePlus veDB for MySQL<br><br>* MySQL connected over public network<br><br>* MySQL connected over express network |* BytePlus RDS for MySQL<br><br>* BytePlus veDB for MySQL<br><br>* MySQL connected over public network<br><br>* MySQL connected over express network |* MySQL 5.5<br><br>* MySQL 5.6<br><br>* MySQL 5.7<br><br>* MySQL 8.0 |* Schema migration<br><br>* Post\-schema migration<br><br>* Full migration<br><br>* Incremental migration<br><br>* User migration |* Schema initialization<br><br>* Full initialization<br><br>* Incremental synchronization |
||BytePlus RDS for PostgreSQL |Database version: supports PostgreSQL versions 11 to 17. |Unsupported ||

## Limits

|Type |Description |
|---|---|
|Source database limits |* Bandwidth requirements: Adequate egress bandwidth is required on the source database server. Failure to meet this prerequisite will lead to suboptimal migration or synchronization performance.<br><br>* The system supports the InnoDB and MyISAM engines, but does not support the migration or synchronization of MariaDB.<br><br>* Partitioned tables are not supported when converting the MyISAM storage engine to the InnoDB storage engine.<br><br>* Tables to be migrated or synchronized must have a primary key or a unique non\-null constraint, and their fields must be unique. Otherwise, data inconsistency may occur.<br><br>* To perform incremental migration or synchronization, the Binlog logs must meet the following requirements:<br><br>   * It must be enabled, and `binlog_format` must be `row`, and `binlog_row_image` must be `full`. Otherwise, errors will be reported during the pre\-check phase, preventing the successful start of the data migration or synchronization task.<br><br>   * Retain for at least 24 hours (7 days or longer recommended). Otherwise, if the link is interrupted due to uncontrollable factors, the inability to retrieve Binlog files may prevent the link from being restored.<br><br>* The account used for data migration or synchronization must have the following permissions:<br><br>   * Schema migration and full migration, or schema initialization and full initialization: SELECT permission for all migration objects.<br><br>   * Incremental migration or synchronization: REPLICATION SLAVER, REPLICATION CLIENT, and SELECT permissions for all migration or synchronization objects.<br><br>* `gtid_mode` limit: When the instance version of the source database is greater than or equal to 5.6, the parameter `gtid_mode` is set to `ON`.<br><br><br>> **tip**<br><br><br>> When MySQL version is less than 8.0 and parameter `gtid_mode` is not enabled, foreign key cascade deletes may fail during data migration or synchronization, causing data inconsistency.<br><br><br><br>* Operation limits of the source database:<br><br>   * During link creation, database or table schema migration or initialization, and full migration or initialization stages, do not perform DDL operations that change the database or table structure, or the data migration or initialization task will fail.<br><br>   * The following DDL operations are only supported during the incremental migration or synchronization stage:<br><br>   * ALTER TABLE, ALTER VIEW<br><br>   * CREATE FUNCTION, CREATE INDEX, CREATE PROCEDURE, CREATE TABLE, CREATE VIEW<br><br>   * DROP INDEX, DROP TABLE, DROP FUNCTION, DROP PROCEDURE<br><br>   * RENAME TABLE<br><br>   * TRUNCATE TABLE<br><br>   * If only full data migration or initialization is performed, do not write new data to the source instance, or the source and target data will be inconsistent. To maintain data consistency in real time, it is recommended to select schema migration, full migration, and incremental migration, or schema initialization, full initialization, and incremental synchronization at the same time.<br><br>* Tables with foreign key dependencies must be synchronized or migrated simultaneously. Data migration or synchronization will fail if tables with foreign key dependencies are not selected.<br><br>* It is recommended that the number of tables in a single task should not exceed 20,000, and the number of databases should not exceed 1,000. If a large number of tables need to be migrated or synchronized, it is recommended to split them into multiple tasks.<br><br>* When a non\-BytePlus instance serves as the source end for data transmission, the source database does not support configuring multi\-node proxy addresses. During incremental data synchronization, incremental migration, and incremental subscription, DTS requires establishing a stable long connection with specific database instances. The load balancing or routing mechanism of multi\-node proxy may cause connection drift or log parsing failure. It is recommended to configure a single node connection address directly or use a database gateway (DG) for access. |
|DDL limitations |* Operation limits<br><br>   * General rules<br><br>      * DDL operations are prohibited during initialization: Do not execute DDL statements during link creation, schema initialization, or full data synchronization—otherwise, the task will fail.<br><br>      * When the target database is being written to by applications, executing DDL on the source may result in data loss. For example:<br><br>         * unidirectional synchronization task: in a unidirectional incremental synchronization task, once application traffic has been switched over (i.e., writes have migrated to the destination), executing DDL operations on the source end is strictly prohibited. Otherwise, it may cause serious consequences such as data loss or schema inconsistency on the destination. At this stage, any DDL operations must be performed on the target database. The source database should be used only for synchronization backtracking or read\-only queries.<br><br>         * Bidirectional synchronization task:When both databases accept application writes, executing DDL on either side may cause data loss or schema inconsistency on the peer database.<br><br><br>> **tip**<br><br><br>> When using online DDL tools such as gh\-ost or pt\-online\-schema\-change, temporary tables are created during schema changes. Data written to the target database during operations like RENAME or DROP on these temporary tables may be lost.<br><br><br><br>      * OnlineDDL support scope:<br><br>         * Do not write data to the target database during DDL synchronization, as it may result in data loss.<br><br>         * DTS supports synchronizing the following temporary tables (ensure the target database has write permissions):<br><br>            * gh\-ost: original table name `_ghc`, original table name `_gho`, original table name `_del`, `tp_{change ID}_ogt_{original table name}`, `tp_{change ID}_g_{original table name} tp_{change ID}_del_{original table name}`, `tp_{change ID}_d_{original table name}`.<br><br>            * pt\-osc: original table name `_new`, original table name `_old`.<br><br>         * Table mapping (renaming) is mutually exclusive with Online DDL temporary table synchronization, only one can be enabled at a time.<br><br>         * Even lightweight operations, such as adding a column to a small table, may cause DDL synchronization to fail if the temporary table exists for too short a duration. It is recommended to perform all such changes uniformly through DBW tickets. For detailed steps, refer to [lock-free schema change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-structural-change-ticket-onlineddl-ticket-for-mysql) or [lock-free data change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-sql-change-ticket-for-mysql).<br><br>      * Avoid frequent DDL operations: Repeatedly applying DDL to the same table may cause DTS metadata updates to fail, risking replication interruption. You can avoid this issue by:<br><br>         * When performing DDL operations via the console, allow a minimum interval of 1–3 seconds between consecutive operations.<br><br>         * Prefer using DBW lock\-free schema change tickets to execute DDL operations. For detailed steps, refer to [lock-free schema change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-structural-change-ticket-onlineddl-ticket-for-mysql) or [lock-free data change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-sql-change-ticket-for-mysql).<br><br>      * Cross\-Database DDL restrictions: If a database is not included in the synchronization objects, you must not execute DDL statements that affect already synchronized databases (e.g., cross\-database views, foreign keys, etc.). Otherwise, the synchronization task will fail.<br><br>      * DDL synchronization is currently supported only from the forward task to the target database; reverse DDL is not automatically synchronized. If reverse DDL synchronization is required, first adjust the DDL synchronization direction, then perform the operation. For detailed operations, refer to [adjusting the DDL synchronization direction of the bidirectional synchronization task](https://docs.byteplus.com/en/docs/DTS/Reversing_the_DDL_synchronization_direction_of_the_bidirectional_synchronization_task?lang=en).<br><br>* Special limitations<br><br>   * Table schema changes must be forward\-compatible and limited to the following safe DDL operations:CREATE TABLE, ADD COLUMN, MODIFY COLUMN (only to increase column length), CREATE INDEX, DROP INDEX.<br><br>   * Prohibited operations: Modifying column data types, dropping columns, or reducing column lengths are not allowed, as they may cause data inconsistency or replication interruption. |
|Other limits |* It is recommended that the source and target RDS for MySQL databases be the same version to ensure compatibility.<br><br>* Prior to executing data migration or synchronization, assess the performance of both source and target databases. It is also advised to perform migration or synchronization during off\-peak business hours. Otherwise, during full migration or initiation, DTS consumes certain read/write resources on both source and target databases, which may lead to an increase in database load.<br><br>* During the migration or synchronization process, the target database may generate a large number of Binlog files. In scenarios involving full migration or initialization, the generated Binlog files may even be larger than the data files. Therefore, it is recommended to configure an appropriate Binlog retention policy for the target database before starting migration or initialization to prevent Binlog files from occupying excessive storage space.<br><br>* For data migration or synchronization tasks with database or table name mapping, the mapping may not take effect after the stored procedure and function are migrated or synchronized.<br><br>* For migration tasks that include both schema and incremental migrations, or synchronization tasks that include both schema initialization and incremental synchronization, triggers will be migrated or synchronized after the task is terminated.<br><br>* The migration account privileges of the target RDS for MySQL database will affect the use of views, stored procedures, and functions. The specific restrictions are as follows:<br><br>   * If the migration account of the target RDS for MySQL database has the SET_USER_ID privilege:<br><br>      * Views, stored procedures, and functions will retain the original `definer` and `sql_security`.<br><br>      * The views, stored procedures, and functions can be used normally only after the account migration task is completed or the corresponding account is manually created in the target database.<br><br>   * If the migration account of the target RDS for MySQL database does not have or support the SET_USER_ID privilege:<br><br>      * After views, stored procedures, and functions are migrated, the `definer` will be replaced with the migration account.<br><br>      * `Sql_security` will be set to `invoker`.<br><br><br>> **tip**<br><br><br>> Only RDS for MySQL 8.0 supports setting SET_USER_ID permissions.<br><br><br><br>* The task suspension time can not exceed 7 days. If it exceeds 7 days, the task can not be recovered.<br><br>* If the source database is RDS for MySQL 8.0, when configuring migration or synchronization tasks, you must manually grant the relevant data migration permissions directly to the following accounts:<br><br>   * The accounts for the source or target database are granted relevant permissions through the Role.<br><br>   * The accounts that need to perform User migration are granted relevant permissions through the Role.<br><br>* Only the following objects can be migrated or synchronized:<br><br>   * Migration object: table, view, stored procedure, function, trigger, and event.<br><br>   * Synchronization object: table, view, stored procedure, and function.<br><br>* Explanation of `DEFINER` and `SQL SECURITY` behaviors for views, stored procedures, and functions in MySQL migration:<br><br><br>During data transmission tasks migrating to MySQL, if migrating views, stored procedures, or functions and the destination migration account lacks (or cannot be granted) `SET_USER_ID` permission, the `DEFINER` of related objects may be replaced by the migration account after migration, and `SQL SECURITY` may be adjusted to `INVOKER`.<br><br>If maintaining the original `DEFINER / SQL SECURITY` behavior is required, manually recreate or correct the definitions of related objects on the destination end after migration completes. |
|Special cases |* The migration or synchronization task will fail if the RDS source database performs a primary/standby switchover during the migration or synchronization. If the RDS source database performs a restart operation during migration or synchronization, the migration or synchronization task will be temporarily interrupted and automatically attempted to recover. If the task does not recover for a long time, [submit a ticket](https://console.byteplus.com/workorder/create/) for technical support.<br><br>* Since the delay time of DTS is derived by comparing the timestamp of the last data migrated or synchronized to the target database with the current timestamp, the delay information may be inaccurate if the source database has not performed DML operations for a long time. If the delay time displayed for the task is too long, you can execute a DML operation in the source database to update the delay information.<br><br>   > **tip**<br>   <br><br>   > If you select the entire database as the migration or synchronization object, you can also create a heartbeat table, which is regularly updated or written with data every second.<br>   <br><br>* If the target database is a BytePlus RDS for MySQL, and the high\-privilege account is used for the target database when configuring the migration or synchronization task, DTS will automatically create a database in the BytePlus RDS for MySQL target database. If the name of the database to be migrated or synchronized does not comply with the naming conventions of BytePlus RDS for MySQL, you need to create the database in BytePlus RDS for MySQL before configuring the migration task.<br><br>* When the source database is Alibaba Cloud PolarDB MySQL, the Binlog feature must be enabled at the source end during migration task configuration, and ensure that the primary endpoint of PolarDB MySQL is used. |
||When creating a bidirectional synchronization task, you need to pay attention to the following information:<br><br><br>* Data writing and conflict control<br><br>   * Single\-point write principle: for records with the same primary key, business key, or unique key, updates are allowed only on one node (source end or destination end).<br><br>      * If both ends update the data simultaneously, the system will automatically resolve the conflict based on the primary key conflict resolution strategy configured in the task.<br><br>      * It is recommended to avoid writing to the same primary key from both ends at the application layer.<br><br>   * Do not write non\-DTS data to the target database: During synchronization, do not write data to the target database via applications, scripts, or other tools, as this may cause primary key conflicts or data overwrites.<br><br>* Network and topology recommendations<br><br>   * Outbound Cloud Link Performance Risk:If the synchronization involves data transfer from BytePlus to a public cloud (outbound), network bandwidth or latency may cause performance bottlenecks. Creating a bidirectional synchronization task directly is not recommended.<br><br>   * Bidirectional synchronization consists of two independent unidirectional tasks (forward + reverse) that must be configured separately, with consistent filter rules and conflict resolution strategies. |
