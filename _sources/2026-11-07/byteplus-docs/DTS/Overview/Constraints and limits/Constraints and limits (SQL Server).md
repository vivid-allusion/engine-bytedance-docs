This topic outlines the limits and database contents for migrating RDS for SQL Server databases, for example, BytePlus RDS for SQL Server.

<span id=".5pSv5oyB55qE5pWw5o2u5bqT"></span>
## Supported databases


|**Source database** |**Target database** |**Supported versions** |**Migration type** |
|---|---|---|---|
|* BytePlus RDS for SQL Server<br><br>* Public network SQL Server<br><br>* SQL Server connected over express network |* BytePlus RDS for SQL Server<br><br>* Public network SQL Server<br><br>* SQL Server connected over express network |* RDS for SQL Server 2019 Enterprise Edition<br><br>* RDS for SQL Server 2019 Standard Edition<br><br>* RDS for SQL Server 2019 Web Edition<br><br>* RDS for SQL Server 2022 Enterprise Edition<br><br>* RDS for SQL Server 2022 Standard Edition<br><br>* RDS for SQL Server 2022 web edition |* Schema migration<br><br>* Full migration<br><br>* Incremental migration |

## Limits


|**Type** |**Description** |
|---|---|
|Source database limits |* General limits:<br><br>   * Bandwidth requirements: Adequate egress bandwidth is required on the source database server. Failure to meet this prerequisite will lead to suboptimal migration performance.<br><br>   * Tables to be migrated must contain a primary key or unique constraint, and the fields must be unique. Otherwise, duplicate data may occur in the target database.<br><br>   * If the migration objects are at the table level, then a single migration task supports a maximum of 1,000 tables. If the quantity limit is exceeded, it is recommended to split the tables to be migrated and create multiple tasks (create new tasks only after the previous one has completed).<br><br>   * A single migration task supports a maximum of 10 databases. Exceeding the quantity limit introduces risks of stability and performance issues. In such cases, it is recommended to split the tables to be migrated and create multiple tasks.<br><br>   * Do not perform write operations on the target database. Otherwise, data inconsistency may occur.<br><br>   * DTS does not migrate foreign keys from the source database to the target database, and as a result, operations such as cascading updates and deletes from the source will not be migrated.<br><br>   * The storage space of the target instance must be larger than the used storage space of the source instance.<br><br>   * Migration of data from read\-only instances is unsupported.<br><br>   * Column encryption during migration is unsupported.<br><br>   * Only RDS for SQL Server 2019 and 2022 instances are currently supported for migration.<br><br>   * Only tables are currently supported for migration (Views and triggers are not yet supported).<br><br>   * Configuring multiple migration tasks in the same table is unsupported.<br><br>   * For non\-BytePlus RDS for SQL Server sources, avoid switching to the primary during migration as this will cause task failure.<br><br>* Limits for schema or full migration:<br><br>   * During the table schema migration and full migration stages, do not perform DDL operations that change the database or table structure, or the data migration task will fail.<br><br>   * If only full data migration is performed, do not write new data to the source instance, or the source and target data will be inconsistent. To maintain real\-time data consistency, it is recommended to select schema migration, full migration, and incremental migration.<br><br>   * It supports selecting the table structure, data, and indexes of the table.<br><br>   * When migrating table structure, the functions `newid`, `getutcdate`, and `getdate` are supported as default values. When using these functions as default values, the target database also needs functions with the same functions.<br><br>   * It supports migrating columns with auto\-incrementing attributes.<br><br>   * Writing source database calculated columns to target database calculated columns is currently not supported, but writing source database calculated columns to target database ordinary columns is supported.<br><br>* Limits for incremental migration:<br><br>   * You need to enable data logs and set the instance backup mode to `Full`.<br><br>   * For a non\-BytePlus RDS for SQL Server source, the `srvname` in `sys.sysservers` must match the `SERVERPROPERTY` function's return value.<br><br>   * For a BytePlus RDS for SQL Server source, avoid operations such as switching to the primary, restart and changing configurations during incremental migration as they may lead to data inconsistency.<br><br>   * The delete action for the following large data types is not supported: `IMAGE`, `TEXT`, and `NTEXT`.<br><br>   * The update action for the following large data types is not supported: `IMAGE`, `TEXT`, `NTEXT`, `varchar(max)`, `nvarchar(max)`, and `varbinary(max)`.<br><br>   * The source database does not support performing multiple add/drop column operations in succession (with intervals less than 10 minutes). Consecutive execution will cause the task to report an error.<br><br>   * Incremental changes to computed columns are unsupported.<br><br>   * Incremental migration is not supported if the source database instance is RDS for SQL Server 2019/2022 Web Edition.<br><br>   * As CDC is enabled by default during the incremental migration phase, it is critical that before migration begins, the local disk hosting the source database has sufficient free space to accommodate the database to be migrated.<br><br>   * During incremental migration, CDC data cleaning is performed every 24 hours to help maintain system stability and data consistency.<br><br>* The account used for data migration must have the following permissions:<br><br>   * During schema and full migrations, the migration account must have the `db_owner` permission for each database to be migrated.<br><br>   * During incremental migration, if you are migrating a BytePlus RDS for SQL Server instance, the migration account must have the `db_owner` permission for each database to be migrated. If you are not migrating a BytePlus RDS for SQL Server instance, the migration account must have the `sysadmin` permission for the database instance to be migrated.<br><br>   * During migration, if the target database to be migrated does not exist in the target instance, the migration account must have `create any database` permission. If the target database already exists, the account must have `db_owner` permissions for each database. |
|Other limits |* It is recommended that the source and target database instances be the same version, or migrate from a lower version to a higher one. If cross\-version migration is required, compatibility must be confirmed before migration. Otherwise, it may lead to data inconsistency.<br><br>* To ensure the accuracy of incremental data migration, DTS creates the trigger `volc_dts_cdc_sync_ddl` and the DDL storage table `volc_dts_cdc_ddl_history` in the source database.<br><br>* Prior to executing data migration, assess the performance of both the source and target database instances. It is also advised to perform the migration during off\-peak business hours. Otherwise, during full migration, DTS consumes certain read/write resources on both source and target databases, which may lead to an increase in database load. |
