This topic describes how to create a task to migrate a public network MySQL to a MySQL connected over express network in the Database Transmission Service (DTS) console.

## Prerequisites

* You have set up MySQL in a public network environment and created a database account.

* Set the target information as needed, as detailed below:

   * When using VPN to perform data migration, the local network where the self\-managed database is located has been connected to BytePlus via VPN gateway. For detailed steps, refer to[ Building a cloud VPC and on-premises multi-data-center network interconnection](https://docs.byteplus.com/en/docs/vpn/Connecting-a-virtual-private-cloud-to-multiple-data-centers).

   * If data migration requires a dedicated line connection, you need to establish a dedicated line connection between a single cloud VPC and a single on\-premises data center network. For more information, refer to [Configuring direct connections](https://docs.byteplus.com/en/docs/directconnect/Quick-start#.6YWN572u5LiT57q_6L-e5o6l).

* When the access method of the database instance is self\-managed over the Internet and access restrictions are enabled, add the DTS server IP addresses to the allowlist or security group of the database instance before creating the database transmission task. DTS server IP addresses vary by region, as detailed below:

   * DTS server IP addresses in China (Guangzhou), China (Shanghai), and China (Beijing) are `221.194.189.0/27,157.148.90.32/27,180.184.132.64/27,61.129.54.64/27,220.196.172.32/27,117.135.143.32/27,220.196.168.32/27,116.132.250.32/27,111.45.13.32/27,125.88.248.32/27,180.153.35.32/27,220.181.65.32/27,220.181.65.64/27`.

   * DTS server IP addresses in Asia Pacific (Johor) are `101.47.0.32/27,220.181.65.32/27,220.181.65.64/27,101.47.65.192/27,101.47.65.32/27`.

   * DTS server IP addresses in Asia Pacific (Jakarta) are `221.194.189.0/27,157.148.90.32/27`.

   * DTS server IP addresses in China (Hong Kong) are `101.47.0.32/27,220.181.65.32/27,220.181.65.64/27,101.47.65.192/27,101.47.65.32/27`.

      For more information on the CIDR block of DTS servers, refer to [Adding the CIDR block of the DTS server](https://docs.byteplus.com/en/docs/DTS/Adding_the_CIDR_block_of_the_DTS_server).

* When your instance connects via the VPC, the subnet of the VPC must communicate with the source or target database. To allow DTS to access instances in the VPC normally, add the subnet CIDR block to the source or target database allowlist or security group rules. For more information, refer to [Adding the CIDR block of the DTS server](https://docs.byteplus.com/en/docs/DTS/Adding_the_CIDR_block_of_the_DTS_server).

* The network connectivity and service availability of the source and destination have been confirmed.

* Optional. Check each migration object in the source and target databases according to the instructions in the pre\-check items. For details, refer to [Pre-check items (RDS for MySQL)](https://docs.byteplus.com/en/docs/DTS/consumption_checkpoint_items_mysql).

## Precautions

* When the source is self\-managed MySQL, pay attention to the following information:

   * If the source end switches to the primary during migration, the migration task will fail.

   * If the source end performs a restart operation during migration, the migration task will be temporarily interrupted and automatically attempted to recover. If the task does not recover for a long time, [submit a ticket](https://console.byteplus.com/workorder/create/) for technical support.

   * Since the delay time of Database Transmission Service (DTS) is derived by comparing the timestamp of the last data migrated to the destination with the current timestamp, the delay information may be inaccurate if the source end has not performed DML operations for a long time. If the delay time displayed for the task is too long, you can execute a DML operation in the source end to update the delay information.

      > **tip**

      > If the migration object is the entire database, you can create a heartbeat table that is updated or written with data every second.

* When the target end uses a high\-privilege account, DTS automatically creates the database at the destination. If the database name to be migrated does not comply with the target database naming conventions, you need to create the database at the destination before the migration task.

* During user migration, if some source database accounts do not support migration, ensure that business operations are not affected by the absence of these accounts.

* During migration, if there are `CREATE TABLE` or `RENAME TABLE` operations on the source end, select the entire database containing the table or the entire database where the table is renamed to when configuring the migration object. Otherwise, the newly created or renamed table will not migrate to the destination.

* When the migration object is not the entire database, OnlineDDL operations are not supported. Meanwhile, incremental migration does not automatically migrate newly added objects and their changes.

* The migration object granularity can be either database or table. If tables are selected as the migration objects, other objects such as views, triggers, functions, or stored procedures will not be migrated to the target end.

* To ensure data migration performance and task stability, the source TRIGGER and EVENT will migrate only after the incremental migration completes.

* During the pre\-check, if you ignore the alert and start the migration task, it may lead to data inconsistencies and pose business risks.

* When creating a data migration task via express network, the system creates several network cards by default in your selected VPC, and the network cards are mounted by default to the subnet you selected. The network card name format is `dts_shuttle_********`.

* During data migration, if duplicate primary key values or unique key values are encountered in the target database, DTS will not retain the conflicting data at the destination. Instead, the data from the source will overwrite the data at the destination. When a conflict overwrite occurs, if there is a table with the same name in the target database, it may cause data inconsistency issues as detailed below. It is recommended to use table name mapping or delete or rename the table with the same name in the target database to avoid data inconsistency and reduce business risks.

   * When the table structure is consistent, the migrated data overwrites records in the target table with the same primary key or unique key values as in the source database.

   * When the table structure is inconsistent, initialization of data may fail, and only partial column data can be migrated.

* Do not perform frequent DDL operations on the same table, as repeated DDL operations may cause DTS metadata update failures and risk transmission interruptions. Avoid this by spacing DDL operations at least 1–3 seconds apart in the console.

## Supported SQL operations

The supported SQL operations for incremental migration are shown in the following table.

|**Operation type** |**SQL statement** |
|---|---|
|**DML** |INSERT, UPDATE, DELETE |
|**DDL** |* ALTER TABLE, ALTER VIEW<br><br>* CREATE FUNCTION, CREATE INDEX, CREATE PROCEDURE, CREATE TABLE, CREATE VIEW<br><br>* DROP INDEX, DROP TABLE, DROP FUNCTION, DROP PROCEDURE<br><br>* RENAME TABLE<br><br>* TRUNCATE TABLE |

11. Optional. If a pre\-check has been performed for the created task, you can confirm whether to restart the pre\-check based on the prompts. If you need to restart, click **OK** in the **Whether to restart the pre\-check** dialog box.

   * If the instances of the source and target databases are not modified, there is no need to restart the pre\-check.

   * If you modify the source and target database instance information or the migration task parameters, it is recommended to restart the pre\-check to avoid task startup failures or interruptions.

12. On the **Pre\-check** configuration wizard page, perform the following actions based on the check result:

   * Click **Details** in the **Actions** column of the pre\-check results to view detailed alert and failure messages. After modifying the databases and tables accordingly, click **Retry**.

   * Click **Ignore** in the **Actions** column to ignore the alert and continue starting the migration task. You can also click **Ignore all** to ignore all alert messages with one click.

      > **tip**

      * > If you choose to **Ignore** the alert and start the migration task, it may cause data inconsistencies and business risks.

      * > For details about the pre\-check, refer to [Pre\-check items](https://docs.byteplus.com/en/docs/DTS/consumption_checkpoints).
