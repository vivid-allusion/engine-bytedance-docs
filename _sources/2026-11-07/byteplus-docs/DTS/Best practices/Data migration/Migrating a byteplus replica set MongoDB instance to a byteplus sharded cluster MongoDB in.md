This topic takes a volcano engine replica set MongoDB instance and a volcano engine sharded cluster MongoDB instance as examples to describe how to migrate a replica set instance to a sharded cluster instance.

<span id=".5YmN5o-Q5p2h5Lu2"></span>
## Prerequisites


* A database and an account for Document Database for MongoDB have been created. For detailed operations, refer to [Create instance](https://docs.byteplus.com/en/docs/mongodb/create-instance) and [Create account](https://docs.byteplus.com/en/docs/mongodb/create-account).

* Confirm the network connectivity and service availability of the source and target databases before creating a data migration task.

* You can also prepare the migration objects in the source and target databases according to the instructions in the Pre\-check items. For more details, refer to [Pre-check items (MongoDB)](https://docs.byteplus.com/en/docs/DTS/consumption_checkpoint_items_mongodb).


<span id=".5rOo5oSP5LqL6aG5"></span>
## Precautions


* If **incremental migration** is not selected, do not write new data to the source instance during data migration to ensure data consistency.

* To ensure real\-time data consistency, it is recommended to select schema migration, full data migration, and incremental data migration.

* Since full data migration performs concurrent `insert` operations, the collection in the target database generates fragments. Therefore, the storage space of the collection in the target database will be larger than that of the collection in the source database after the full migration is complete.

* During data migration, if duplicate primary key values or unique key values are encountered in the target database, DTS will not retain the conflicting data at the destination. Instead, the data from the source will overwrite the data at the destination. When a conflict overwrite occurs, if there is a table with the same name in the target database, it may cause data inconsistency issues as detailed below. It is recommended to use table name mapping or delete or rename the table with the same name in the target database to avoid data inconsistency and reduce business risks.

   * When the table structure is consistent, the migrated data overwrites records in the target table with the same primary key or unique key values as in the source database.

   * When the table structure is inconsistent, initialization of data may fail, and only partial column data can be migrated.

* When migrating a replica set MongoDB to a sharded cluster MongoDB, most CRUD operations can migrate smoothly; however, some oplog\-dependent operations might not perform as expected under the sharded environment, such as batch updates or certain DDL scenarios.

## Limits

<span id=".5bqU55So6ZmQ5Yi2"></span>
### Application limits


|**Type** |**Description** |
|---|---|
|Source database limits |* Bandwidth requirements: Adequate egress bandwidth is required on the source database server. Failure to meet this prerequisite will lead to suboptimal migration performance.<br><br>* The collection of objects to be migrated must contain a primary key or unique constraint, and the fields must be unique. Otherwise, duplicate data may occur in the target database.<br><br>* If the migration object is at the collection level and needs to be edited (e.g., collection name mapping), each migration task only supports migrating up to 1,000 collections. If this limit is exceeded, an error will appear after task submission. In this case, it is recommended to split the collections to be migrated and configure the task in batches.<br><br>* To perform incremental migration, complete the following configuration:<br><br>   * Enable Oplog logs. Otherwise, an error will be reported during the pre\-check phase, and the migration task can not start.<br><br>   * It is recommended that the Oplog be retained for at least 7 days during full migration. To adjust the Oplog size, refer to [Change the size of the Oplog](https://www.mongodb.com/docs/v4.0/tutorial/change-oplog-size/). You can also clean the oplog generated by the DTS source database after the full migration completes and the task runs. |
|Other limits |* It is recommended that the source and target Document Database for MongoDB databases be the same version, or migrate from a lower version to a higher one to ensure compatibility. If you migrate from a higher version to a lower version, there may be database compatibility or data loss issues.<br><br>* Migrating data from admin and local databases is not supported.<br><br>* Transaction information is not retained, that is, transactions in the source database are converted into single records when migrated to the target database.<br><br>* Prior to executing data migration, assess the performance of both source and target databases. It is advised to perform the migration during off\-peak business hours. Otherwise, during full migration, DTS consumes certain read/write resources on both source and target databases, which may lead to an increase in database load.<br><br>* The storage space of the target Document Database for MongoDB database must be greater than the storage space occupied by the source Document Database for MongoDB database. |


<span id=".5pON5L2c6ZmQ5Yi2"></span>
### Operation limits

Operation limits of the source database:


* During the schema and full migration phases, do not perform schema changes to databases or collections. Otherwise, the data migration task will fail.

* If only full data migration is performed, do not write new data to the source database, or the source and target data will be inconsistent.


<span id=".5pWw5o2u5bqT5pyA5bCP5p2D6ZmQ562W55Wl"></span>
## Minimum database permission policy

The account used for data migration must have the following permissions:


* The source database has the `FIND` permission for the objects to be migrated.

* Source database `changestream` permission.

   <div data-tips="true" data-tips-type="tip" data-tips-is-title="true" data-wrapper-indent="1">tip   </div>
   

   <div data-tips="true" data-tips-type="tip" data-wrapper-indent="1">This permission is required for incremental migration.   </div>
   

* The target database requires permissions such as `INSERT`, `UPDATE`, DELETE, `DROPDATABASE`, `DROPCOLLECTION`, `CREATE`, `CREATEINDEX`, and `DROPINDEX`.

   |**Validation type** |DTS automatically generates validation types based on the database type and migration type, and does not support modification.    |**Validation object** |Select the object to be verified as needed.<br><br><br>* **Consistent with the migration task**: The object to be verified matches the object to be migrated, meaning all migration objects are verified.<br><br>* **Custom**: Select the object to be verified as needed. |
   |**Startup settings** |Configure the timing of data verification in the migration task.<br><br><br>* **Automatic start**: The data verification task starts automatically along with the progress of the migration task.    |**Billing type** |Currently, only **Pay\-as\-you\-go** is supported and can not be modified. |
   

10. Click **Pre\-check**.

11. On the **Pre\-check** configuration wizard page, perform the following actions based on the check result:

   * Click **Details** in the **Actions** column of the pre\-check results to view detailed alert and failure messages. After modifying the databases and tables accordingly, click **Retry**.

   * Click **Ignore** in the **Actions** column to ignore the alert and continue starting the migration task. You can also click **Ignore all** to ignore all alert messages with one click.

   * <div data-tips="true" data-tips-type="tip" data-wrapper-indent="1">If you choose to <strong>Ignore</strong> the alert and start the migration task, it may cause data inconsistencies and business risks.   </div>
   

   * <div data-tips="true" data-tips-type="tip" data-wrapper-indent="1">For details about the pre\-check, refer to <a href="https://docs.byteplus.com/en/docs/DTS/consumption_checkpoints">Pre\-check items</a>.   </div>
   

10. At the bottom\-right of the **Pre\-check** page, click **Confirm order**.

11. On the **Confirm order** configuration wizard page, confirm the configuration information again. Read the Service\-Specific Terms for BytePlus Database Products and Services and check **I have read and agree to Service\-Specific Terms for BytePlus Database Products and Services**, and click **Create and start a task**.


After successfully creating the data migration task, you can return to the DTS console to view the data migration task information on the data migration task list. For more information, refer to [Viewing migration tasks](https://docs.byteplus.com/en/docs/DTS/viewing_a_migration_task).
