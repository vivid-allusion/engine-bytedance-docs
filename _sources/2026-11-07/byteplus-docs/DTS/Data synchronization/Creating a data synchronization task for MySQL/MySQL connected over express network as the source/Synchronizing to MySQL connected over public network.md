This topic introduces how to create a MySQL connected over express network synchronization task to MySQL connected over public network in the Database Transmission Service (DTS) console.

## Prerequisites

* Set the source information as needed, as detailed below:

   * When using VPN to perform data migration, the local network where the self\-managed database is located has been connected to BytePlus via VPN gateway. For detailed steps, refer to [Building a cloud VPC and on-premises multi-data-center network interconnection](https://docs.byteplus.com/en/docs/vpn/Connecting-a-virtual-private-cloud-to-multiple-data-centers).

   * If data migration requires a dedicated line connection, you need to establish a dedicated line connection between a single cloud VPC and a single on\-premises data center network.   For more information, refer to [Configuring direct connections](https://docs.byteplus.com/en/docs/directconnect/Quick-start#.6YWN572u5LiT57q_6L-e5o6l).

* A self\-managed instance and its database for RDS for MySQL have been set up in the public network environment.

* When your instance connects via the VPC, the subnet of the VPC must communicate with the source or target database. To allow DTS to access instances in the VPC normally, add the subnet CIDR block to the source or target database allowlist or security group rules. For more information, refer to [Adding the CIDR block of the DTS server](https://docs.byteplus.com/en/docs/DTS/Adding_the_CIDR_block_of_the_DTS_server).

* When the access method of the database instance is self\-managed over the Internet and access restrictions are enabled, add the DTS server IP addresses to the allowlist or security group of the database instance before creating the database transmission task. DTS server IP addresses vary by region, as detailed below:

   * DTS server IP addresses in China (Guangzhou), China (Shanghai), and China (Beijing) are `221.194.189.0/27,157.148.90.32/27,180.184.132.64/27,61.129.54.64/27,220.196.172.32/27,117.135.143.32/27,220.196.168.32/27,116.132.250.32/27,111.45.13.32/27,125.88.248.32/27,180.153.35.32/27,220.181.65.32/27,220.181.65.64/27`.

   * DTS server IP addresses in Asia Pacific (Johor) are `101.47.0.32/27,220.181.65.32/27,220.181.65.64/27,101.47.65.192/27,101.47.65.32/27`.

   * DTS server IP addresses in Asia Pacific (Jakarta) are `221.194.189.0/27,157.148.90.32/27`.

   * DTS server IP addresses in China (Hong Kong) are `101.47.0.32/27,220.181.65.32/27,220.181.65.64/27,101.47.65.192/27,101.47.65.32/27`.

      For more information on the CIDR block of DTS servers, refer to [Adding the CIDR block of the DTS server](https://docs.byteplus.com/en/docs/DTS/Adding_the_CIDR_block_of_the_DTS_server).

* The network connectivity and service availability of the source and destination have been confirmed.

* Optional. Check each synchronization object in the source and target databases according to the instructions in the pre\-check items. For more information, refer to [Pre-check items (MySQL)](https://docs.byteplus.com/en/docs/DTS/consumption_checkpoint_items_mysql).

## Precautions

* When the source is self\-managed MySQL, pay attention to the following information:

   * During synchronization, if the source end switches to the primary, the synchronization task will fail.

   * If the source end performs a restart operation during synchronization, the synchronization task will be temporarily interrupted and automatically attempted to recover. If the task does not recover for a long time, [submit a ticket](https://console.byteplus.com/workorder/create/) for technical support.

   * Since the delay time of Database Transmission Service (DTS) is derived by comparing the timestamp of the last data synchronized to the destination with the current timestamp, the delay information may be inaccurate if the source end has not performed DML operations for a long time. If the delay time displayed for the task is too long, you can execute a DML operation in the source end to update the delay information.

      > **tip**

      > If the synchronization object is the entire database, you can create a heartbeat table that is updated or written with data every second.

* When the target end uses a high\-privilege account, DTS automatically creates the database at the destination. If the database name to be synchronized does not comply with the target database naming conventions, you need to create the database in the target database before the synchronization task.

* During the database and table structure initialization, DTS synchronizes foreign keys from the source database to the target database.

* During full initialization and incremental synchronization, DTS temporarily disables constraint checks and foreign key cascade operations at the Session level. When the task runs, if the source database has cascade update or delete operations, data inconsistency may occur.

* During incremental synchronization, if the target database already has the same primary key value or unique value, you can select the conflict handling method for DTS based on business needs, such as overwrite on conflict, abort on conflict, or ignore on conflict.

* During full initialization, if the target database already has the same primary key or unique value, DTS uses the conflict overwrite strategy, meaning the source data overwrites the target data.

* When a conflict overwrite occurs, if there is a table with the same name in the target database, it may cause data inconsistency issues or task failures as detailed below. It is recommended to use table name mapping or delete or rename the table with the same name in the target database to avoid data inconsistency and reduce business risks.

   * When the table structure is consistent, data from full synchronization overwrites records in the target table with the same primary key or unique key values as in the source database.

   * When the table structure is inconsistent, initialization of data may fail, and only partial column data can be synchronized or synchronization may fail.

* During synchronization, if there are `CREATE TABLE` or `RENAME TABLE` operations on the source end, select the entire database containing the table or the entire database where the table is renamed to when configuring the synchronization object. Otherwise, the newly created or renamed table will not synchronize to the destination.

* When creating a data synchronization task via express network, the system creates several network cards by default in your selected VPC, and the network cards are mounted by default to the subnet you selected. The network card name format is `dts_shuttle_********`.

|Source limits |* Database version: MySQL 5.6, 5.7, and 8.0 instances are supported.<br><br>* When the source database instance version is 5.6 or higher, `gtid_mode` and `enforce_gtid_consistency` must both be set to `ON`.<br><br>   > **tip**<br>   <br><br>   > When the MySQL version is earlier than 8.0 and the parameter `gtid_mode` is disabled, foreign key cascading deletion may fail during data synchronization, resulting in data differences.<br>   <br><br>* Bandwidth requirements: Adequate egress bandwidth is required on the source database server. Failure to meet this prerequisite will lead to suboptimal synchronization performance.<br><br>* Supports the `InnoDB` database storage engine. `MariaDB` database engine is not supported currently.<br><br>* Tables to be synchronized must have a primary key or a unique non\-null constraint, and their fields must be unique. Otherwise, the DTS task may fail because it can not obtain the logs, potentially leading to data loss.<br><br>* Tables with foreign key dependencies must be synchronized together, or data synchronization will fail.<br><br>* It is recommended that the number of tables in a single task should not exceed 20,000, and the number of databases should not exceed 1,000. For example:<br><br>         * unidirectional synchronization task: in a unidirectional incremental synchronization task, once application traffic has been switched over (i.e., writes have migrated to the destination), executing DDL operations on the source end is strictly prohibited. The source database should be used only for synchronization backtracking or read\-only queries.<br><br>         * Bidirectional synchronization task:When both databases accept application writes, executing DDL on either side may cause data loss or schema inconsistency on the peer database.<br><br><br>> **tip**<br><br><br>> When using online DDL tools such as gh\-ost or pt\-online\-schema\-change, temporary tables are created during schema changes. Data written to the target database during operations like RENAME or DROP on these temporary tables may be lost.<br><br><br><br>      * OnlineDDL support scope:<br><br>         * Do not write data to the target database during DDL synchronization, as it may result in data loss.<br><br>         * DTS supports synchronizing the following temporary tables (ensure the target database has write permissions):<br><br>            * gh\-ost: original table name `_ghc`, original table name `_gho`, original table name `_del`, `tp_{change ID}_ogt_{original table name}`, `tp_{change ID}_g_{original table name} tp_{change ID}_del_{original table name}`, `tp_{change ID}_d_{original table name}`.<br><br>            * pt\-osc: original table name `_new`, original table name `_old`.<br><br>         * Table mapping (renaming) is mutually exclusive with Online DDL temporary table synchronization, only one can be enabled at a time.<br><br>         * Even lightweight operations, such as adding a column to a small table, may cause DDL synchronization to fail if the temporary table exists for too short a duration. It is recommended to perform all such changes uniformly through DBW tickets. For detailed steps, refer to [lock-free schema change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-structural-change-ticket-onlineddl-ticket-for-mysql) or [lock-free data change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-sql-change-ticket-for-mysql).<br><br>      * Avoid frequent DDL operations: Repeatedly applying DDL to the same table may cause DTS metadata updates to fail, risking replication interruption. If reverse DDL synchronization is required, first adjust the DDL synchronization direction, then perform the operation. For detailed operations, refer to [adjusting the DDL synchronization direction of the bidirectional synchronization task](https://docs.byteplus.com/en/docs/DTS/Reversing_the_DDL_synchronization_direction_of_the_bidirectional_synchronization_task?lang=en).<br><br>* Special limitations<br><br>   * Table schema changes must be forward\-compatible and limited to the following safe DDL operations:CREATE TABLE, ADD COLUMN, MODIFY COLUMN (only to increase column length), CREATE INDEX, DROP INDEX.<br><br>   * Prohibited operations: Modifying column data types, dropping columns, or reducing column lengths are not allowed, as they may cause data inconsistency or replication interruption. |
|Bidirectional synchronization limits |When creating a bidirectional synchronization task, you need to pay attention to the following information:<br><br><br>* Data writing and conflict control<br><br>   * Single\-point write principle: for records with the same primary key, business key, or unique key, updates are allowed only on one node (source end or destination end).<br><br>      * If both ends update the data simultaneously, the system will automatically resolve the conflict based on the primary key conflict resolution strategy configured in the task.<br><br>      * It is recommended to avoid writing to the same primary key from both ends at the application layer.<br><br>   * Do not write non\-DTS data to the target database: During synchronization, do not write data to the target database via applications, scripts, or other tools, as this may cause primary key conflicts or data overwrites.<br><br>   * During grayscale evaluation, if the table contains an auto\-increment primary key, strictly evaluate the newly added data on the source end and destination to ensure no primary key value conflict. If not avoided in advance, primary key conflicts easily occur during bidirectional synchronization, leading to data inconsistency.<br><br>* Network and topology recommendations<br><br>   * Outbound Cloud Link Performance Risk:If the synchronization involves data transfer from BytePlus to a public cloud (outbound), network bandwidth or latency may cause performance bottlenecks. Creating a bidirectional synchronization task directly is not recommended.<br><br>   * Bidirectional synchronization consists of two independent unidirectional tasks (forward + reverse) that must be configured separately, with consistent filter rules and conflict resolution strategies. |
|Other limits |* It is recommended that the MySQL versions of the source and destination be consistent, or synchronize from a lower version to a higher version, to ensure compatibility.<br><br>* Prior to executing data synchronization, assess the performance of both source and target databases. Otherwise, during full data initiation, DTS consumes certain read/write resources on both source and target ends, which may lead to an increase in database load.<br><br>* During synchronization, the target database may generate a large number of Binlog files, causing the target disk usage to be much higher than that of the original instance. It is recommended that you modify the storage policy of the target database Binlog before or during synchronization to avoid Binlog files from occupying too much storage space.<br><br>* For data synchronization tasks with database or table name mapping, the mapping may not take effect after the stored procedure synchronization and function are synchronized.<br><br>* If the source end is MySQL 8.0, when configuring synchronization tasks, you must manually grant the relevant data synchronization permissions directly to the following accounts:<br><br>   * The accounts for the source or target end are granted relevant permissions through the Role.<br><br>   * The accounts that need to perform User synchronization are granted relevant permissions through the Role.<br><br>* Currently only supported synchronization table, view, stored procedure and function. |
