Database Transmission Service (DTS) provides various types of database migration services. This topic uses creating a migration task from BytePlus RDS for MySQL to another BytePlus RDS for MySQL as an example to introduce how to create and start a data migration task through Database Transmission Service (DTS).

## Prerequisites

* An instance and database for RDS for MySQL have been created. For details, refer to [Creating an instance (RDS for MySQL)](https://docs.byteplus.com/en/docs/RDS_for_MySQL/creating_an_instance_1) and [Creating a database](https://docs.byteplus.com/en/docs/RDS_for_MySQL/creating_a_database).

* Confirm the network connectivity and service availability of the source and target databases before creating a data migration task.

* You can also prepare the migration objects in the source and target databases according to the instructions in the Pre\-check items. For more information, refer to [Pre-check items (MySQL)](https://docs.byteplus.com/en/docs/DTS/consumption_checkpoint_items_mysql).

## Precautions

* Since the delay time of Database Transmission Service (DTS) is derived by comparing the timestamp of the last data migrated to the target database with the current timestamp, the delay information may be inaccurate if the source database has not performed DML operations for a long time. If the delay time displayed for the task is too long, you can execute a DML operation in the source database to update the delay information.

   > **tip**

   > If the migration object is the entire database, you can create a heartbeat table that is updated or written with data every second.

* When the target database uses a high\-privilege account, DTS automatically creates the database at the destination. If the database name to be migrated does not comply with the target database naming conventions, you need to create the database at the destination before the migration task.

* Do not write new data to the source database instance during data migration when incremental migration is not selected to ensure data consistency.

* During user migration, if some source database accounts do not support migration, ensure that business operations are not affected by the absence of these accounts.

* When the migration object is not the entire database, OnlineDDL operations are not supported. Meanwhile, incremental migration does not automatically migrate newly added objects and their changes.

* The migration object granularity can be either database or table. If tables are selected as the migration objects, other objects such as views, triggers, functions, or stored procedures will not be migrated to the target database.

* During migration, if there are `CREATE TABLE` or `RENAME TABLE` operations on the source end, select the entire database containing the table or the entire database where the table is renamed to when configuring the migration object. Otherwise, the newly created or renamed table will not migrate to the destination.

* During data migration, if duplicate primary key values or unique key values are encountered in the target database, DTS will not retain the conflicting data at the destination. Instead, the data from the source will overwrite the data at the destination. When a conflict overwrite occurs, if there is a table with the same name in the target database, it may cause data inconsistency issues as detailed below. It is recommended to use table name mapping or delete or rename the table with the same name in the target database to avoid data inconsistency and reduce business risks.

   * When the table structure is consistent, the migrated data overwrites records in the target table with the same primary key or unique key values as in the source database.

   * When the table structure is inconsistent, initialization of data may fail, and only partial column data can be migrated.

* Do not perform frequent DDL operations on the same table, as repeated DDL operations may cause DTS metadata update failures and risk transmission interruptions. The mitigation measures are as follows:

   * Perform DDL operations with intervals of 1 to 3 seconds.

   * Perform DDL operations using [Lock-free schema change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-structural-change-ticket-onlineddl-ticket-for-mysql) of Database Workshop (DBW).

## Limits

|**Type** |**Description** |
|---|---|
|Source database limits |* Database version: RDS for MySQL 5.7 and 8.0 instances are supported.<br><br>* When the instance version of the source database is greater than or equal to 5.6, the parameter `gtid_mode` is set to `ON`.<br><br>   > **tip**<br>   <br><br>   > When the MySQL version is earlier than 8.0 and the parameter `gtid_mode` is disabled, foreign key cascading deletion may fail during data synchronization, resulting in data differences.<br>   <br><br>* Bandwidth requirements: Adequate egress bandwidth is required on the source database server. Failure to meet this prerequisite will lead to suboptimal migration performance.<br><br>* Data migration supports storage engines including `InnoDB`, `MyISAM`, and `RocksDB`. During data migration, if the source database is not using the `InnoDB` storage engine, the system automatically converts it to `InnoDB`. MariaDB database engine is not supported currently.<br><br>* Partitioned tables are not supported when converting the MyISAM storage engine to the InnoDB storage engine.<br><br>* Tables to be migrated must have a primary key or a unique non\-null constraint, and their fields must be unique. Otherwise, data inconsistency may occur.<br><br>* To perform incremental migration, the Binlog logs must meet the following requirements:<br><br>   * The Binlog feature must be enabled, and the parameter `binlog_format `set to` row`, `binlog_row_image` set to `full`. Otherwise, pre\-check will report an error, and data migration tasks can not start successfully.<br><br>   * Binlogs must be retained for at least 24 hours, and a retention period of more than seven days is recommended. Otherwise, the DTS task may fail because it can not obtain logs, potentially leading to data loss.<br><br>* Tables with foreign key dependencies must be migrated together, or data migration will fail.<br><br>* It is recommended that the number of tables in a single task should not exceed 20,000, and the number of databases should not exceed 1,000. When a large number of databases and tables need to be migrated, it is recommended to split them into multiple tasks. |
|Target database limits |* Database version: RDS for MySQL 5.7 and 8.0 instances are supported.<br><br>* The migration account privileges of the target database will affect the use of views, stored procedures, and functions. The specific limits are as follows:<br><br>   * When the migration account of the target database has `SET_USER_ID` permission, the limits for views, stored procedures, and functions are as follows:<br><br>      * Views, stored procedures, and functions will retain the original `definer` and `sql_security`.<br><br>      * The views, stored procedures, and functions can be used normally only after the account migration task is completed or the corresponding account is manually created in the target database.<br><br>   * When the migration account of the target database does not have or support `SET_USER_ID` permission, after migrating views, stored procedures, and functions, the `definer` will be replaced by the migration account, and `sql_security` will be set to `invoker`.<br><br>      > **tip**<br>      <br><br>      > Only MySQL 8.0 supports setting `SET_USER_ID` permission.<br>       |
|DDL limitations |* Operation limits<br><br>   * General rules<br><br>      * DDL operations are prohibited during initialization: Do not execute DDL during link creation, schema migration, or full data migration—otherwise, the task will fail.<br><br>      * When business writes occur on the destination, executing DDL on the source end may cause data loss. For example: in incremental migration tasks, once the business traffic switches completely (i.e., writes have migrated to the destination), executing DDL on the source end is strictly forbidden, as it may result in severe consequences such as data loss or structural inconsistency on the destination. At this stage, any DDL operations must be performed on the destination. The source is only for migration backtracking or read\-only queries.<br><br><br>> **tip**<br><br><br>> When using online DDL tools such as gh\-ost or pt\-online\-schema\-change, temporary tables are created during schema changes. Data written to the target database during operations like RENAME or DROP on these temporary tables may be lost.<br><br><br><br>      * OnlineDDL support scope:<br><br>         * Do not write data to the target database during DDL migration, as it may result in data loss.<br><br>         * DTS supports migrating the following temporary tables (ensure the target database has write permissions):<br><br>            * gh\-ost: original table name`_ghc`, original table name`_gho`, original table name`_del`, `original table name_del`, `tp_{change ID}_ogt_{original table name}`, `tp_{change ID}_g_{original table name} tp_{change ID}_del_{original table name}`, `tp_{change ID}_d_{original table name}`.<br><br>            * pt\-osc: original table name `_new`, original table name `_old`.<br><br>         * Table mapping (renaming) is mutually exclusive with Online DDL temporary table migration, only one can be enabled at a time.<br><br>         * Even lightweight operations, such as adding a column to a small table, may cause DDL migration to fail if the temporary table exists for too short a duration. It is recommended to perform all such changes uniformly through DBW tickets. For detailed steps, refer to [lock-free schema change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-structural-change-ticket-onlineddl-ticket-for-mysql) or [lock-free data change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-sql-change-ticket-for-mysql).<br><br>      * Avoid frequent DDL operations: Repeatedly applying DDL to the same table may cause DTS metadata updates to fail, risking replication interruption. You can avoid this issue by:<br><br>         * When performing DDL operations via the console, allow a minimum interval of 1–3 seconds between consecutive operations.<br><br>         * Prefer using DBW lock\-free schema change tickets to execute DDL operations. For detailed steps, refer to [lock-free schema change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-structural-change-ticket-onlineddl-ticket-for-mysql) or [lock-free data change tickets](https://docs.byteplus.com/en/docs/DBW/creating-a-lock-free-sql-change-ticket-for-mysql).<br><br>      * Cross\-database DDL restrictions: If a database is not included in the Migration object, DDL affecting migrated databases (such as cross\-database views or foreign keys) cannot be executed on it; otherwise, the Migration task will fail.<br><br>* Special limitations<br><br>   * Table schema changes must be forward\-compatible and limited to the following safe DDL operations:`CREATE TABLE`, `ADD COLUMN`, `MODIFY COLUMN` (only to increase column length), `CREATE INDEX`, `DROP INDEX`.<br><br>   * Prohibited operations: Modifying column data types, dropping columns, or reducing column lengths are not allowed, as they may cause data inconsistency or migration interruption. |
|Other limits |* It is recommended that the source and target MySQL databases be the same version, or migrate from a lower version to a higher one to ensure compatibility. If you migrate from a higher version to a lower version, there may be database compatibility or data loss issues.<br><br>* Prior to executing data migration, assess the performance of both source and target databases. It is also advised to perform the migration during off\-peak business hours. Otherwise, during full data migration, DTS consumes certain read/write resources on both source and target databases, which may lead to an increase in database load.<br><br>* During migration, the target database may generate a large number of Binlog files, causing the target database disk usage to be much higher than that of the original instance. It is recommended to adjust the Binlog retention policy in the target database before migration or synchronization to prevent excessive storage usage by Binlog files.<br><br>* For data migration tasks with database or table name mapping, the mapping may not take effect after the stored procedure and function are migrated.<br><br>* If the source database is MySQL 8.0, when configuring migration tasks, you must manually grant the relevant data migration permissions directly to the following accounts:<br><br>   * The accounts for the source or target database are granted relevant permissions through the Role.<br><br>   * The accounts that need to perform User migration are granted relevant permissions through the Role.<br><br>* Only migration of tables, views, stored procedures, functions, triggers, and events is supported.<br><br>* Explanation of `DEFINER` and `SQL SECURITY` behavior in MySQL migration for views, stored procedures, and functions:<br><br><br>In data transmission tasks migrating to MySQL, if migrating views, stored procedures, or functions, and the migration account at the target database does not have (or cannot be granted) the `SET_USER_ID` permission, the `DEFINER` of related objects may be replaced by the migration account, and the `SQL SECURITY` may be adjusted to `INVOKER`.<br><br>If the original `DEFINER / SQL SECURITY` behavior needs to be retained, manually recreate or correct the definition of the related objects on the target after the migration is complete. |

## Supported SQL operations

The supported SQL operations for incremental migration are shown in the following table.

|**Operation type** |**SQL** **operation statements** |
|---|---|
|**DML** |INSERT, UPDATE, DELETE |
|**DDL** |* ALTER TABLE, ALTER VIEW<br><br>* CREATE FUNCTION, CREATE INDEX, CREATE PROCEDURE, CREATE TABLE, CREATE VIEW<br><br>* DROP INDEX, DROP TABLE, DROP FUNCTION, DROP PROCEDURE<br><br>* RENAME TABLE<br><br>* TRUNCATE TABLE |

## Database account minimum permission policy

|**Database** |**Schema migration** |**Full migration** |**Incremental migration** |
|---|---|---|---|
|Source database |`SELECT` permission |`SELECT` permission |`REPLICATION SLAVE`, `REPLICATION CLIENT`, and `SELECT` permissions. |
|Target database |Read/Write permissions |Read/Write permissions |Read/Write permissions |

Adjust appropriately based on the read and write pressure of the source and target databases.<br> |

8. Click **Data validation configuration**.

9. On the **Create migration task** page, locate the **Configure data verification** wizard, and configure the following parameters.

   |**Parameter** |**Description** |
   |---|---|
   |**Data verification**<br><br> |Select whether to configure the data verification function directly when creating a migration task (built\-in).<br><br><br>* **Enable**: Configure data verification tasks directly when creating a data migration task.<br><br>* **Disable**: Do not configure data verification tasks when creating a data migration task. |
   |**Validation type** |DTS automatically generates validation types based on the database type and migration type, and does not support modification. For more information on validation types, refer to [Background](https://docs.byteplus.com/en/docs/DTS/configuring_data_validation#.6IOM5pmv5L-h5oGv). |
   |**Validation object** |Select the object to be verified as needed.<br><br><br>* **Consistent with the migration task**: The object to be verified matches the object to be migrated, meaning all migration objects are verified.<br><br>* **Custom**: Select the object to be verified as needed. |
   |**Startup settings** |Configure the timing of data verification in the migration task.<br><br><br>* **Automatic start**: The data verification task starts automatically along with the progress of the migration task. Automatic start occurs when full migration (if any) is complete and the delay of incremental migration is 0.<br><br>* **Manually start**: The data verification task does not start automatically with the migration task progress. You must manually start the data verification at the appropriate time. It is recommended to manually start data verification only after full migration (if any) is complete and the delay of incremental migration is 0. Otherwise, verification results may be inaccurate. |
   |**Billing type** |Currently, only **Pay\-as\-you\-go** is supported and can not be modified. |

10. Click **Pre\-check**.

11. Optional. If a pre\-check has been performed for the created task, you can confirm whether to restart the pre\-check based on the prompts. If you need to restart, click **OK** in the **Whether to restart the pre\-check** dialog box.

   * If the instances of the source and target databases are not modified, there is no need to restart the pre\-check.

   * If you modify the source and target database instance information or the migration task parameters, it is recommended to restart the pre\-check to avoid task startup failures or interruptions.

12. On the **Pre\-check** configuration wizard page, perform the following actions based on the check result:

   * Click **Details** in the **Actions** column of the pre\-check results to view detailed alert and failure messages. After modifying the databases and tables accordingly, click **Retry**.

   * Click **Ignore** in the **Actions** column to ignore the alert and continue starting the migration task. You can also click **Ignore all** to ignore all alert messages with one click.

      > **tip**

      * > If you choose to **Ignore** the alert and start the migration task, it may cause data inconsistencies and business risks.

      * > For details about the pre\-check, refer to [Pre\-check items](https://docs.byteplus.com/en/docs/DTS/consumption_checkpoints).

13. At the bottom\-right of the **Pre\-check** page, click **Confirm order**.

14. On the **Confirm order** configuration wizard page, confirm the configuration information again. Read the Service\-Specific Terms for BytePlus Database Products and Services and check **I have read and agree to Service\-Specific Terms for BytePlus Database Products and Services**. Then perform the following operations.

   * Click **Create and start a task**. After successfully creating the data migration task, data migration starts immediately.

   * Click **Create task**. After successfully creating the data migration task, you need to manually start data migration at the right time.

After successfully creating the data migration task, you can return to the DTS console to view the data migration task information on the data migration task list. For more information, refer to [Viewing migration tasks](https://docs.byteplus.com/en/docs/DTS/viewing_a_migration_task).
