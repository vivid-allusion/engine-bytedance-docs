This topic put forward recommendations on how to use Cache for Redis to develop business code.


|Recommendation level |Description |
|---|---|
|Strong recommendation |* Use Redis only as a cache. The reason is that Redis' persistence and primary\-secondary replication are performed asynchronously, making it unsuitable for applications with high requirements for data reliability and consistency.<br><br>* Set the cache expiry time.<br><br>* Monitor server timeout errors and set up client retry mechanisms to handle traffic throttling or failover.<br><br>* Set Redis instance alerts for monitoring memory usage, CPU usage, and other metrics. For more details, refer to [Monitoring and alerts](https://docs.byteplus.com/en/docs/redis/monitoring-metric).<br><br>* Pay close attention to indicators related to big keys (such as the **Maximum byte number per single response**) and manage them in a timely manner. For more details, refer to [Big key analysis](https://docs.byteplus.com/en/docs/redis/big-key-analysis).<br><br>* Enable the connection pooling function in the client SDK to avoid using a single connection and set up a reconnection mechanism. The specific reasons are as follows:<br><br>   * When a single connection is used, a slow query would lead to long queuing for subsequent queries, meaning it takes longer to obtain a free connection. In the event of the connection being suspended, it would also affect many other queries.<br><br>   * You may use the following formula to calculate the number of connections required for the client SDK connection pool:<br><br>      The number of connections required = expected QPS ÷ QPS of a single connection.<br><br>      The QPS of a single connection can be calculated based on the average time per request in one second. For example, if the average time per request for the client is 1 ms, then a single connection can process up to 1,000 QPS. To reach 20,000 QPS using a single client, 20 connections need to be set. It is generally advisable to create a certain level of redundancy by, for example, setting 30 connections.<br><br>   * If the database contains a substantial number (for example more than 1 million) of keys, we recommend that you enable the load balancer feature.<br><br>* Set generous retry timeouts (for example, more than 200 ms) to avoid retry storms caused by timeouts. |
||* Avoid using the same Redis instance in different services.<br><br>* Avoid storing too many sub\-keys (we recommend that you cap the total number of sub\-keys at 1,000) in data structures such as hash, set, and zset.<br><br>* Avoid operating too much data with a single command. For example, using commands like `HGRTALL` or `KEYS` on hash structures with a large number of elements. )<br><br>* When using pipeline, avoid submitting too many commands at once (we recommend that you keep them below 100).<br><br>   Although there is no hard limit on the number of commands that can be executed in a single pipeline operation, each pipeline command uses a socket connection exclusively. Submitting too many commands in a single pipeline affects the allocation of the connection pool and may also result in slow queries. The actual total number of commands that can be executed is also limited by the socket buffer and Redis request queue size. The more commands, the more likely it is to cause timeouts or blocking, which can affect cluster stability.<br><br>* Avoid having any single key with a length exceeding 128 bytes or a value exceeding 10 KiB.<br><br>* Avoid using commands such as `SCAN`, `ISCAN`, `HSCAN`, `SSCAN`, or `ZSCAN` with a limit count exceeding 500.<br><br>* Avoid `O(N)` commands such as `LRANGE`, `ZRANGE`, `SMEMBERS`, `SUNION`, or `SINTER` where a single request return value exceeds 100 KiB.<br><br>* Avoid using Lua (EVAL, EVALSHA) scripts. For suggestions on how to use Lua scripts, refer to [Lua scripting guide](https://docs.byteplus.com/en/docs/redis/lua-user-guide).<br><br>* Avoid using Redis transactions. The reasons are as follows:<br><br>   * Redis transactions do not have rollback capabilities, so atomicity cannot be guaranteed.<br><br>   * During the execution of a Redis transaction, even if a command reports an error, the remaining commands will still be executed. |
||* Do not adopt the cache double deletion strategy of "deleting the cached data first, updating the database, and finally deleting the cache again with a delay". This prevents cache penetration and even database downtime issues due to the deletion of hot spot data.<br><br>* Do not use `KEYS`, `FLUSHDB`, `FLUSHALL` or other disabled commands.<br><br>* Do not use the `HGETALL` command (the `HSCAN` command is recommended if traversal is required). |
|Suggestions |* Update the database first, and then delete the cache.<br><br>* Add a small random value to the cache expiration time to prevent cache avalanche.<br><br>* The length of a single key should not exceed 44 bytes. Wherever possible, try to maintain the length of the key to less than 12 bytes.<br><br>* Compress the text type string data (GZIP or ZSTD compression algorithm is recommended) before storing it in Redis.<br><br>* Pay close attention to hot keys and manage them appropriately. For more details, refer to [Hot key analysis](https://docs.byteplus.com/en/docs/redis/hot-key-analysis).<br><br>* Pay close attention to slow queries. For more details, refer to [Querying slow logs](https://docs.byteplus.com/en/docs/redis/query-slow-log).<br><br>* Use pipelines instead of commands that require batch tasks such as `MGET` and `MSET`. |
||* Avoid directly executing the `DEL` commands on data such as Hash, Set, and Zset. If necessary, we recommend that you use commands such as `HSCAN`, `SSCAN`, and `ZSCAN` to perform progressive deletion.<br><br>* Avoid batch deleting more than 500 cache keys at once (within one second). |
