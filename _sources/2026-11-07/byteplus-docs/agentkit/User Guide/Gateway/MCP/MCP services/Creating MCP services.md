An MCP service is a unified service access capability provided by AgentKit that connects external tools, system interfaces, or existing services to the platform for agents to call. By creating an MCP service, you can incorporate external capabilities from different sources and in various forms into a unified management and invocation system, reducing integration complexity and improving capability reuse and integration efficiency.

## Background information

The MCP protocol is designed to simplify the interaction between Large Language Models (LLMs) and external tools, APIs, and services. Through standardized interfaces, LLMs can call external APIs, run scripts, access databases, and more, expanding their capability boundaries. The transport layer of MCP supports multiple protocols to ensure efficient and secure data transmission. Typical application scenarios include intelligent assistants and agents, enterprise\-level knowledge management, developer tools and IDE integration, and multimodal data integration. In addition, MCP provides an interactive debugging tool to help developers efficiently test and debug relevant servers and clients.

## MCP protocol version

The MCP protocol version defines message format, capability declaration, initialization method, and invocation behavior. Streamable HTTP is a message transport mechanism. The two are distinct concepts. When an MCP service is exposed over Streamable HTTP, clients still need to select the appropriate MCP protocol version based on what they support. AgentKit MCP services are compatible with the following MCP protocol versions:

* **`2026-07-28`**

* **`2025-11-25`**

* **`2025-06-18`**

* **`2025-03-26`**

For more information about compatibility with MCP protocol version **`2026-07-28`** **,**  its stateless mechanism, and how to use Multi Round\-Trip Requests (MRTR), see [MCP protocol version compatibility](https://docs.byteplus.com/en/docs/agentkit/MCP_protocol_version_compatibility).

## Creation method descriptions

AgentKit supports three creation methods: **Deploy MCP service**, **Import MCP service**, and **HTTP to MCP**, which apply to three scenarios respectively: deploying from scratch, connecting existing services, and transforming existing APIs.

* If no platform\-based service is available for direct integration and you want AgentKit to manage deployment and access, choose "**Deploy MCP service**".

* If you already have a mature and available MCP service, choose **Import MCP service** for a shorter integration cycle.

* If what you have accumulated is mainly HTTP APIs rather than native MCP services, choose **HTTP to MCP** to reduce transformation costs.

> **warning**

> **The MCP service is a paid feature**. Charges apply regardless of the creation method.

* > Different creation methods involve different billing items. Billing items also differ between services connected to a shared gateway and those connected to a dedicated gateway. We recommend reviewing the relevant fees before creating a service. For more information, see [Billing instructions](https://docs.byteplus.com/en/docs/agentkit/Billing_items).

* > After creating an MCP service using "Deploy MCP service", if your resource usage is relatively stable, you can purchase a package as needed.

|**Creation method** |**Application scenarios** |
|---|---|
|**Deploy MCP service** |* Applicable to scenarios where you need to deploy an MCP service directly in AgentKit. It supports deploying self\-developed/public MCP services and providing external access, and it also supports automatically converting a local MCP service to a remote MCP service.<br><br>* The focus is on completing the integration starting from deployment, **which suits scenarios that involve creating new services or require unified management**. |
|**Import MCP service** |* Applicable to scenarios where an MCP service is already available and you want to quickly integrate it. ## Deploy an MCP service

### Prerequisites

* Confirm the source of the MCP service to be deployed (self\-developed/public), and confirm the basic environment and access requirements needed for deployment.

* If you use the ** Import MCP service** or **HTTP to MCP** method in dedicated gateway mode and the backend service is accessed through a fixed domain name over a private network, establish network connectivity in advance.

   * **Establish network connectivity between the dedicated gateway and the backend service**. For detailed configuration, see [Direct Connect - Best practices](https://docs.byteplus.com/en/docs/directconnect/best-practices-overview?lang=en).

   * **Allow the service ports and UDP/TCP port 53 required by DNS** (if you use a custom DNS port, use the actual port). For example, if the backend service is deployed on a third\-party cloud, create a Private DNS inbound endpoint. In the "Internal resolution/Service address" section of Private DNS on the third\-party cloud, create an inbound endpoint, select the third\-party VPC that is already connected to the BytePlus VPC, and record the inbound service IP address. By standard, the DNS port is 53. We recommend that you allow both UDP 53 and TCP 53.

      * Tencent Cloud: For configuration details, see[ Private DNS service address](https://cloud.tencent.com/document/product/1338/123753) in the Tencent Cloud official documentation.

      * Alibaba Cloud: For configuration details, see [Inbound endpoint in the Alibaba Cloud](https://help.aliyun.com/zh/dns/pvtz-inbound-endpoint) official documentation.

### Lifecycle description

When creating an MCP service, you need to configure instance information. The platform scales in or out based on actual requests. The specific rules are as follows:

* **Scale out:**  When request concurrency exceeds the capacity of a single instance, the platform may create new instances. The number of instances will not exceed the configured "Maximum instance count".

* **Scale in:**  When traffic decreases and scale\-in conditions are met, the platform reclaims excess instances. If "Minimum instance count" is set to **0**, the platform may scale in to **0** instances.

> **warning**

* > Stateful MCP stores sessions in instance memory. Scale\-in, deployment, abnormal exit, instance replacement, or routing changes may all invalidate existing sessions.

* > Even if "Minimum instance count" is greater than **0**, sessions are not guaranteed to remain valid indefinitely. **We recommend that the caller retain the ability to reconnect or retry after a session becomes invalid**.

## HTTP to MCP

### Prerequisites

* Prepare the corresponding API file and backend service address in advance; otherwise, the conversion and integration cannot be completed.

* Currently, only Swagger 2.0 and OpenAPI 3.0 format API description files are supported. If the backend has only nonstandard API documentation, such as a Word document or wiki page, convert it into an OpenAPI 3.0\-compliant file before integration. For the API file specifications, see [MCP service API file specifications and examples](https://docs.byteplus.com/en/docs/agentkit/MCP_service_API_file_specifications_and_examples).

### Procedure

1. Log in to the [AgentKit console](https://console.byteplus.com/agentkit).

2. In the left\-side navigation pane, select "Gateway \> MCP integration", and click the "MCP Service" tab.

3. Click "Create MCP service". Then, refer to the table below to configure the parameters. After configuration, click "Create" to complete the operation.
