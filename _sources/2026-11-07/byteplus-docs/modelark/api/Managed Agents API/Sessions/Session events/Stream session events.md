`GET https://ark.ap-southeast.bytepluses.com/api/v3/sessions/{session_id}/events/stream`

Subscribe to events of the main session thread through the SSE (Server\-Sent Events) protocol over a long\-lived HTTP connection. The event scope is as follows:

* Events in the main session thread are returned in full.

* For sub\-agent threads, lifecycle events, collaboration messages, custom tool calls, and tool authorization events that require client handling are returned.

* Built\-in tool calls that the host needs to execute in a self\-hosted environment are also returned.

> **Tip**

* > Thread\-related events use `session_thread_id` to identify the thread they belong to.

* > A self\-hosted worker executes built\-in tool calls in session event order and sends back results by `tool_use_id`; do not rely on `session_thread_id` for result routing.

* > Thinking, regular replies, spans, and preview frames from sub\-agent threads are not returned, and tool execution results generated by the server are not expanded. Receive them through the corresponding [thread event stream](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/stream-thread-events-api). Tool results and tool authorization replies sent back by the client are still returned, so you can verify whether the results have been delivered.

* > This API does not support resuming after disconnection. After the connection is interrupted, you can query events generated during the interruption through [List session events](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/list-events-api), and then re\-establish the streaming connection.

* > After the connection is established, `: ready` is received first. The server then sends `: heartbeat` about every 15 seconds; before a service instance exits, it may send `: server draining, reconnect`. All lines that start with a colon are SSE comments. The client should ignore them and set the read timeout to at least two heartbeat intervals.

* > The server sends parsable event JSON through `data:` lines and may omit explicit `event:` lines. The connection ends through EOF, `session.deleted`, or an active client disconnect; whether business processing is complete is determined by session status events.

For the event parameter structure, see [Session event structure reference](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/sessions-events-reference-v2).

## Request parameters

### Path parameters

**session_id** `string` `Required`  |  Session ID

Specify the session ID for the events you want to subscribe to, in the form `sesn-...`.

### Query parameters

> Passed as URL query string.

**event_deltas** `array`  |  Preview event types

Specify the event types for which preview content should be received through `event_start` and `event_delta`. Currently, `agent.message` and `agent.thinking` are supported.

If this parameter is not provided, no preview frames are returned. Preview frames may be incomplete; treat the complete event returned later as authoritative.

> **Tip**

> Multiple values can be passed in multiple times (`?event_deltas=agent.message&event_deltas=agent.thinking`) or as a comma\-separated list (`?event_deltas=agent.message,agent.thinking`).

> **Note**

> The parameter name must be `event_deltas`, not `event_deltas[]`. The server ignores unknown parameter names and unsupported event types and continues to return HTTP 200; ignored values do not produce preview frames.

## Response parameters

### Streaming response (SSE)

**data** `string`  |  Event JSON data

The server returns event JSON through `data:` lines. SSE responses may not contain an `event:` line; in this case, the client can still read the `data:` content as the default `message` event.

Parse `type` based on the event kind:

* For a complete event, the top\-level `type` indicates the business event type.

* For a preview frame, the top\-level `type` is fixed as `event_start` or `event_delta`. Here, `event_start.event.type` indicates the business event type being previewed.

Complete events and each preview frame contain their own `id`, `type`, and `processed_at`. Preview frames include the following delta information:

* `event_start.event` contains the `id` and `type` of the event being previewed.

* `event_delta.delta` contains the delta `type`, `content`, and `index`.

The top\-level `id` of a preview frame is the ID of the current frame; `event_start.event.id` and `event_delta.event_id` point to the complete event being previewed.

Preview frames may be incomplete; the complete event with the same previewed event ID is authoritative.

`session_thread_id` is not a public parameter and is returned only when it is explicitly listed in the corresponding event structure.

Built\-in tool calls that the host needs to execute in a self\-hosted environment also appear in the session event stream. The client sends back results by `tool_use_id` and does not rely on `session_thread_id`.

For the complete structure, see [Session event structure reference](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/sessions-events-reference-v2).
