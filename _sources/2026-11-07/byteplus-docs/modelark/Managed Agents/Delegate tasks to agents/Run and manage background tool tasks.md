When a Bash command or video generation takes a long time to complete, you can run tools in the background in the following two ways:

* Explicitly ask the agent to run a Bash command in the background, or call `video_generate`, which runs in the background by default. After the tool submits the task, it immediately returns `task_id`.

* Let the Bash command run directly. The system waits 60 seconds by default. If the command still has not completed, the system converts the same task to run in the background and returns `task_id`.

Background tool tasks are child resources under a session. They are generated by tool calls and do not provide a separate creation API. Business applications can call [List session tasks](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/list-session-tasks-api), [Query session task](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/get-session-task-api), and [Cancel session task](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/cancel-session-task-api) to manage tasks. In a session that supports background tasks and is compatible with the current configuration, the main agent automatically gets the `task_list`, `task_get`, and `task_kill` tools without manual configuration.

## Prerequisites

Before you start, you need:

* **An API key**: Configure it as the `ARK_API_KEY` environment variable. For details, see [API key management](https://ai.byteplus.com/ark/region:ap-southeast-1/apiKey).

* **An agent**: For details, see [Define an agent](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/define-agent).

* **An environment**: For details, see [Configure cloud environments](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/configure-cloud-environment).

* Create a session that uses a cloud environment. To learn how to create one, see [Start session](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/start-session).

* Configure the tools that the agent needs to run. Bash uses the basic toolset, and video generation uses the multimodal toolset. For details, see [Tools](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/tools).

* Install `curl` locally, and set the API key, session ID, and optional session thread ID:

   ```bash
   export ARK_API_KEY="<ARK_API_KEY>"
   export SESSION_ID="<SESSION_ID>"
   export SESSION_THREAD_ID="<SESSION_THREAD_ID>"
   ```

`SESSION_THREAD_ID` is used to limit the list to the specified session thread. If you do not need to filter by thread, you can omit this environment variable and remove `session_thread_id` from the request URL.

For details about the base URL and authentication method in the examples in this section, see [Base URL and authentication](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/base-url-and-authentication).

## Understand how background tasks run

Background tasks are suitable for tool calls that take a long time and should not block the session main thread. The following tools are currently supported:

|Tool |How it enters the background |Runtime behavior |
|---|---|---|
|`bash` |Explicitly ask the agent to run the command in the background, or the command still has not completed after running normally for 60 seconds. |When explicitly run in the background, `task_id` is returned immediately. When run normally, the system waits 60 seconds by default. If the same task has not completed, it is then converted to a background task and `task_id` is returned. |
|`video_generate` |Runs in the background by default |Returns `task_id` after submission. After video generation is complete, the agent reads the result. |

For example, after you send "Run the tests in the background and summarize the failed cases after completion", the agent starts a Bash background task and obtains `task_id`. If subsequent messages do not depend on the task result, the agent can continue processing. Steps that depend on the task result continue after the task is complete.

> **Note**

> As long as there are unfinished background tasks or pending completion notifications, the session resource's `status` remains `running`. The main thread may temporarily be waiting, but this does not mean the session has entered `idle`. The task completion notification wakes up the main thread and lets the agent continue processing. Do not determine whether a background task is complete only by polling the session status. Query the corresponding task's `state` instead.

A task goes through the following states from submission to completion:

|Status |Note |
|---|---|
|`queued` |The task has been created and is waiting to run. |
|`running` |The tool is running, or the tool artifacts are being saved to the session workspace. |
|`succeeded` |The task was executed successfully. When you query a single task, the response contains `result`. |
|`failed` |The task failed. Troubleshoot the cause based on `error_code`, `error_message`, and `result`. |
|`cancelled` |The task has been canceled and will not continue to run. |
|`unknown` |The task status cannot be determined currently. Keep the `task_id` and query again later. The status may return to `running` or change to the actual final status, so do not treat this status as success. |

## List tasks in a session

Call `GET /sessions/{session_id}/tasks` to view the background tasks that have been generated in the specified session. A normally executed `bash` command appears in the list only after it is converted into a background task:

```Bash
curl -sS --fail-with-body \
  "https://ark.ap-southeast.bytepluses.com/api/v3/sessions/${SESSION_ID}/tasks? session_thread_id=${SESSION_THREAD_ID}&state=queued,running&limit=20" \
  -H "Authorization: Bearer $ARK_API_KEY"
```

For complete request parameters and response parameters, see [List session tasks](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/list-session-tasks-api).

The list is returned in descending order by creation time. You can use the following query parameters to narrow the scope:

|Parameter |Type |Note |
|---|---|---|
|`state` |string |Filter by status. Separate multiple statuses with half\-width commas, for example, `queued,running`. |
|`session_thread_id` |string |Return only tasks created by the specified session thread. If omitted, tasks for the entire session are returned. |
|`limit` |integer |The number of tasks per page. The default is 20, and the maximum is 50. |
|`cursor` |integer |The `next_cursor` from the previous page response. If omitted or set to `0`, the query starts from the latest task. |

`items` in the response contains only task summaries and does not contain `result`. If there is a next page, continue querying with `next_cursor`:

```Plain Text
{
  "items": [
    {
      "task_id": "task-20260910173330-54321",
      "tool": {
        "name": "video_generate",
        "tool_use_id": "toolu_02",
        "description": "Generate a city night video"
      },
      "session_id": "sesn-20260910171500-abcde",
      "session_thread_id": "sthr-20260910171500-abcde",
      "state": "running",
      "summary": "Generate a city night video",
      "created_at": 1789032810494,
      "started_at": 1789032813926
    }
  ],
  "next_cursor": 1024
}
```

Record the `task_id` of the target task:

```bash
export TASK_ID="<TASK_ID>"
```

## Query task details

Call `GET /sessions/{session_id}/tasks/{task_id}` to query the latest status of a task:

```Bash
curl -sS --fail-with-body \
  "https://ark.ap-southeast.bytepluses.com/api/v3/sessions/${SESSION_ID}/tasks/${TASK_ID}" \
  -H "Authorization: Bearer $ARK_API_KEY"
```

For the complete response structure, see [Query session task](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/get-session-task-api).

When querying a single task, if the task status is `succeeded`, `failed`, `cancelled`, or `unknown`, the response includes `result`; it is not returned when the task status is `queued` or `running`. Depending on the task status and tool type, the response includes the following information:

* **`result.status`**: the tool execution result. Valid values are `ok` or `error`.

* **`result.content`**: the text result returned by the tool.

* **`result.meta_info`**: information used to locate artifacts or logs. A Bash task can return the exit code and paths to standard output and standard error logs; a video generation task can return the generation task ID, the video URL, and the artifact path in the session workspace.

* **`error_code`** ** and ** **`error_message`**: Error information when the task fails, is canceled, or has an unknown status, and the server has recorded the failure reason.

* **`finished_at`**: The time when the task enters a terminal state, as a Unix timestamp in milliseconds.

> **Note**

> The list API does not return `result`. To read artifact paths, log locations, or error details, you must query the individual task.

## Cancel a task

Call `POST /sessions/{session_id}/tasks/{task_id}/cancel` to cancel a background task that is no longer needed:

```Bash
curl -sS --fail-with-body \
  "https://ark.ap-southeast.bytepluses.com/api/v3/sessions/${SESSION_ID}/tasks/${TASK_ID}/cancel" \
  -H "Authorization: Bearer $ARK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{}'
```

For the complete API description, see [Cancel session task](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/cancel-session-task-api).

The API returns HTTP 200 to indicate that the cancellation request has been processed, but this does not mean the task has necessarily stopped. Determine the result based on `state` and `message` in the response:

|Response |Meaning |Next steps |
|---|---|---|
|`state` is `cancelled` |The task has been canceled. |No need to keep waiting for the task result |
|`state` is `queued` or `running`, with no `message` |The cancellation request has been accepted, but the task status has not been refreshed yet. |Query the task again after 3 seconds. |
|`state` is `queued` or `running`, with a `message` |The task could not be canceled at the current execution stage, such as when video generation has already started. |Continue querying until the task ends naturally. |
|Another terminal state is returned |The task had already ended before the cancellation request was processed. |Handle the result according to the returned status. |

If you need to stop a specific task, use the cancel task API first.`user.interrupt` interrupts the current execution process of the session, finds tasks in the current session whose status is `queued` or `running`, and then attempts to cancel them one by one. This process is not atomic. If cancellation of a single task fails, other tasks will still continue to be processed; it also does not guarantee that all tasks have stopped. When multiple background tasks exist in a session, do not use it as a substitute for cancellation by `task_id`.

## Handle events after task completion

When a background task completes, the platform sends a result notification to the corresponding session. As long as the session has not been explicitly interrupted, terminated, or deleted, this notification wakes the main thread, allowing the agent to read the result and continue processing the original task. Late notifications after an explicit interruption do not automatically resume execution; when a session has been terminated or deleted, late notifications also do not restore the session. Business applications still receive agent replies and status events through session SSE:

1. Keep the SSE connection open and receive agent replies generated after task completion.

2. If the SSE connection is interrupted, re\-establish the connection first, and then query historical events to fill the interruption window.

3. Record `task_id`. Even if you miss real\-time events, you can use [List session tasks](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/list-session-tasks-api) to locate the task, and then use [Query session task](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/get-session-task-api) to read the latest status and result.

4. When the session is explicitly interrupted, query the final result according to step 3. When the agent needs to continue processing, send a new user message; the new message starts a new processing round.

5. When the session has been terminated, late results do not resume execution. When further processing is needed, create a new session and initiate the subsequent steps again. For details, see [Start session](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/start-session).

6. When a task's `state` is `unknown`, retain `task_id` and query it later. This status may recover to `running` or an actual terminal state and cannot be used as evidence of success.

For details about the subscription order for session events and how to backfill after disconnection, see [Session event stream](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/session-event-stream).

## Limitations

* Background tool tasks currently support `bash` and `video_generate`.

* Each session can run at most 32 tool tasks at the same time, including `bash` commands that have not yet been converted to background tasks. After the limit is reached, new tasks fail and return `ToolTaskLimitExceeded`.

* Sessions using a self\-hosted environment do not currently support background tool tasks.

* When the main agent is configured with custom tools, the session does not currently support background tool tasks.

* Sub\-agents do not currently support executing tools in the background.

* A task can only be generated by an agent's tool call and cannot be proactively created through the Session Task API.

* Whether a task can be canceled or not depends on the tool's execution stage. If video generation has already started, the cancellation request will not terminate generation or stop billing.
