This topic describes how to configure a self\-hosted environment from scratch, start a worker by using the Go, Python, or Java SDK, and complete a full session tool execution.

## What you will complete

* Create an environment of type `self_hosted` in the console

* Configure a separate instance ID for each worker

* Configure and securely store an API key for the worker

* Select the Go, Python, or Java SDK and start the worker on an enterprise host

* Create a session bound to the self\-hosted environment

* Send a user message so that the primary agent runs Bash and file tools on the enterprise host

* Verify the tool execution result, the terminal state of the session, and the worker status

## Core concepts

|Concept |Note |
|---|---|
|**Environment** |Agent runtime configuration. When `type` is `self_hosted`, it indicates a self\-hosted environment. |
|**Worker** |An enterprise\-deployed process that polls the work queue and runs the primary agent's `bash`, `read`, `write`, `edit`, `glob`, and `grep` in the enterprise sandbox |
|**Work Item** |A task item generated by ModelArk for a session that requires tool execution. The work ID is the same as the session ID. |
|**Worker instance ID** |Identifies the worker instance that claims and executes work. When ack and heartbeat use the same non\-empty ID, the original worker can resume work that stopped because the heartbeat lease expired. |
|**API Key** |The authentication credential used by workers and business applications to call ModelArk APIs. The permissions of the API key used by a worker depend on the account, project, and credential policy it belongs to, and are not automatically limited to accessing only a specific environment. |

## Workflow

The following is the end\-to\-end workflow for a self\-hosted environment:

1. An enterprise administrator creates a self\-hosted environment and prepares an API key for the worker.

2. Enterprise operations personnel start the worker on an enterprise host, and the worker starts polling the work queue.

3. The business application uses a business API key to create a session, establishes an event stream, and then sends a user message.

4. The ModelArk control plane generates a work item, and the worker claims and acknowledges it.

5. When the primary agent calls `bash`, `read`, `write`, `edit`, `glob`, or `grep`, the worker executes it in the enterprise sandbox and returns the result.

6. When the primary agent calls web, MCP, or multimodal tools, ModelArk completes the execution. When the agent calls custom tools, the business application completes the execution.

7. The tool result drives the next turn of inference.

8. Repeat steps 5\-7 until the session enters `idle` or a terminal state.

9. The worker completes the work item and continues polling.

> **Note**

> A self\-hosted environment does not move all tools to the worker. The file and network policies of the enterprise sandbox constrain only the six tools executed by the worker. They do not constrain web, MCP, or multimodal tools executed on the ModelArk side.

## Prerequisites

Before you start, make sure the following prerequisites are met:

* The Managed Agents service has been activated, and an agent has been created (see [Quick start](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/quick-start-code)).

* Prepare an enterprise\-managed Linux host or isolated container that meets the following requirements:

   * `/bin/bash` is available.

   * The `/workspace` directory is writable.

   * An Ark Runtime SDK has been selected, and the runtime environment has been prepared according to the README of the corresponding repository: [Go](https://github.com/volcengine/ark-runtime-go), [Python](https://github.com/volcengine/ark-runtime-python), or [Java](https://github.com/volcengine/ark-runtime-java).

* The worker host can access the ModelArk API (`https://ark.ap-southeast.bytepluses.com/api/v3`) over outbound HTTPS. No inbound port needs to be opened.

* The host where the business application runs has `curl` 7.76 or later and `jq` installed.

* A business API key is available. It is used to create sessions and held by the business application.

* A ModelArk API key used by the worker is available and held by the worker host.

> **Note**

> There is currently no independent worker credential that can access only a specified environment. The worker uses a standard ModelArk API key to access the work queue. The actual permissions depend on the account, project, and credential policy that the API key belongs to. Do not mistake `MA_ENVIRONMENT_ID` for an authorization scope limit.

> We recommend assigning separate API keys to the business application and the worker, and storing them separately in Secret Manager. The permissions of the worker API key are not automatically limited to a single environment. Separate credentials make individual rotation and revocation easier, but they cannot replace account\-level and project\-level permission controls.

## Step 1: Create a self\-hosted environment

Create a self\-hosted environment on the [Environments](https://ai.byteplus.com/ark/region:ap-southeast-1/managed-agents/environments) page in the console or by using the API.

Create an environment by using the API:

```Bash
export ARK_API_KEY="<BUSINESS_API_KEY>"

ENVIRONMENT_RESPONSE=$(curl --fail-with-body -sS https://ark.ap-southeast.bytepluses.com/api/v3/environments \
  -H "Authorization: Bearer $ARK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "my-self-hosted-env",
    "description": "A self-hosted environment for running internal enterprise tools",
    "config": {
      "type": "self_hosted"
    }
  }') &&
ENVIRONMENT_ID=$(printf '%s\n' "$ENVIRONMENT_RESPONSE" | jq -er \
  '.id | select(type == "string" and startswith("env-"))') &&
export ENVIRONMENT_ID &&
printf 'Environment ID: %s\n' "$ENVIRONMENT_ID"
```

> **Tip**

> The `type` of the `config` of a self\-hosted environment must be set to `self_hosted`. Dependencies (`packages`), environment variables (`env`), startup scripts (`setup_script`), and network policies (`networking`) are managed by the enterprise and are not defined in the environment configuration.

Response example:

```Plain Text
{
  "id": "env-20260822120000-xxxxx",
  "type": "environment",
  "name": "my-self-hosted-env",
  "config": {
    "type": "self_hosted"
  },
  "created_at": "2026-08-22T04:00:00Z"
}
```

The command reads `id` from the response, verifies that it starts with `env-`, and then writes it to `ENVIRONMENT_ID`. If the request returns HTTP 4xx/5xx, the response is not valid JSON, or the response does not contain a valid ID, subsequent commands will not run.

## Step 2: Configure the worker API key

Prepare a ModelArk API key for the worker that can access Managed Agents resources in the current account and project. For details about how to create an API key, see [API key management](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/manage-api-keys).

> **Note**

> The worker uses a standard ModelArk API key, not an environment\-specific credential. Do not assume that this key can only poll or acknowledge work items in the current environment. Use a separate project, a separate API key, Secret Manager, and worker\-side network policies to limit the risk scope.

On the worker host, write the `ENVIRONMENT_ID` obtained in step 1 to `MA_ENVIRONMENT_ID`, and then configure the worker API key:

```bash
export MA_ENVIRONMENT_ID="<ENVIRONMENT_ID>"
export MA_WORKER_ID="worker-prod-a-01"
export MA_WORKDIR="/workspace"
export ARK_API_KEY="<WORKER_API_KEY>"
# Optional: set ARK_BASE_URL only when overriding the SDK default endpoint.
export ARK_BASE_URL="https://ark.ap-southeast.bytepluses.com/api/v3"
```

Set `ARK_API_KEY` to the ModelArk API key used by the worker. The SDK uses `MA_ENVIRONMENT_ID` to identify the work queue, and uses `MA_WORKER_ID` in ack and heartbeat requests to identify the current worker. Set a unique, stable, non\-empty ID for each worker instance. Do not let multiple instances share the same ID.

When a work item enters `stopped` because its heartbeat lease expires, only the original worker that claimed the work item can use the same `MA_WORKER_ID` to restore it directly to `active` through a heartbeat. This process does not requeue the work item or hand it off to another worker. If no worker ID is set, or if the work stopped for another reason, it cannot be restored through heartbeat.

## Step 4: Start a persistent worker

Start `EnvironmentWorker` by using the SDK. The following example continuously polls the work queue and, after picking up a work item, creates a separate working directory for each session under `MA_WORKDIR`.

**Go**

Create `main.go`:

```go
package main

import (
    "context"
    "log"
    "os"
    "os/signal"
    "syscall"

    "github.com/volcengine/ark-runtime-go/arkruntime"
    "github.com/volcengine/ark-runtime-go/arkruntime/lib/environments"
)

func main() {
    apiKey := os.Getenv("ARK_API_KEY")
    baseURL := os.Getenv("ARK_BASE_URL")
    envID := os.Getenv("MA_ENVIRONMENT_ID")
    workdir := os.Getenv("MA_WORKDIR")
    if apiKey == "" || envID == "" {
        log.Fatal("ARK_API_KEY and MA_ENVIRONMENT_ID are required")
    }
    if workdir == "" {
        workdir = "/workspace"
    }

    clientOptions := make([]arkruntime.ConfigOption, 0, 1)
    if baseURL != "" {
        clientOptions = append(clientOptions, arkruntime.WithBaseUrl(baseURL))
    }
    client := arkruntime.NewClientWithApiKey(apiKey, clientOptions...)
    worker := environments.NewEnvironmentWorkerForClient(client, environments.EnvironmentWorkerOptions{
        EnvironmentID: envID,
        WorkerID:      os.Getenv("MA_WORKER_ID"),
        Workdir:       workdir,
    })

    log.Printf("worker starting for environment %s", envID)
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()
    if err := worker.Run(ctx); err != nil {
        log.Fatalf("worker exited with error: %v", err)
    }
}
```

**Python**

Create `worker.py`:

```python
import os
import signal
import sys

from arkruntime import Ark
from arkruntime.selfhosted import ClientAPI, EnvironmentWorker, EnvironmentWorkerOptions


def required_env(name):
    value = os.environ.get(name, "")
    if not value:
        raise RuntimeError(f"{name} is required")
    return value


client_options = {"api_key": required_env("ARK_API_KEY")}
if os.environ.get("ARK_BASE_URL"):
    client_options["base_url"] = os.environ["ARK_BASE_URL"]

client = Ark(**client_options)

worker = EnvironmentWorker(
    ClientAPI(client),
    EnvironmentWorkerOptions(
        environment_id=required_env("MA_ENVIRONMENT_ID"),
        worker_id=os.environ.get("MA_WORKER_ID", ""),
        workdir=os.environ.get("MA_WORKDIR", "/workspace"),
    ),
)

print(f"worker starting for environment {os.environ['MA_ENVIRONMENT_ID']}", file=sys.stderr)
for sig in (signal.SIGINT, signal.SIGTERM):
    signal.signal(sig, lambda _signum, _frame: worker.close())

try:
    worker.run()
finally:
    worker.close()
    client.close()
```

**Java**

In the Maven project's `src/main/java/` directory, create `SelfHostedWorkerExample.java`:

```java
import com.volcengine.ark.runtime.selfhosted.EnvironmentWorker;
import com.volcengine.ark.runtime.selfhosted.SelfHostedClient;

public class SelfHostedWorkerExample {
    public static void main(String[] args) {
        String environmentId = requiredEnv("MA_ENVIRONMENT_ID");
        String workerId = System.getenv("MA_WORKER_ID");
        String workdir = envOrDefault("MA_WORKDIR", "/workspace");

        SelfHostedClient.Builder clientBuilder = new SelfHostedClient.Builder()
                .apiKey(requiredEnv("ARK_API_KEY"));
        String baseUrl = System.getenv("ARK_BASE_URL");
        if (baseUrl != null && !baseUrl.isEmpty()) {
            clientBuilder.baseUrl(baseUrl);
        }

        SelfHostedClient client = clientBuilder.build();

        EnvironmentWorker worker = new EnvironmentWorker(
                client,
                new EnvironmentWorker.Options()
                        .environmentId(environmentId)
                        .workerId(workerId)
                        .workdir(workdir));

        System.out.printf("worker starting for environment %s%n", environmentId);
        Runtime.getRuntime().addShutdownHook(new Thread(worker::close, "ark-self-hosted-worker-shutdown"));
        try {
            worker.run();
        } finally {
            worker.close();
        }
    }

    private static String requiredEnv(String name) {
        String value = System.getenv(name);
        if (value == null || value.isEmpty()) {
            throw new IllegalArgumentException(name + " is required");
        }
        return value;
    }

    private static String envOrDefault(String name, String defaultValue) {
        String value = System.getenv(name);
        return value == null || value.isEmpty() ? defaultValue : value;
    }
}
```

Start the worker:

**Go**

```bash
go mod tidy
go run main.go
```

**Python**

```bash
python worker.py
```

**Java**

```bash
mvn -q exec:java -Dexec.mainClass=SelfHostedWorkerExample
```

Expected log output:

```Plain Text
worker starting for environment env-20260822120000-xxxxx
polling work queue...
```

`EnvironmentWorker` continuously polls the work queue. When the queue is empty, it keeps waiting and does not create sessions. Return to the environment details page in the console. The worker connection status should show "Online".

> **Note**

> If the worker still shows "Not connected", first check:

* > Whether `MA_ENVIRONMENT_ID` is correct

* > Whether `ARK_API_KEY` on the worker host is a valid ModelArk API key under the current account and project

* > If `ARK_BASE_URL` is set, confirm that the address matches the current ModelArk region.

* > Whether the system time on the worker host is accurate (excessive drift can cause signature verification to fail)

* > Whether outbound HTTPS can reach `https://ark.ap-southeast.bytepluses.com/api/v3`

## Step 5: Create a session, establish an event stream, and send a task

### 5.1 Create a session

Return to the business application terminal used in step 1, and create a session with the business API key. Do not reuse the worker API key in production:

```Bash
export ARK_API_KEY="<BUSINESS_API_KEY>"
export ARK_BASE_URL="https://ark.ap-southeast.bytepluses.com/api/v3"
export AGENT_ID="<AGENT_ID>"

: "${ENVIRONMENT_ID:?Run step 1 to create an Environment first}" &&
: "${AGENT_ID:?Set AGENT_ID to an existing Agent ID}" &&
SESSION_RESPONSE=$(curl --fail-with-body -sS https://ark.ap-southeast.bytepluses.com/api/v3/sessions \
  -H "Authorization: Bearer $ARK_API_KEY" \
  -H "Content-Type: application/json" \
  -d "$(jq -n \
    --arg agent "$AGENT_ID" \
    --arg environment_id "$ENVIRONMENT_ID" \
    '{agent: $agent, environment_id: $environment_id}')") &&
SESSION_ID=$(printf '%s\n' "$SESSION_RESPONSE" | jq -er \
  '.id | select(type == "string" and startswith("sesn-"))') &&
export SESSION_ID &&
printf 'Session ID: %s\n' "$SESSION_ID"
```

Replace `<AGENT_ID>` with the created agent ID. The command directly uses the `ENVIRONMENT_ID` saved in step 1 and writes the session ID to `SESSION_ID`. If the request fails or the response does not contain a valid ID, subsequent commands will not run.

Response example:

```Plain Text
{
  "id": "sesn-20260822120100-xxxxx",
  "status": "idle",
  "environment_id": "env-20260822120000-xxxxx"
}
```

### 5.2 Subscribe to the session event stream

In another terminal, establish an SSE connection through [Stream session events](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/stream-events-api):

```Bash
curl -N "https://ark.ap-southeast.bytepluses.com/api/v3/sessions/$SESSION_ID/events/stream" \
  -H "Authorization: Bearer $ARK_API_KEY" \
  -H "Accept: text/event-stream"
```

Wait until the server returns `: ready` before sending a user message. SSE pushes only events generated after the connection is established; if you send the message first, the business application will miss events that have already been generated.

### 5.3 Send the first event to start the agent

Creating a session alone does not trigger a task. Only after you submit the first `user.message` event through [Send session event](https://ai.byteplus.com/ark/region:ap-southeast-1/docs/send-event-api) will ModelArk generate a work item and write it to the work queue of the self\-hosted environment:

```Bash
curl -sS "https://ark.ap-southeast.bytepluses.com/api/v3/sessions/$SESSION_ID/events" \
  -H "Authorization: Bearer $ARK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "events": [{
      "type": "user.message",
      "content": [{
        "type": "text",
        "text": "Read /workspace/input.csv, generate a summary report, and write it to /workspace/output.md"
      }]
    }]
  }'
```

> **Tip**

> After the message is sent, the session changes from `idle` to `running`, and ModelArk generates a work item for this execution round and writes it to the environment's work queue. The business application does not create work items directly or call the Work API.

## Step 6: Verify the execution result

### 6.1 Worker side

You should see the following key events in the worker logs:

```text
work claimed: work_id=sesn-20260822120100-xxxxx
session started: session_id=sesn-20260822120100-xxxxx
tool call: bash, command=cat /workspace/input.csv
tool call: write, path=/workspace/output.md
session completed: session_id=sesn-20260822120100-xxxxx
work completed: work_id=sesn-20260822120100-xxxxx
```

Confirm that `/workspace/output.md` has been generated and that its content meets expectations.

### 6.2 Business application side

In the SSE connection established in step 5.2, confirm that the following events are received:

```text
user.message          Read /workspace/input.csv and generate a summary report
agent.tool_use        bash: cat /workspace/input.csv
agent.tool_result     (bash execution result)
agent.tool_use        write: /workspace/output.md
agent.tool_result     (write execution result)
agent.message         Completed. The summary report has been saved to /workspace/output.md
session.status_idle
```

### 6.3 Console side

On the environment details page, confirm the following:

|Page |Expected result |
|---|---|
|Overview |The worker is online. The number of `running` items increases during execution and drops after execution ends. |
|Work Items |You can find this work item by session ID. When a work item completes normally, its status changes to `queued`, `starting`, `active`, and `stopped` in sequence; when the original worker resumes work that was stopped because the lease expired, the status changes directly from `stopped` to `active`. |

## Production deployment methods

### Resident worker

Suitable for direct execution on VMs, standalone containers, or existing isolated nodes.`EnvironmentWorker.run()` / `EnvironmentWorker.Run()` manages the complete lifecycle: polling, acknowledgment, heartbeats, enterprise\-side tool execution, result return, and work completion.

To scale out, start multiple worker processes or pods first, and set a separate `MA_WORKER_ID` for each instance. Do not let multiple workers share the same session working directory.

### Separate sandbox per session

Suitable for running one pod per session in Kubernetes. The poller claims work items and creates pods. Inside each pod, call the SDK's `HandleItem` / `handle_item` to manage the complete lifecycle of the work item.

```go
poller := environments.NewWorkPollerForClient(ctx, client, environments.WorkPollerOptions{
    EnvironmentID: envID,
})

for poller.Next() {
    work := poller.Current()
    workID := getWorkID(work)
    workerID := "worker-" + workID
    createPod(work, map[string]string{
        "MA_WORK_ID":        workID,
        "MA_ENVIRONMENT_ID": envID,
        "MA_SESSION_ID":     workID,
        "MA_WORKER_ID":      workerID,
    })
}

workerID := os.Getenv("MA_WORKER_ID")
if workerID == "" {
    log.Fatal("MA_WORKER_ID is required")
}

worker := environments.NewEnvironmentWorkerForClient(client, environments.EnvironmentWorkerOptions{
    WorkerID: workerID,
    Workdir:  "/workspace",
})
worker.HandleItem(ctx, environments.HandleItemOptions{
    WorkID:        os.Getenv("MA_WORK_ID"),
    EnvironmentID: os.Getenv("MA_ENVIRONMENT_ID"),
    SessionID:     os.Getenv("MA_SESSION_ID"),
})
```

Before creating the pod, the poller reads the work ID from the work item, generates `MA_WORKER_ID`, and injects it into the pod together with `MA_WORK_ID`, `MA_ENVIRONMENT_ID`, and `MA_SESSION_ID`. When the pod process starts, it must verify that `MA_WORKER_ID` is not empty and pass it to `EnvironmentWorker`. When the pod process for the same work restarts or the pod is recreated, continue using the original `MA_WORKER_ID`; generate a new worker ID only for new work. This ensures that ack, heartbeat, and lease recovery use the same worker identity.

> **Note**

> The API key used by the worker should be mounted through a Kubernetes Secret, Secret Manager, or an equivalent mechanism. It must not be written in plaintext to the pod spec, image, working directory, or logs. Before the worker executes agent tools such as `bash`, it should clear environment variables that contain credentials.

## Running and troubleshooting

|Symptom |Check item |Fix |
|---|---|---|
|Worker not connected |API key, environment ID, network |Check whether `ARK_API_KEY` on the worker host is valid and can access the current account and project, and confirm that outbound HTTPS is reachable. |
|Work remains queued for a long time |Worker online status, number of worker instances |Confirm that the worker is online. Add more worker instances if necessary. |
|Heartbeat returns 412 |`MA_WORKER_ID`, `expected_last_heartbeat`, latest work status |Confirm that ack and heartbeat use the same worker ID, and use `last_heartbeat` from the previous response to continue renewing the lease. |
|Work stops because the lease expires |`stop_reason`, `MA_WORKER_ID`, `lease_extended` |The original worker uses the same ID to resume heartbeats. If the response is `active` and `lease_extended=true`, continue execution; otherwise, stop the current task and release resources. |
|Repeated tool execution |Worker execution ledger and whether the working directory is persistent |Check whether the existing result is reused directly for the same tool call ID. Server\-side idempotent handling of tool results applies only to result return and cannot prevent the worker from executing a local tool again. If the execution status cannot be confirmed, do not automatically retry operations with side effects. |
|No session result |Check work and session events separately |Confirm that the work item has been claimed and is `active`, and also check whether events contain error events. |

## Clean up resources

After confirming that the artifacts have been transferred, clean up in dependency order:

```Bash
# 1. Stop the worker (Ctrl+C or kill)
# 2. Confirm that no work is running
# 3. Delete the test session
: "${SESSION_ID:?Run step 5.1 to create a Session first}" &&
: "${ENVIRONMENT_ID:?Run step 1 to create an Environment first}" &&
curl --fail-with-body -sS -X DELETE "https://ark.ap-southeast.bytepluses.com/api/v3/sessions/$SESSION_ID" \
  -H "Authorization: Bearer $ARK_API_KEY" &&
# 4. Delete the test environment
curl --fail-with-body -sS -X DELETE "https://ark.ap-southeast.bytepluses.com/api/v3/environments/$ENVIRONMENT_ID" \
  -H "Authorization: Bearer $ARK_API_KEY"
```

> **Warning**

> Only delete resources that were created in this session and for which exact IDs were recorded. Never use fuzzy name matching for bulk deletion: Resources under an enterprise account may be shared by multiple people, and accidental deletion cannot be recovered.
