**File permissions** control the boundaries of agent operations on local files in the sandbox. Granular permission modes restrict file read, write, modify, and delete operations, preventing agents from tampering with or leaking sensitive local files and comprehensively protecting files on the device.

Two permission levels are supported: **Global default** and **Project configuration**. Each level is configured independently and does not affect the other. Project permissions take precedence over global default permissions, allowing unified global control and differentiated settings for individual projects.

* **Global default**: Governs all **sessions that are not bound to a project workspace** (draft sessions and standalone temporary sessions). All conversations that do not belong to a project follow this set of permission rules. You can switch between three permission modes: Read\-only, Full access, and Custom.

* **Project configuration**: Configures permissions independently for sessions in a specific project space. **These permissions take precedence over global default permissions**. When you enter a session bound to a project, the permission rules configured for that project take precedence and are not affected by the global default configuration. Four permission modes are supported: Workspace write, Read\-only, Full access, and Custom. Permissions are isolated across projects, meaning that the configuration for one project does not affect others.

## Considerations

1. Permission scope: All file permission modes primarily control **file write, modify, and delete operations**, and do not restrict file read operations by default.

2. Permission priority and isolation: Project\-level permissions take precedence over global default permissions. Project\-level and global configurations are independent, so changing a single configuration does not affect other scenarios.

3. Temporary permission override rule: When you switch to Full access, the directory allowlist constraint for the corresponding scope is temporarily lifted, but the command risk control rules on the device remain in effect.

4. Support for both assistants: Both the Local assistant and the Cloud assistant strictly enforce file permission checks. The Cloud assistant follows the same rules in the cloud sandbox, and the permission configurations for the two assistants are independent.

5. Troubleshooting: If an agent fails to write files, first check whether the directory is added to the allowlist for custom permissions and whether the current permission mode supports write operations.

## Applicable scenarios

1. **Security and compliance**: Apply read\-only or custom permissions to the global scope or sensitive projects to restrict agents' access to directories such as the system directory, the desktop, and private documents, preventing accidental file tampering and data leaks.

2. **Project data isolation**: Configure independent, differentiated permissions for different projects to isolate file operations between projects and prevent cross\-project misoperations and data mix\-ups.

3. **Routine project O&M**: For daily project development and debugging, use the default workspace write permission to balance security and operational convenience.

4. **Quick debugging**: For trusted, low\-sensitivity temporary debugging tasks, you can temporarily enable full access to simplify directory authorization and improve debugging efficiency.

## Switch file access permissions

1. Log in to the ArkClaw client locally.

2. Switch to the target ArkClaw.

3. Enter the main session or project session interface.

4. Click the "Request approval mode \> Current file system permission for sessions" button at the bottom of the chat box.

5. In the  **"Local sandbox permissions"**  section, switch the permission mode for  **"Global default"**  or the target project to  **"Custom permissions", "Read\-only", "Full access", or "Workspace write permission" (project only).**

## Manage custom permissions

When the local file permission is set to **Custom**, you can add writable directories to grant write access to specific local directories. After a directory is added, local file tools and terminal commands can perform write operations only in the added directories and their subdirectories. If a task attempts to write to an unauthorized directory, the operation is rejected due to insufficient permissions.

Permission configurations fall into two types:

* **Global default**: Applies to sessions that are not bound to a project workspace.

* **Project configuration**: Applies to a specific project, for example, the bytedance project at /Users/bytedance.

> **warning**

> If the restricted sandbox is unavailable on the current device, you cannot configure custom permissions, and the following message is displayed: "Unavailable restricted sandbox. File system boundaries cannot be enforced for this level."

### **Add a directory**

1. Log in to the ArkClaw client locally.

2. Switch to the target ArkClaw.

3. Enter the main session or project session interface.

4. Click the "Request approval mode \> Current file system permission for sessions" button at the bottom of the chat box.

5. On the **File permissions** tab, change the permission type of **Global default** or the target project to **Custom**.

6. Click "+ Add writable directory".

7. In the folder picker that appears, select the local path you want to authorize.

8. After the directory is added, the path and the time it was added are displayed in the directory list.

### **Delete a directory**

> **warning**

> After an authorized directory is deleted, ArkClaw can no longer access or perform operations on files under that directory. The local directory and its content are not affected.

1. Click the "Delete" button to the right of an added directory you want to delete.

2. In the dialog box that appears, click "Remove" to revoke the access authorization for the directory.
