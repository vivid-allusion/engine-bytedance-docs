本章介绍基于 HTTP、UDP 和 QUIC 协议的信令交互。

<span id="685b18b6"></span>
## HTTP 信令交互

**优势**：兼容性优秀，支持浏览器/客户端互通；可靠性高。

**劣势**：


* 在弱连接环境下（如往返时延 RTT 较长或网络信号不稳定），成功率较低；

* 回放请求的返回调用结果可能较慢或超时，主要原因是信令数据包体积较大以及 TCP 重传。


**传输方式**：标准 SDP 信令基于 HTTP 协议时，数据在客户端与服务器之间传输。

下图展示了基于 HTTP 协议的 SDP 信令交互流程。

<span>![图片](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/a43c049e72374f6aaaf28b188b5b2ac1~tplv-goo7wpa0wc-image.image) </span>

<span id="99cb380c"></span>
### **信令请求流程**


1. 客户端生成 Offer SDP；

2. 客户端通过 HTTP 协议向信令服务器发送数据请求（offer request），传递接口行为信息（Offer SDP）；

3. 服务器收到 Offer SDP 请求后，执行回源到指定媒体数据源站，查询音视频媒体信息，并生成标准 answer SDP；

4. 服务器向发起请求的客户端发送返回调用结果（answer response）；

5. SDP 双方完成协商后，建立[ICE](https://docs.byteplus.com/en/docs/byteplus-media-live/docs-rtm-terminology#ice)连接。客户端随后从服务器查询网络地址并完成握手；

6. RTP 传输启动，回放根据传统 P2P 连接流程开始。


<span id="9c81a2b3"></span>
### 停止回放流程

停止回放流程有两种方案。更多信息请参见[结束媒体传输](https://docs.byteplus.com/en/docs/byteplus-media-live/docs-rtm-ending-transmission)。


* 推荐方案：通过 RTCP 媒体反馈通道向媒体服务器发送 RTCP Bye 消息；

* 备选方案：使用 UDP Socket 向信令服务器发送停止命令，由信令服务器控制媒体服务器停止数据传输；


<span id="1b02ad57"></span>
## UDP 信令交互

UDP 信令交互分为两种类型：**UDP 标准路径**和**UDP 快速路径**。

<span id="d1deb45f"></span>
### UDP 标准路径


* **优势**：首帧渲染速度更快，瞬时加载和成功率更高。

* **劣势**：在要求认证加密的合规区域存在安全相关问题，且无法支持网页浏览器。

* **传输方式**：通过 MiniSDP 协议以 UDP 传输；单个 UDP 数据包请求即可传递完整 SDP 压缩信息。


下图展示了 UDP 协议下 MiniSDP 信令的交互流程。

<span>![图片](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/bd4be5472b094b48a5211afa65faade1~tplv-goo7wpa0wc-image.image) </span>

<span id="2ed5f750"></span>
#### **信令请求流程**


1. 客户端生成 offer SDP；

2. 客户端根据指定协议将标准 SDP 压缩为 MiniSDP；

3. 客户端通过 UDP Socket 在 offer request 中向信令服务器发送 MiniSDP（Offer SDP）；

4. 服务器收到 MiniSDP 请求后，根据指定协议提取并还原为标准 SDP；

5. 服务器根据标准 SDP 回源到 FLV 数据源站，查询音视频媒体信息，并生成标准 SDP；

6. 服务器根据指定协议将标准 SDP 压缩为 MiniSDP；

7. 服务器通过 UDP Socket 在 answer response 中向客户端返回 MiniSDP（Answer SDP）；

8. 客户端接收到 MiniSDP 请求，并根据指定协议提取并还原该请求为标准 SDP；

9. RTP 传输开始，并按照传统 P2P 连接流程开始回放。


<span id="8064ac92"></span>
#### **停止回放流程**

停止回放的流程与 HTTP 信令一致。详情请参见[结束媒体传输](https://docs.byteplus.com/en/docs/byteplus-media-live/docs-rtm-ending-transmission)。

<span id="ec7392aa"></span>
### UDP 快速路径

UDP 快速路径通过复用信令和媒体数据传输通道，消除 ICE 建立时间对首帧渲染造成的开销。

<span id="5276804a"></span>
#### 信令请求流程

与 UDP 标准路径不同，使用快速路径时，交互连接的建立过程与媒体数据的传输和解码并行进行。这意味着服务器在 ICE 连接建立过程中，同时向客户端发送媒体数据以进行解码和渲染。


* **UDP 标准路径**：服务器在 ICE 连接建立后向客户端发送媒体数据（RTP 包）；

* **UDP 快速路径**：UDP 信令通道被复用。服务器在信令成功但 ICE 连接尚未建立时，通过信令通道发送媒体数据（RTP 包）。一旦 ICE 连接建立，服务器切换至新的 socket 媒体通道，并继续发送 RTP 包。


下图展示了 UDP 快速路径的信令请求流程图。

<span>![图片](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/1e263a715486429b84b80e09e5288d0a~tplv-goo7wpa0wc-image.image) </span>


1. 客户端通过 MiniSDP 与服务器建立信令通道；

2. 服务器向客户端发送远端应答；

3. 客户端建立 ICE 连接的同时，服务器将包含音视频数据的 RTP 数据包发送至信令 socket。

4. 客户端激活 WebRTC，并在客户端内部的视频接收引擎（video_recv_pipeline，PeerConnection）中使 RTP 数据包能够访问传输模块；

5. ICE 连接建立后，服务器将 RTP 数据包发送至传输模块 socket。


<span id="08aa990c"></span>
#### 停止回放流程

停止回放的流程与 HTTP 信令一致。详情请参见[结束媒体传输](https://docs.byteplus.com/en/docs/byteplus-media-live/docs-rtm-ending-transmission)。

## QUIC 信令交互

QUIC 信令交互是一种增强安全性的交互方案。QUIC 信令交互与 HTTP/UDP 信令交互的区别如下：


1. 标准化 SDP 信令理想情况下通过支持 CDN 的 HTTP/HTTPS 进行传输，但这会导致信令建联时间最长，并且在弱连接环境下成功率相对较低。

2. 现有 MiniSDP 信令通过裸 UDP 通道传输时效果最佳。此方式提升了弱连接环境下的成功率，但也带来了潜在的安全问题。

3. 基于 QUIC 的 MiniSDP 预计可提供优异的安全性，其信令建联时间介于 HTTP 和 UDP 指标之间，并且在弱连接环境下与 UDP 相比不会对成功率产生显著不利影响。

4. QUIC 的最终优势在于增强的安全性。QUIC 传输的所有内容默认均为加密，从而保护用户隐私。


<span id="1e3b4eba"></span>
### QUIC 标准传输

下图展示了基于 QUIC 的 MiniSDP 信令交互流程图。

<span>![图片](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/b7b4d52c622349299f9bf3bbb9ffb454~tplv-goo7wpa0wc-image.image) </span>

**初始 QUIC 连接**


1. 客户端生成 offer SDP。

2. 客户端根据指定协议将标准 SDP 压缩为 MiniSDP。

3. 客户端向服务器发送不完整 hello，请求服务器公钥。

4. 服务器返回带有服务器公钥、证书和随机数的拒绝消息。

5. 客户端验证证书并计算对称密钥（K1）。随后，客户端发送包含自身公钥、随机数以及用 K1 加密的 MiniSDP offer 的完整 hello 消息。最后，客户端通过已建立的 QUIC 通道，使用 HTTP/1.1 POST 方法发送 MiniSDP 数据缓冲区。

6. 服务器再次接收客户端回复，并根据指定协议将收到的 MiniSDP 解析还原为标准 SDP。

7. 服务器根据标准 SDP 对媒体数据执行回源，查询视音频媒体信息，并生成 answer SDP。

8. 服务器根据指定协议将标准 SDP 压缩为 MiniSDP。

9. 服务器生成临时服务器公钥 2，计算前向安全对称密钥 K2，并返回 server hello 以及用对称密钥 K2 加密的 MiniSDP answer。

10. 客户端接收 MiniSDP 请求，并根据指定协议将请求还原为标准 SDP。

11. RTP 传输启动，并按照传统 P2P 连接流程开始回放。


**后续 QUIC 连接**


1. 客户端生成 offer SDP。

2. 客户端根据指定协议将标准 SDP 压缩为 MiniSDP。

3. 客户端发送完整 hello，内容包括客户端公钥、随机数，以及用保存的服务器配置（包含服务器公钥）计算的对称密钥 K1 加密的 MiniSDP offer（MiniSDP over QUIC）。

4. 服务器再次接收客户端回复，并根据指定协议将收到的 MiniSDP 解析还原为标准 SDP。

5. 服务器根据标准 SDP 对媒体数据执行回源，查询视音频媒体信息，并生成 answer SDP。

6. 服务器根据指定协议将标准 SDP 压缩为 MiniSDP。

7. 服务器生成临时服务器公钥 2，计算前向安全对称密钥 K2，并返回 server hello 以及用对称密钥 K2 加密的 MiniSDP answer。

8. 客户端接收 MiniSDP 请求，并根据指定协议将请求还原为标准 SDP。

9. RTP 传输启动，并按照传统 P2P 连接流程开始回放。


**QUIC 失败降级**

客户端在与服务器建立 QUIC 连接时设置连接超时时间。若连接超时，则根据设定的重试次数发起重连。若多次尝试均失败，则连接降级为其他流媒体方式，如 HTTP\-FLV 或 HLS。


* **初始连接（1\-RTT 信令）** ：客户端保存服务器公钥，服务器也保存自身服务器公钥。服务器端保存的服务器公钥一周后过期，而客户端保存的服务器公钥不会过期。

* **后续连接（0\-RTT 信令）** ：当客户端进行 0\-RTT 连接时，若返回 server hello，则 0\-RTT 连接成功；若返回拒绝，则重新走 1\-RTT 连接流程。

* **QUIC数据发送（MiniSDP）** ：服务器打开一个支持QUIC协议的端口，客户端通过域名访问监听UDP端口的QUIC服务器，并通过QUIC通道以HTTP/1.1 POST方法（HTTP/HTTPS类型封装）将MiniSDP数据发送到对端。


<span id="89497b30"></span>
### QUIC快速传输

QUIC快速传输采用多路复用信令和媒体数据传输通道，消除首帧渲染过程中的ICE建立时间。

**信令请求流程**

与QUIC标准传输不同，使用快速路径时，建立交互连接的过程与媒体数据的传输和解码并行进行。这意味着服务器在ICE连接建立期间，将媒体数据发送给客户端进行解码和渲染。


* **QUIC标准传输**：服务器在ICE连接建立后，将媒体数据（RTP包）发送给客户端；

* **QUIC快速传输**：UDP（quic\-minisdp）信令通道实现多路复用。服务器在信令建立成功但ICE连接尚未建立时，通过信令通道发送媒体数据（RTP包）。ICE连接建立后，服务器切换到新的socket媒体通道，继续发送RTP包。


下图展示了QUIC快速传输的信令请求流程图。

<span>![图片](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/2302100ef57f400f901d738f93fd9efc~tplv-goo7wpa0wc-image.image) </span>


1. 客户端通过QUIC协议与服务器建立信令通道；

2. 服务器将远端应答发送给客户端；

3. 客户端建立ICE连接的同时，服务器将RTP数据包发送到信令socket QUIC。

4. 客户端激活内部的WebRTC视频接收引擎（video_recv_pipeline），使RTP数据包能够进入QUIC传输模块；

5. ICE连接建立后，服务器将RTP数据包发送到传输模块的传输socket。

### QUIC规范

基于QUIC的MiniSDP信令交互采用[gQUIC](https://www.chromium.org/quic)协议（QUIC协议的早期版本），并将持续演进以支持IETF QUIC（由互联网工程任务组（IETF）标准化的QUIC协议）。


* [QUIC线路布局规范](https://docs.google.com/document/d/1WJvyZflAO2pq77yOLbp9NsGjC1CHetAXV8I0fQe-B_U/edit#heading=h.o9jvitkc5d2g)

* QUIC规范兼容gQUIC Q043。
