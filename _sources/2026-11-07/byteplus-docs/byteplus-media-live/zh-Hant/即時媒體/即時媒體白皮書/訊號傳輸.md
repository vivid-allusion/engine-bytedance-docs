本章節介紹基於 HTTP、UDP 和 QUIC 協議的訊號互動。

<span id="685b18b6"></span>
## HTTP 訊號互動

**優點**：相容性極佳，支援瀏覽器／客戶端互通；可靠性高。

**缺點**：


* 在連線較弱、往返時間（RTT）較長或網路訊號不穩定的環境下，成功率較低；

* 播放請求的回應可能較慢或逾時，主要原因是訊號資料封包較大以及 TCP 重傳。


**傳輸方式**：在基於 HTTP 協議的標準 SDP 訊號情境下，資料於客戶端與伺服器間傳輸。

下圖展示基於 HTTP 協議的 SDP 訊號互動流程。

<span>![图片](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/a43c049e72374f6aaaf28b188b5b2ac1~tplv-goo7wpa0wc-image.image) </span>

<span id="99cb380c"></span>
### **訊號請求流程**


1. 客戶端產生 Offer SDP；

2. 客戶端透過 HTTP 協議向訊號伺服器發送資料請求（offer request），傳送描述資訊（Offer SDP）；

3. 伺服器收到 Offer SDP 請求後，對指定媒體資料來源進行重定向至原始伺服器，查詢音視頻媒體資訊，並產生標準 Answer SDP；

4. 伺服器回覆，向發起請求的客戶端發送回應（answer response）；

5. SDP 雙方完成協商後，建立 [ICE](https://docs.byteplus.com/en/docs/byteplus-media-live/docs-rtm-terminology#ice) 連線。客戶端再向伺服器查詢網路位址並完成握手；

6. RTP 傳輸啟動，並依傳統 P2P 連線流程開始播放。


<span id="9c81a2b3"></span>
### 停止播放流程

停止播放流程有兩種選項。更多資訊請參見 [結束媒體傳輸](https://docs.byteplus.com/en/docs/byteplus-media-live/docs-rtm-ending-transmission)。


* 推薦選項：透過 RTCP 媒體回饋通道向媒體伺服器發送 RTCP Bye 訊息；

* 備用選項：使用 UDP Socket 向訊號伺服器發送停止指令，由其控制媒體伺服器並停止資料傳輸；


<span id="1b02ad57"></span>
## UDP 訊號互動

UDP 訊號互動分為兩種：**UDP 標準路徑**與**UDP 快速路徑**。

<span id="d1deb45f"></span>
### UDP 標準路徑


* **優點**：首幀渲染速度更快，瞬時載入及成功率更高。

* **缺點**：在要求認證加密的區域會產生安全合規問題，且無法支援網頁瀏覽器。

* **傳輸方式**：透過 MiniSDP 協議以 UDP 傳輸；單一 UDP 資料封包請求即可傳送完整 SDP 壓縮資訊。


下圖展示 UDP 協議下 MiniSDP 訊號互動流程。

<span>![图片](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/bd4be5472b094b48a5211afa65faade1~tplv-goo7wpa0wc-image.image) </span>

<span id="2ed5f750"></span>
#### **訊號請求流程**


1. 客戶端產生 Offer SDP；

2. 客戶端依指定協議將標準 SDP 壓縮為 MiniSDP；

3. 客戶端透過 UDP socket 向訊號伺服器發送 offer request，傳送 MiniSDP（Offer SDP）；

4. 伺服器收到 MiniSDP 請求後，依指定協議解壓並還原為標準 SDP；

5. 伺服器依標準 SDP 對 FLV 資料進行重定向至原始伺服器，查詢音視頻媒體資訊並產生標準 SDP；

6. 伺服器依指定協議將標準 SDP 壓縮為 MiniSDP；

7. 伺服器透過 UDP socket 回覆 answer response，傳送 MiniSDP（Answer SDP）給客戶端；

8. 客戶端接收 MiniSDP 請求，並根據指定協議提取並還原請求為標準 SDP；

9. RTP 傳輸開始，並依照傳統 P2P 連線流程開始播放。


<span id="8064ac92"></span>
#### **停止播放流程**

停止播放的流程與 HTTP 訊號流程相同。詳細內容請參閱[結束媒體傳輸](https://docs.byteplus.com/en/docs/byteplus-media-live/docs-rtm-ending-transmission)。

<span id="ec7392aa"></span>
### UDP 快速路徑

UDP 快速路徑採用多路復用訊號與媒體資料傳輸通道，以消除第一幀渲染開銷中的 ICE 建立時間。

<span id="5276804a"></span>
#### 訊號請求流程

與 UDP 標準路徑不同，使用快速路徑時，建立互動連線的流程與媒體資料的傳輸與解碼同步進行。這表示伺服器在建立 ICE 連線的同時，將媒體資料傳送至客戶端進行解碼與渲染。


* **UDP 標準路徑**：伺服器在 ICE 連線建立後，將媒體資料（RTP 封包）傳送至客戶端；

* **UDP 快速路徑**：UDP 訊號通道進行多路復用。伺服器在訊號成功後但 ICE 連線尚未建立前，透過訊號通道傳送媒體資料（RTP 封包）。一旦 ICE 連線建立，伺服器切換至新的 socket 媒體通道，並持續傳送 RTP 封包。


下圖顯示 UDP 快速路徑的訊號請求流程圖。

<span>![图片](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/1e263a715486429b84b80e09e5288d0a~tplv-goo7wpa0wc-image.image) </span>


1. 客戶端透過 MiniSDP 與伺服器建立訊號通道；

2. 伺服器將遠端回覆傳送至客戶端；

3. 客戶端建立 ICE 連線的同時，伺服器同步將包含音視頻資料的 RTP 數據包傳送至訊號套接字。

4. 客戶端啟動 WebRTC，並於客戶端內部（PeerConnection）啟用視頻接收引擎（video_recv_pipeline），讓 RTP 數據包進入傳輸模組；

5. 一旦 ICE 連線建立，伺服器將 RTP 數據包傳送至傳輸模組的 socket。


<span id="08aa990c"></span>
#### 停止播放流程

停止播放的流程與 HTTP 訊號流程相同。詳細內容請參閱[結束媒體傳輸](https://docs.byteplus.com/en/docs/byteplus-media-live/docs-rtm-ending-transmission)。

<span id="601e00ad"></span>
## QUIC 訊號互動

QUIC 訊號互動是一種補充安全性的互動方案。QUIC 訊號互動與 HTTP/UDP 訊號互動有以下不同：


1. 標準化 SDP 訊號理想上透過 HTTP/HTTPS 並搭配 CDN 支援傳輸，但這會導致訊號連線時間最長，且在弱連線環境下成功率較低。

2. 當現有 MiniSDP 訊號透過裸 UDP 通道傳輸時，可獲得最佳效果。這提升了弱連線環境下的成功率，但也產生潛在安全問題。

3. MiniSDP over QUIC 預期可提供優異的安全性，訊號連線時間介於 HTTP 與 UDP 指標之間，且在弱連線環境下與 UDP 相比不會對成功率造成顯著負面影響。

4. QUIC 的終極優勢在於安全性提升。QUIC 傳輸的所有內容預設皆加密，從而保護用戶隱私。


<span id="1e3b4eba"></span>
### QUIC 標準傳輸

下圖顯示 MiniSDP Over QUIC 的訊號互動流程圖。

<span>![图片](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/b7b4d52c622349299f9bf3bbb9ffb454~tplv-goo7wpa0wc-image.image) </span>

**初始 QUIC 連線**


1. 客戶端生成 offer SDP。

2. 客戶端根據指定協議將標準 SDP 壓縮為 MiniSDP。

3. 用戶端發送初始 hello 給伺服器，以請求伺服器公鑰。

4. 伺服器回傳一個拒絕響應，內容包含伺服器的公鑰、憑證及隨機數。

5. 用戶端驗證憑證並計算對稱金鑰（K1）。然後發送完整 hello 訊息，內容包含其公鑰、一個隨機數，以及以 K1 加密的 MiniSDP offer。最後，使用 HTTP/1.1 POST 方法，透過已建立的 QUIC 通道傳送 MiniSDP 資料緩衝區。

6. 伺服器再次收到用戶端回應，並依據指定協議將收到的 MiniSDP 解出並還原為標準 SDP。

7. 伺服器根據標準 SDP，對媒體資料進行源伺服器重定向，查詢視聽媒體資訊，並產生 answer SDP。

8. 伺服器依據指定協議將標準 SDP 壓縮為 MiniSDP。

9. 伺服器產生臨時伺服器公鑰 2，計算前向安全的對稱金鑰 K2，並回傳 server hello 及以 K2 對稱金鑰加密的 MiniSDP answer。

10. 用戶端收到 MiniSDP 請求後，依據指定協議將請求解出並還原為標準 SDP。

11. 根據傳統 P2P 連線流程，開始 RTP 傳輸並啟動播放。


**後續 QUIC 連線**


1. 用戶端產生 offer SDP。

2. 用戶端依據指定協議將標準 SDP 壓縮為 MiniSDP。

3. 用戶端發送完整 hello，內容包含用戶端公鑰、隨機數，以及以已儲存伺服器配置（包含伺服器公鑰）計算出的對稱金鑰 K1 加密的 MiniSDP offer（MiniSDP over QUIC）。

4. 伺服器再次收到用戶端回應，並依據指定協議將收到的 MiniSDP 解出並還原為標準 SDP。

5. 伺服器根據標準 SDP，對媒體資料進行源伺服器重定向，查詢視聽媒體資訊，並產生 answer SDP。

6. 伺服器依據指定協議將標準 SDP 壓縮為 MiniSDP。

7. 伺服器產生臨時伺服器公鑰 2，計算前向安全的對稱金鑰 K2，並回傳 server hello 及以 K2 對稱金鑰加密的 MiniSDP answer。

8. 用戶端收到 MiniSDP 請求後，依據指定協議將請求解出並還原為標準 SDP。

9. 根據傳統 P2P 連線流程，開始 RTP 傳輸並啟動播放。


**QUIC 失敗降級**

用戶端在與伺服器建立 QUIC 連線時設置連線逾時。若連線逾時，則依照設定的重試次數發起重連。若多次重試仍失敗，則將連線降級為其他串流方式，例如 HTTP\-FLV 或 HLS。


* **初始連線（1\-RTT\-signaling）** ：用戶端儲存伺服器公鑰，伺服器也儲存自身的伺服器公鑰。伺服器儲存的伺服器公鑰一週後過期，而用戶端儲存的伺服器公鑰則不會過期。

* **後續連線（0\-RTT\-signaling）** ：當用戶端進行 0\-RTT 連線時，若收到 server hello 則 0\-RTT 連線成功；若收到拒絕則重新啟動 1\-RTT 連線流程。

* **QUIC 數據傳送（MiniSDP）** ：伺服器開啟一個支援 QUIC 協議的端口，客戶端透過域名訪問正在 UDP 端口上監聽的 QUIC 伺服器，並且 MiniSDP 數據透過 QUIC 通道以 HTTP/1.1 POST 方法（HTTP/HTTPS 類型封裝）傳送至對端。


<span id="89497b30"></span>
### QUIC 快速傳輸

QUIC 快速傳輸利用多路複用的信令與媒體數據傳輸通道，消除首幀渲染時的 ICE 建立時間。

**信令請求流程**

與 QUIC 標準傳輸不同，使用快速路徑時，建立互動連線的流程與媒體數據的傳輸與解碼同步進行。這表示伺服器在 ICE 連線建立期間，會將媒體數據傳送給客戶端進行解碼與渲染。


* **QUIC 標準傳輸**：伺服器在 ICE 連線建立完成後，將媒體數據（RTP 封包）傳送至客戶端；

* **QUIC 快速傳輸**：UDP（quic\-minisdp）信令通道進行多路複用。伺服器在信令成功但 ICE 連線尚未建立時，透過信令通道傳送媒體數據（RTP 封包）。一旦 ICE 連線建立，伺服器切換至新的 socket 媒體通道並持續傳送 RTP 封包。


下圖展示 QUIC 快速傳輸的信令請求流程圖。

<span>![图片](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/2302100ef57f400f901d738f93fd9efc~tplv-goo7wpa0wc-image.image) </span>


1. 客戶端透過 QUIC 協議與伺服器建立信令通道；

2. 伺服器將遠端回覆傳送給客戶端；

3. 客戶端建立 ICE 連線的同時，伺服器同步將 RTP 數據封包傳送至信令 socket QUIC。

4. 客戶端啟動內部的 WebRTC 視訊接收引擎（video_recv_pipeline），使 RTP 數據封包能進入 QUIC 傳輸模組；

5. ICE 連線建立完成後，伺服器將 RTP 數據封包傳送至傳輸模組的傳輸 socket。

### QUIC 規範

基於 QUIC 的 MiniSDP 信令互動採用 [gQUIC](https://www.chromium.org/quic) 協議（QUIC 協議的早期版本），並將持續演進以支援 IETF QUIC（由 Internet Engineering Task Force（IETF）標準化的 QUIC 協議）。


* [QUIC 線路佈局規範](https://docs.google.com/document/d/1WJvyZflAO2pq77yOLbp9NsGjC1CHetAXV8I0fQe-B_U/edit#heading=h.o9jvitkc5d2g)

* QUIC 規範與 gQUIC Q043 相容。
