Upsert Kafka Connector supports reading data from a Kafka topic in upsert mode and writing data to a Kafka topic, serving as both a source and sink table.


* As a source table, the Upsert Kafka Connector can convert data stored in Kafka into a changelog stream, where each data record represents an update or delete event. In the data record, a key indicates an UPDATE; absence of a key indicates INSERT; and a key with an empty value indicates DELETE.

* As a result table, the Upsert Kafka Connector can consume changelog streams generated by upstream computation logic. It writes INSERT or UPDATE_AFTER data as regular Kafka messages, and writes DELETE data as Kafka messages with empty values to indicate the deletion of messages associated with that key.

   Flink partitions data based on the values of the Primary Key columns to ensure that messages on the same Primary Key are ordered and thus updates or deletes on the same Primary Key will be in the same partition.


<span id="153606e7"></span>
## Usage Restrictions

The Upsert\-kafka Connector is currently only supported in the **Flink 1.16\-byted** engine version.

<span id="05ded5cb"></span>
## DDL Definition

```SQL
CREATE TABLE upsert_kafka_sink (
  user_region STRING,
  pv BIGINT,
  uv BIGINT,
  PRIMARY KEY (user_region) NOT ENFORCED
) WITH (
  'connector' = 'upsert-kafka',
  'topic' = '<yourTopicName>',
  'properties.bootstrap.servers' = '...',
  'key.format' = 'avro',
  'value.format' = 'avro'
);
```

## WITH Parameters


|**Parameters** |**Mandatory** |**Default Value** |**Data Type** |**Description** |
|---|---|---|---|---|
|connector |Yes |(none) |String |Specifies the connector to use, in this case, the upsert\-kafka connector. |
|topic |Yes |(none) |String |Specifies the name of the Kafka topic used for reading or writing. |
|properties.bootstrap.servers |Yes |(none) |String |A comma\-separated list of Kafka brokers, formatted as `host:port,host:port`. |
|properties.\* |No |(none) |String |Configuration parameters passed to Kafka, for specific parameters, please see [configuration](https://kafka.apache.org/documentation/#configuration).<br><br>Flink will remove `properties.` and pass the remaining configuration to the underlying KafkaClient.<br><br>'properties.allow.auto.create.topics' = 'false' disables automatic Topic creation. |
|key.format |Yes |(none) |String |The format for serialization and deserialization used when reading or writing the key part of Kafka messages supports `csv`, `json`, `avro`, `confluent-avro`, `raw`. |
|key.fields |No |(none) |String |The key part of the Kafka message corresponds to the source or result table field. Multiple field names are separated by a semicolon (;). For example `field1;field2`. |
|key.fields\-prefix |No |(none) |String |Define custom prefixes for all `key.fields` to avoid conflicts with `value.fields` field names.<br><br>Example: Specify a prefix as prefix_, and if the Key field name is name, it will appear as prefix_name after being written into Kafka.<br><br><div data-tips="true" data-tips-type="tip" data-tips-is-title="true">tip</div><br><br><br><br>* <div data-tips="true" data-tips-type="tip"><code>key.fields-prefix</code> is used only to distinguish column names between source tables and result tables, and this prefix will be removed when parsing and generating the Kafka message key.</div><br><br><br>* <div data-tips="true" data-tips-type="tip">If using <code>key.fields-prefix</code>, then <code>value.fields-include</code> must be set to <code>EXCEPT_KEY</code>.</div><br> |
|value.format |Yes |(none) |String |The format used for serialization and deserialization of the value part when reading from or writing to Kafka messages, supports `csv`, `json`, `avro`, `confluent-avro`, `raw`. |
|value.fields\-include |No |ALL |String |Controls which fields should appear in the value.<br><br><br>* ALL: By default, the value part of the message will include all fields in the schema, including those defined as primary keys.<br><br>* EXCEPT_KEY: The value part of the message will include all fields in the schema except those defined as primary keys. |
|scan.parallelism |No |(none) |Integer |Set the source concurrency independently. If not set, the parallelism will default to the job's concurrent number.<br><br>This parameter is often used in scenarios where the Source and downstream operators need to break the operator chain, allowing downstream recomputing operators to use higher default parallelism, enhancing their computational ability. At the same time, it maintains the Source parallelism equal to the number of Kafka partitions. As a result, due to different parallelisms, data shuffling from Source to downstream is uniform, thereby optimizing the overall computation rate. |
|sink.parallelism |No |(none) |Integer |Defines the parallelism of the upsert\-kafka sink operator. By default, it maintains consistency with the parallelism of upstream operators, determined by the framework. |
|sink.buffer\-flush.max\-rows |No |0 |Integer |Maximum number of records that can be cached. The default value is 0, meaning caching is not enabled.<br><br>When the sink receives many updates with the same key, the cache will retain the last record of the same key, thus the sink cache can help reduce the amount of data sent to the Kafka topic.<br><br><div data-tips="true" data-tips-type="tip" data-tips-is-title="true">tip</div><br><br><br><div data-tips="true" data-tips-type="tip">If caching needs to be enabled, then both <code>sink.buffer-flush.max-rows</code> and <code>sink.buffer-flush.interval</code> must be set with values greater than 0.</div><br> |
|sink.buffer\-flush.interval |No |0 |Duration |The interval for refreshing the cache; data in the cache will be refreshed after this time period has passed. The default value is 0, which means that caching is not enabled.<br><br>When the sink receives many updates with the same key, the cache will retain the last record for each key, thereby helping to reduce the volume of data sent to the Kafka topic.<br><br><div data-tips="true" data-tips-type="tip" data-tips-is-title="true">tip</div><br><br><br><div data-tips="true" data-tips-type="tip">If caching needs to be enabled, then both <code>sink.buffer-flush.max-rows</code> and <code>sink.buffer-flush.interval</code> must be set with values greater than 0.</div><br> |

## Sample Code


* Source Table

   ```SQL
   CREATE TABLE upsert_source (
        order_id bigint,
        order_product_id bigint,
        order_customer_id bigint,
        order_status varchar,
        order_update_time timestamp,
        PRIMARY KEY (order_id) NOT ENFORCED
        )
        WITH (
     'connector' = 'upsert-kafka',
     'topic' = 'source',
     'properties.bootstrap.servers' = 'localhost:9092',
     'properties.group.id' = 'group_01', 
     'key.format' = 'json', 
     'value.format' = 'json'  
   );
   
    CREATE TABLE print_sink (
        order_id bigint,
        order_product_id bigint,
        order_customer_id bigint,
        order_status varchar,
        order_update_time timestamp
       )
   WITH (
        'connector' = 'print'           
   );
   
   insert into print_sink
   select * from upsert_source; 
   ```
   

* Result Table

   ```SQL
   CREATE TABLE datagen_source (
        order_id bigint,
        order_product_id bigint,
        order_customer_id bigint,
        order_status varchar,
        order_update_time as localtimestamp
       )
   WITH (
        'connector' = 'datagen',
        'rows-per-second' = '5'          
   );
   
   CREATE TABLE upsert_sink (
        order_id bigint,
        order_product_id bigint,
        order_customer_id bigint,
        order_status varchar,
        order_update_time timestamp,
        PRIMARY KEY (order_id) NOT ENFORCED
   ) WITH (
     'connector' = 'upsert-kafka',
     'topic' = 'sink',
     'properties.bootstrap.servers' = 'localhost:9092',
     'properties.group.id' = 'group_01', 
     'key.format' = 'json', 
     'value.format' = 'json'  
   );
   
   
   INSERT INTO upsert_sink
   SELECT * FROM datagen_source;
   ```
